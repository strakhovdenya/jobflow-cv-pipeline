# Ralph Loop — правила автономной работы

Этот файл — рабочие правила для одной автономной итерации Ralph loop. Выбор Issue, base branch
и промпт итерации — не текст в конфиге, а код: `.claude/hooks/ralph-core.js` сам выбирает
следующий готовый Issue, сам решает, от какой ветки/main его ответвлять, сам создаёт git worktree
и сам генерирует короткий промпт для `claude -p`. Этот файл описывает, что происходит внутри
одной итерации и по каким правилам она должна себя вести — читай его как контекст, который
`ralph-core.js` вставляет в начало промпта каждой итерации.

## Настройка (один раз)

`.claude/ralph.config.json` — **не в git** (`.gitignore`). Он содержит живой список задач
(`issues`), флаг `enabled` и рантайм-счётчик `iterationsRun`, которые постоянно меняются (сам
цикл их переписывает, и ты сам будешь менять список задач под текущую работу) — если бы файл был
трекаемым, любое переключение веток рисковало бы конфликтом с незакоммиченной правкой, а
`enabled: true` мог бы случайно закоммититься и достаться следующей сессии/клону. Перед первым
использованием: скопируй `.claude/ralph.config.example.json` → `.claude/ralph.config.json` и
отредактируй список `issues` под актуальную задачу.

## Запуск и остановка (важно!)

`hooks.Stop` в `.claude/settings.json` глобален — он читается в **любой** сессии Claude Code в
этом репозитории, не только во время специально запущенного Ralph loop. Чтобы обычный
интерактивный чат не запускал автономную реализацию Issue сам по себе после каждого ответа,
`.claude/hooks/stop.js` — no-op, пока `.claude/ralph.config.json`'s `"enabled"` не `true`
(дефолт в `ralph.config.example.json` — `false`). Он же no-op (не падает), если файла вообще нет —
это ожидаемо внутри worktree одной итерации (см. ниже: git worktree наследует `hooks.Stop` из
той же ветки, но не гитигнорённый `ralph.config.json`, которого там просто никогда не было).

- **Запуск**: `node .claude/hooks/ralph-start.js` из обычного терминала (не из интерактивного
  чата) — ставит `enabled: true` в `ralph.config.json` и сразу выполняет первую итерацию.
  Можно и вручную поставить `"enabled": true` в файле, если следующим шагом сам вызовешь
  `node .claude/hooks/stop.js` (или дождёшься следующего `Stop` любой сессии).
- Пока `enabled: true`, каждый `Stop` любой claude-сессии **в этой рабочей директории**
  (не внутри worktree итерации — см. предыдущий абзац) продолжает цикл.
- **Остановка**: `.claude/hooks/ralph-core.js` сам ставит `enabled: false` (переписывая файл),
  когда все Issue из конфига закрыты. Если нужно прервать цикл раньше — поставь `enabled: false`
  вручную.
- Если все оставшиеся Issue уже имеют открытый PR (ждут review/merge) — цикл сам приостанавливается
  (`enabled` остаётся `true`); следующий `Stop` снова проверит состояние и продолжит, как только
  PR смёрджен.

## Изоляция через git worktree (важно!)

Каждая итерация работает не в основной рабочей директории, а в отдельном git worktree —
`../jobflow-cv-pipeline-ralph-worktrees/issue-<n>` (соседняя папка, не внутри самого репозитория).
`claude -p` запускается с `cwd`, указывающим внутрь этого worktree.

Причина — обнаружено на живом прогоне (#215, 2026-08-29): итерация в рамках реализации Issue
делает реальные `git checkout`/`git branch` операции. Если бы это происходило в той же рабочей
директории, где живёт сам контроллер (`ralph-core.js`/`ralph.config.json`), переключение ветки
итерацией физически убирало бы эти файлы с диска (если целевая ветка их не содержит) —
следующий шаг контроллера (запись `iterationsRun`) падал бы с `ENOENT`/`MODULE_NOT_FOUND`.
Worktree даёт итерации собственный чекаут поверх той же самой `.git`-базы объектов — она может
свободно переключать ветки внутри своей директории, не трогая основной чекаут вообще.

- Ветку и base branch для worktree выбирает `ralph-core.js` **до** запуска `claude -p`
  (`branchNameFor`/`resolveBaseRef`) — независимый Issue ответвляется от `origin/main`,
  зависимый — от ветки ещё не смёрженной зависимости (`task/ISSUE-<depId>-...`, стек PR, см. ниже).
  Сама итерация не выбирает и не создаёт ветку — она уже находится на правильной.
- После успешной итерации (PR создан) worktree удаляется — но только если `git status --porcelain`
  внутри него действительно пуст; если что-то осталось незакоммиченным несмотря на успешный выход
  `claude -p`, worktree оставляется для разбора, а не удаляется вслепую (`git worktree remove
  --force` в остальных случаях).
- После неудачной итерации (нештатный выход, например `--max-turns` исчерпан) worktree
  **оставляется** — путь печатается в лог для разбора, что успело произойти, прежде чем прогонять
  заново.
- **Права git/gh внутри worktree.** Свежий worktree получает только трекаемые файлы — личный
  `.claude/settings.local.json` (там живёт широкий `git */gh *` allow для интерактивной работы)
  в него не попадает вообще. Поэтому `ralph-core.js` сразу после `git worktree add` сам пишет
  **отдельный, узкий** `.claude/settings.local.json` внутрь worktree (`writeWorktreePermissions`)
  — только конкретные команды, которые реально нужны одной итерации (`git add/commit/push/status/
  diff/log/fetch`, `gh issue view/comment/edit`, `gh pr create/list`, `gh label list`), без
  `git push --force`/`git reset --hard`/`gh pr merge`/`gh repo delete` и без общего широкого
  `git */gh *`. Это осознанно уже, чем личные права в основном чекауте — least privilege для
  агента, работающего без присмотра, не копия человеческих прав. Найдено живьём на прогоне
  #215 (2026-08-29, после мёрджа #294): без этого механизма итерация сообщила "`gh` is blocked
  by the settings policy" и не смогла ничего сделать.

## Ограничители (`maxIterations`, `maxTurns`)

- `maxIterations` — сколько раз за один прогон (с момента, когда `enabled` в последний раз стал
  `true`) `ralph-core.js` вообще запустит `claude -p`, независимо от того, сколько Issue ещё
  осталось. Счётчик — `iterationsRun` в том же файле, сбрасывается в `0` при каждом
  `ralph-start.js`/`setEnabled(true)`. Когда счётчик достигает `maxIterations`, loop сам ставит
  `enabled: false` и останавливается — это самый внешний предохранитель от неограниченного
  автономного прогона, полезный в первую очередь для тестового/проверочного запуска (например,
  `maxIterations: 1`, чтобы проверить ровно одну итерацию перед тем как доверять всей цепочке).
- `maxTurns` — передаётся в саму итерацию как `claude -p ... --max-turns <N>`: ограничивает,
  сколько ходов агент сделает **внутри одной** итерации, прежде чем принудительно остановится,
  даже если ещё не закоммитил/не создал PR. Защищает от одной зависшей/зацикленной итерации,
  а не от цикла в целом (для этого — `maxIterations`). `ralph-core.js` оборачивает запуск в
  `try/catch` — исчерпанный `--max-turns` (ненулевой exit code) не роняет весь контроллер,
  а логируется как неудачная итерация; `iterationsRun` инкрементируется в любом случае.

## Выбор Issue и base branch (делает код, не промпт)

- `ralph-core.js`'s `classify()` берёт ровно один открытый Issue за итерацию — первый в списке
  `issues` из `ralph.config.json`, у которого выполнены все зависимости из `dependsOn` (каждая
  зависимость уже `done` — смёрждена — либо `in-flight` — есть открытый PR, то есть её ветка уже
  существует). Issue, зависимости которого ещё не готовы, помечается `waiting` и пропускается —
  на него возьмётся отдельная будущая итерация, как только его зависимость сама будет взята.
- Порядок элементов в `issues` — только приоритет среди одновременно готовых, не зависимость.
  Единственный источник зависимостей — поле `dependsOn`.
- Issue, для которого уже есть открытый или смёрженный PR (`gh pr list --search
  "head:task/ISSUE-<n>-"`), считается уже обработанным предыдущей итерацией — не берётся заново.
- Base branch: независимый Issue (`dependsOn: []`) — от `origin/main`; зависимый — от ветки
  зависимости (`task/ISSUE-<depId>-...`), если она ещё не смёрждена, иначе тоже от `origin/main`.
  Цепочка может выглядеть как `main -> task/ISSUE-215-... -> task/ISSUE-282-... ->
  task/ISSUE-287-...`, пока эти изменения ещё не интегрированы в `main`.
- Имя ветки — `<branchPrefix><id>-<slug(title issue)>`, вычисляется детерминированно из
  `ralph.config.json`'s `branchPrefix` и заголовка issue (`gh issue view`), не придумывается
  агентом.

## Именование коммитов

- По правилам `git-commit` skill / корневого `CLAUDE.md` Git/PR order: conventional commit,
  `<type>: ISSUE-<n> ...` (`<type>` — реальный тип по характеру изменения: `feat`/`fix`/`docs`/
  `chore`/`refactor`/`test`, не всегда `feat`).

## Правила реализации

- Сначала тесты — потом реализация (TDD), где применимо к характеру задачи.
- После каждого финального изменения прогоняй relevant tests/`tsc --noEmit`/lint для затронутых
  `apps/*`.
- Если тесты остаются красными после 5 попыток исправить — остановись, **не коммить**, напиши
  `BLOCKED: <описание проблемы>` комментарием в Issue (`gh issue comment <n> --body "BLOCKED: ..."`)
  и заверши итерацию без коммита и без закрытия Issue.
- **Если реализация требует менять `apps/api/prisma/prompts` (AI-промпты) или
  `apps/api/knowledge-sources` (база знаний)** — не делай эти изменения автоматически. Это
  осознанное, продуктовое решение, а не рутинный код-фикс, и должно проходить через человека, а не
  через автономный цикл. Останови работу над этим Issue: без коммита, без ветки с изменениями, без
  push, без PR. Поставь лейбл `ralph-needs-prompt-change` (`gh issue edit <n> --add-label
  ralph-needs-prompt-change`) и оставь комментарий с точным описанием, что и почему нужно поменять.
  `ralph-core.js` распознаёт этот лейбл и больше не будет пытаться взять этот Issue (а также любой
  Issue, который на него транзитивно завязан через `dependsOn`) — только на что-то незаблокированное.
  Loop останавливается, когда ничего незаблокированного не осталось; продолжить его можно, только
  вручную внеся нужные изменения в prompts/knowledge-sources и сняв лейбл.
- **Не запрашивай разрешения (permission) и не редактируй `.claude/settings.json`/
  `.claude/settings.local.json`, чтобы обойти их.** Если тебе не хватает разрешения на команду —
  это сигнал остановиться и сообщить об этом в комментарии к Issue (как при `BLOCKED`), а не
  самостоятельно расширять себе права. `.claude/settings.json` — файл политики безопасности,
  редактировать его для конкретного Issue вне его Acceptance Criteria — не твоя задача.
  (Найдено живьём на прогоне #215, 2026-08-29 — итерация сама отредактировала `settings.json`,
  чтобы снять с себя ограничение.)

## Правила завершения итерации

- Убедись, что все относящиеся к задаче тесты зелёные.
- Убедись, что все Acceptance Criteria в теле Issue выполнены и отмечены `[x]`.
- Пройди Task Closure Checklist из корневого `CLAUDE.md` (кроме шагов, явно исключённых для
  Ralph-режима — см. ниже).
- Опционально: запусти skill `code-review` (`/code-review`) по итоговому diff перед коммитом, если
  задача достаточно рискованная, чтобы это оправдать.
- Закоммить изменения в текущую ветку (ты уже на ней — см. "Изоляция через git worktree" выше),
  сделать `git push -u origin <branch>` и создать PR (`gh pr create --base <base-branch> --body
  'Closes #<n> ...'`), где `<base-branch>` — та же ветка, от которой была создана текущая
  (её тебе назвал промпт итерации). Issue закрывается автоматически при мёрже PR, не отдельной
  командой.
- Не мёрджи созданный PR и не жди его review/merge — это делает человек вручную в GitHub. После
  создания PR итерация сразу останавливается.

## Осознанные отступления от стандартного процесса (только внутри Ralph-режима)

- **Без Plan-first и без confirm-before-push/PR.** Issue уже полностью специфицирован (это и есть
  выполненный Issue-first protocol) — Ralph-итерация не останавливается для подтверждения плана
  или для подтверждения push/PR у пользователя, в остальном следует обычному Git/PR order из
  корневого `CLAUDE.md` (add → commit → push → `gh pr create` с `Closes #<n>`).
- **Без выбора Issue/base branch самим собой** — это уже сделал `ralph-core.js` до запуска
  (см. "Выбор Issue и base branch" выше). Отступление от обычной работы в том, что агенту не
  нужно (и не следует) самому решать, откуда ветвиться.
- Стек PR по зависимостям: для зависимого Issue, чья зависимость ещё не смёрждена, PR указывает
  на ветку зависимости, а не на `main`. Репозиторий настроен на автоудаление ветки при мёрже
  (`deleteBranchOnMerge: true`), поэтому GitHub сам ретаргетит такой PR на `main`, когда PR
  зависимости мёрджится и её ветка удаляется — вручную ничего перецеплять не нужно.
- После push + создания PR итерация останавливается. `.claude/hooks/stop.js` сам проверяет через
  `gh issue view`/`gh pr list`, для каких Issue ещё нет PR, и либо запускает следующую итерацию
  (`claude -p ...`) для незапущенного Issue, либо (если все оставшиеся уже имеют открытый PR)
  останавливает loop и ждёт, пока человек смёрджит PR вручную — это не задача текущей итерации.

## Не делай

- Не смешивай изменения разных Issue в одной ветке/коммите.
- Не переходи к следующему Issue в рамках одной и той же итерации.
- Не мёрджи PR и не жди его мёржа — только создай (см. выше).
- Не начинай Issue заново, если для него уже есть открытый или смёрженный PR (в процессе ревью).
- Не считай зависимость интегрированной только потому, что её Issue закрыт — фактически проверь,
  что base branch содержит нужные изменения.
- Не переключай ветку и не создавай новую — ты уже на правильной (см. "Изоляция через git
  worktree" выше).
- Не редактируй `.claude/settings.json`/`.claude/settings.local.json` (см. "Правила реализации").
