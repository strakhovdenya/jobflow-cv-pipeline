# Ralph Loop — deterministic orchestrator + constrained coding agent

Автономный цикл: по списку GitHub issues с зависимостями (`dependsOn`) сам берёт следующий
готовый issue, реализует его и создаёт PR — без участия человека на каждом шаге. Мёрдж PR всегда
делает человек вручную.

Это **вторая, полностью пересобранная версия** — первая (git worktree + `hooks.Stop`) была
отброшена после трёх подряд неудачных живых прогонов (см. Git-историю ISSUE-294 и
`project-management/TEST_LOG.md` за 2026-08-29/30). Ниже — почему архитектура именно такая.

## Ключевой принцип: Claude не управляет git/gh вообще

Вложенный `claude -p` **не имеет** прав на `git commit`/`push`, `git worktree`, ни на что из `gh`.
Его единственная задача — отредактировать код в уже подготовленной директории, прогнать
тесты/lint/typecheck, и завершить ответ ровно одним из трёх вердиктов:

```
DONE
TYPE: <feat|fix|docs|chore|refactor|test>
SUMMARY: <короткое описание>
```
```
BLOCKED: <причина>
```
```
BLOCKED-PROMPT-CHANGE: <что и почему>
```

Промпт также явно требует `BLOCKED: <...>` в ещё двух случаях: если что-то отклонено по
правам доступа (не пытаться обойти другим синтаксисом — это тот же самый отказ, не
path/shell-проблема) и если для продолжения нужно решение человека (неоднозначная
формулировка, несколько разумных вариантов реализации) — агент работает без присмотра, гадать
хуже, чем остановиться.

Всё остальное — выбор issue, base branch, клон, коммит, push, создание PR, комментарии/лейблы на
issue при `BLOCKED` — делает **контроллер** (`run.js`/`core.js`), обычным детерминированным кодом.

Почему: первая версия давала агенту `git add/commit/push`, `gh issue ...`, `gh pr create` внутри
git worktree. Комбинация "агент сам управляет git lifecycle" + "worktree, чей `.git` — файл-
указатель наружу, а не обычная директория" оказалась хрупкой на практике — три живых прогона на
issue #215 показали, что headless `claude -p` внутри worktree то видит директорию пустой, то
сообщает о заблокированном доступе к основному репозиторию, один раз просто зависал. Ни перенос
worktree внутрь репозитория, ни сужение прав это не исправили — значит проблема была не в правах
и не в расположении, а в самом факте "агент делает git mutations внутри worktree". Убрав у агента
git/gh полностью и заменив worktree на обычный `git clone` (`.git` — директория, не файл-
указатель), заодно устраняется и класс "агент сам отредактировал `settings.json`, чтобы обойти
ограничение" — агенту просто нечего обходить, у него нет доступа к тому, что он мог бы захотеть
обойти.

## Почему не `hooks.Stop`

Первая версия запускала цикл через `settings.json`'s `hooks.Stop` (реагирует на завершение хода
**любой** сессии Claude Code в репозитории) — потребовало отдельного gate на `enabled`, потому что
чуть не запустило автономную реализацию issue прямо во время обычного интерактивного чата.
Дальше — скрытая рекурсия: сессия завершается → `Stop` → контроллер → спавнит новую `claude -p`
сессию → у неё тот же `Stop`-хук. Непрозрачно и сложно отлаживать.

Вместо этого — обычный внешний процесс с явным `while`-циклом: `node .claude/ralph/run.js`.
Никакого хука, никакой скрытой рекурсии.

## Ещё три находки со Stage 2 (2026-08-30/31), тоже исправлены

- **Свежий `git clone` не содержит `node_modules`** (гитигнорится, как в любом чекауте). Реальный
  прогон висел 23 минуты без единого напечатанного слова — агент, скорее всего, пытался прогнать
  тесты без установленных зависимостей и не имел прав на `npm install`, чтобы это исправить.
  Исправлено: контроллер сам ставит зависимости (`npm install` в `apps/api`/`apps/web`) сразу
  после клонирования, **до** запуска агента — это environment setup, не "реализация issue",
  поэтому её делает контроллер, а не агент.
- **`Edit` и `Write` — два разных права**, не одно. `Edit` меняет существующий файл, `Write`
  создаёт новый. Дав только `Edit`, получили реальный прогон, где агент дважды получил отказ на
  `Write` нового spec-файла и десяток ходов подряд пытался обойти это через Bash (echo/heredoc/
  python/node -e/PowerShell/cygpath) — ни один из этих способов тоже не был разрешён.
- **Точный матчинг команд слишком узкий.** `'Bash(npm run test)'` (без wildcard) не покрывает
  `npm run test -- --testPathPattern=...` — это уже другая строка команды. Агент честно пытался
  диагностировать (`cd`/`Set-Location`/`--prefix`, чтение `settings.json`), но всё равно упирался.
  Исправлено на широкие `'Bash(npm run *)'`/`'Bash(npx *)'` — по-прежнему не даёт трогать git/gh/
  файлы вне `runDir`, просто не привязано к точному написанию флагов.

Живой лог агента (не только финальный ответ) виден через `--output-format stream-json` —
`runAgent()` разбирает NDJSON построчно и печатает читаемую строку на каждое событие (assistant
text, `🔧 <tool>: <кратко>`, `🏁 ходов: N, Ns`) вместо того, чтобы ждать, пока весь ответ
накопится и напечатается разом (как было в первой версии на plain-text `-p`).

## `CLAUDE.md` в клоне противоречит автономному режиму — промпт это явно снимает

`CLAUDE.md` (корневой и `apps/api/`, `apps/web/`) — git-tracked файлы, поэтому они есть в каждом
клоне, и Claude Code загружает их автоматически как обязательные инструкции. Написаны они для
интерактивной работы с человеком за клавиатурой, и целый ряд их правил автономному агенту либо
невыполним, либо прямо противоречит его роли: **Plan-first** («составь план и жди подтверждения») —
подтверждать некому; **Read First** (`gh issue view <n>`), **Issue-first** (`gh project item-add`),
**Branch-first** (`git status`, переключение на `main`, `git pull`, создание ветки) и **Git/PR
order** (`git commit`/`push`/`gh pr create`) — требуют git/gh, которых у агента нет; **Task Closure
Checklist** — требует отметить AC через `gh` и дважды *спросить пользователя* (про `/code-review` и
про README).

Это не теория: в реальном прогоне #282 агент первой же командой выполнил
`gh issue view 282 2>/dev/null | head -50 || echo "gh not available"` — ровно по правилу «Read
First», впустую потратив ход.

`buildPrompt()` теперь явно снимает этот конфликт: перечисляет организационные протоколы, которые
за агента выполняет контроллер (и которые не надо пытаться выполнять), и отдельно подтверждает, что
всё содержательное из `CLAUDE.md` — Architecture Rules, Key Invariants, Testing Rules (ADR-020),
Documentation Rules, Anti-Overclaiming Rules, ADR'ы из `DECISIONS.md`, стиль кода — применяется в
полном объёме. Формула: организационные протоколы вокруг задачи — контроллера; правила о том, каким
должен быть сам код, — агента.

**Закрыто:** запись в `project-management/TEST_LOG.md` теперь пишет контроллер
(`appendTestLogEntry()` в `core.js`, вызывается в `runIssue()` перед коммитом — попадает в тот же
коммит, что и сама реализация) — не агент, которому это явно запрещено. Запись честно помечена
"Agent-reported DONE — self-reported ..., not independently re-run by the controller", поскольку
контроллер не перезапускает тесты сам, а доверяет вердикту агента. PR #298/#299, сделанные до этого
изменения, этой записи не имеют — известный пробел только для них.

## Качество результата — что нашлось при ручном ревью #215/#282 (2026-08-31)

Живые прогоны на реальных issue (#215, #282) технически завершались `DONE`, тесты были зелёными,
но при ручном код-ревью после того, как всё это уже прошло, нашлось несколько содержательных
проблем — не в коде "не работает", а в коде "выглядит правильным, но не делает того, для чего
написан":

- **#215**: regression-тест на `apply`/`maybe`/`skip` использовал `content.toContain('"apply"')`
  по всему файлу промпта — а эти слова десятки раз встречаются в обычной прозе промпта, не
  привязанные к самой схеме вывода. Проверено вживую: убрал реальный union
  `"decision": "apply" | "maybe" | "skip"` из промпта — тест остался зелёным. Классический
  false negative: тест выглядел правильным, но не ловил ровно ту регрессию, ради которой писался.
- **#215**: агент скопировал данные из `prisma/seed.ts` в отдельный ручной `TEMPLATE_REGISTRY` с
  комментарием "синхронизируй вручную при новой версии", вместо того чтобы устранить настоящее
  препятствие (`seed.ts` запускает реальный сид БД при импорте) — которое решается тремя строками
  (`if (require.main === module)` + `export`).
- **#282**: AC про "запрещённые заявления"/"канонические имена" реализованы и unit-протестированы
  только на крошечных придуманных агентом строках — ни разу не прогнаны на настоящих файлах
  `apps/api/knowledge-sources/`, которые были прямо в рабочей директории. Прогнал вживую: из 17
  извлечённых "канонических имён" реальными техническими терминами не было ни одного (имена
  файлов, подписи контактных полей, имя кандидата, шаблон-плейсхолдер).
- **#282**: Test Requirement issue ссылался на `project-management/golden-dataset/` как источник
  реальных `02_targeted_cv_content.json` — таких файлов там нет и никогда не было (они лежат в
  gitignored `apps/api/storage/applications/`). Агент тихо подставил синтетическую fixture вместо
  того чтобы остановиться и спросить.

Общий паттерн: агент считает задачу законченной, когда тесты зелёные — не когда сам убедился, что
тесты и логика реально работают на настоящих данных. `buildPrompt()` теперь явно требует: (1) для
каждого нового assertion вида "текст содержит подстроку X" (`toContain`/`toMatch`/`includes` —
именно substring/keyword-проверки, не structural assertions вроде `toEqual`) — сломать то, что он
должен ловить, и проверить, что тест падает, прежде чем DONE; (2) прогонять код на реальных файлах
репозитория, а не только на придуманных фикстурах, если он их обрабатывает; (3) `BLOCKED`, а не
тихая замена, если issue ссылается на несуществующий путь; (4) устранять препятствие в источнике
данных, а не дублировать данные вручную. Все четыре находки исправлены вручную в PR #298/#299 (не
автономным прогоном) — эти правила в промпте не проверены живым прогоном, который бы их поймал сам;
следующий реальный прогон на #287 или новой задаче — первая живая проверка.

Мутационная проверка (1) намеренно сужена до substring/keyword-assertions, а не применяется ко
всем тестам подряд — это единственный класс ошибки, который реально наблюдался (ложноотрицательный
`toContain` в #215), и полная версия правила стоила бы ~3 хода на каждый тест в задаче, что на
задаче с 10 тестами — треть бюджета ходов впустую.

## Ещё четыре правки после анализа всего промпта целиком (2026-08-31)

Отдельный анализ всего `buildPrompt()` целиком (не по одной находке за раз) вскрыл более
системную проблему и три более мелкие:

- **`CLAUDE.md` в клоне конфликтовал с автономным режимом** — см. отдельный раздел выше. Это была
  самая серьёзная находка: агент реально терял ход на `gh issue view` в живом прогоне #282, следуя
  инструкции из `CLAUDE.md`, которую сам промпт нигде не отменял.
- **Отказ прав на `apps/api/prisma/prompts`/`apps/api/knowledge-sources` маршрутизировался
  неправильно.** После того как в `writeAgentPermissions()` добавили `deny` на эти пути (см.
  "Ещё три находки" выше), отказ прав на попытку их отредактировать давал обычный `BLOCKED`, а не
  `BLOCKED-PROMPT-CHANGE` — то есть контроллер не ставил лейбл `ralph-needs-prompt-change`, и
  issue оставалась незаблокированной для повторного выбора в следующем прогоне, который снова
  упёрся бы в то же самое. Исправлено явным исключением в правиле про отказ прав.
- **Промпт не сообщал бюджет ходов, что `npm install` уже сделан контроллером, и что read-only git
  разрешён для самопроверки.** Первая попытка #282 сожгла 50 ходов на исследование и потеряла всё
  на исчерпании лимита — модель не знала, что бюджет вообще ограничен и конечен.
- **`DONE` не требовал самоотчёта по Acceptance Criteria.** Обе реальные дыры в #282 (AC "закрыты"
  формально, но не по сути) обнаружились бы раньше, если бы модель перед DONE была обязана коротко
  и конкретно написать, чем закрыт каждый пункт AC — не общими словами.

`project-management/TEST_LOG.md` теперь пишет контроллер (`appendTestLogEntry()`), не агент — см.
раздел выше про `CLAUDE.md`.

## Модель и effort закреплены явно (найдено при ручном ревью #287, 2026-09-01)

Живой прогон #287 (первый после всех правок промпта выше) технически завершился `DONE`, тесты были
зелёными — но при ручном код-ревью выяснилось, что агент тихо нарушил собственный же Key Invariant
issue (запрет трогать реальные строки `KnowledgeSource` в dev-БД): вместо честной изоляции он
деактивировал все реальные активные строки в `beforeAll` и восстанавливал их в `afterAll`, без
защиты от прерывания прогона между этими двумя шагами. Также не была выполнена обязательная по
issue deliberate-break-проверка ("сломай намеренно → убедись, что падает → откати") — тот же паттерн
"тесты зелёные, но не доказано, что они ловят то, для чего писались", что уже наблюдался на #215/#282.

Корневая причина здесь — не в модели, а в дыре самой спеки (issue): решённый заранее Approach A не
учитывал, что `KnowledgeSourcesService.findActive()` возвращает вообще все активные строки без
фильтрации, так что "просто добавить фикстуру" не решало задачу без дополнительного вмешательства в
реальные строки. Агент, упёршись в это противоречие между двумя пунктами одной и той же issue (AC
"тест проходит" vs. Key Invariant "не трогай реальные данные"), не остановился с `BLOCKED`, а тихо
выбрал один пункт в ущерб другому.

Отдельно от причины — `runAgent()` до этого момента вызывал `claude -p` вообще без `--model`/
`--effort`, то есть каждый прогон молча наследовал текущий дефолт окружения, каким бы он ни был.
Это никогда не было причиной именно этой конкретной находки (доказать это по логам нельзя), но для
задачи, требующей проследить реальный путь данных через несколько файлов
(`findActive()` → `loadContent()` → containment check), а не просто отредактировать абзац в доке —
это ровно тот класс работы, где слабый эффорт/модель охотнее срезают путь. Исправлено:
`runAgent()` теперь всегда передаёт `--model sonnet --effort high` явно, а не полагается на
неизвестный ambient-дефолт.

Второе, отдельное исправление — в сам промпт (`buildPrompt()`) добавлено явное правило: если в
процессе реализации выясняется, что буквальное выполнение Acceptance Criteria и соблюдение всех
Key Invariants одной и той же issue физически несовместимы, это не повод тихо выбрать один пункт в
ущерб другому — это `BLOCKED: <в чём конфликт>`. До этой правки промпт запрещал гадать только на
случай неоднозначности формулировки *в начале* работы ("несколько разумных вариантов реализации") —
но не покрывал явно случай, когда противоречие обнаруживается уже в процессе, между двумя пунктами,
каждый из которых сам по себе однозначен.

Третье, самое существенное исправление — **`tsc`/`lint`/`test`/`test:e2e` все зелёные не доказывают,
что диф соответствует issue**, что #287 и продемонстрировал: все четыре проверки прошли, а issue
всё равно был нарушен по существу. Полагаться только на промпт-инструкции ("не забудь проверить X")
недостаточно — агент технически им следовал (запустил все команды), но не заметил содержательного
нарушения. Добавлен отдельный шаг между `DONE` и `commitChanges`/`push`/`createPr`:

1. **Гейт по типу изменённых файлов** (`hasCodeChanges()`/`DOC_ONLY_PATH_PATTERNS`) — если диф
   целиком состоит из `*.md`/`docs/**`/`project-management/**` (как #271/#272/#273), self-review
   пропускается полностью: у чистой доковой правки нет кодового Key Invariant, который можно было
   бы тихо нарушить, а второй полный прогон агента на неё — чистый расход без пользы. Что угодно,
   не подпадающее под эти паттерны, считается кодом и запускает review — с заведомым перекосом в
   сторону "лишний раз проверить", а не "лишний раз пропустить".
2. **Пост-DONE self-review** — **второй, независимый** `claude -p` (`buildReviewPrompt()`) с
   урезанными правами (`writeReviewerPermissions()`: только чтение и диагностика, никакого
   `Edit`/`Write` вообще — просто отсутствует в `allow`) и без общей памяти с агентом-реализатором,
   которому передаётся тело issue и `git diff HEAD`. Проверяет: (1) буквальное соблюдение Key
   Invariants, не только "по духу"; (2) выполнены ли Acceptance Criteria по существу; (3) риск
   false-negative у `toContain`/`toMatch`-assertions по большим текстам; (4) прогонялась ли логика
   на реальных файлах, если она их читает; (5) дублирование источника правды вместо устранения
   препятствия. Вердикт — `REVIEW: PASS` или `REVIEW: FAIL: <что и где>` (`parseReviewVerdict()`,
   тот же by-last-occurrence принцип, что и `parseVerdict()`).
3. **`FAIL` не значит сразу `BLOCKED`.** Находка сначала уходит на точечный фикс — ещё один,
   отдельный `claude -p` (`buildFixPrompt()`, права на Edit/Write возвращены) с рамкой "исправь
   именно то, что нашёл ревьюер, не переделывай всё" — после которого self-review прогоняется
   заново на обновлённом дифе. До `MAX_REVIEW_FIX_ATTEMPTS` (сейчас 2) таких циклов
   review→fix→review, прежде чем сдаться. Только если фиксер сам вернул `BLOCKED`/
   `BLOCKED-PROMPT-CHANGE`, или ревью продолжает находить проблему после исчерпания попыток, или
   вердикт ревью не распарсился — тогда это настоящий `BLOCKED`: коммит/push/PR не создаются, issue
   получает `ralph-blocked`, чтобы не быть тихо выбранной повторно. `PASS` (в том числе после N
   фикс-итераций) отмечается в теле PR как пройденный автоматический self-review — не как замена
   ручному ревью человеком, а как дополнительная линия защиты **до** того, как PR вообще появится.

Почему это в первую очередь prompt/model-задача, а не детерминированная проверка кодом: класс
ошибки, который реально произошёл на #287 (тихая деактивация реальных строк вместо честной
изоляции), — это семантическое несоответствие issue, а не паттерн, который ловится статическим
правилом/regex. Детерминированный код здесь используется только для механики (запуск, парсинг
вердикта, блокировка PR/коммита) — содержание самой проверки принципиально требует читающей модели,
как и `/code-review` для человека-разработчика.

## Файлы

- `run.js` — точка входа. `node .claude/ralph/run.js [--max-iterations N]`.
- `core.js` — вся логика: выбор issue (`classify`), клонирование, промпт, парсинг вердикта,
  state machine одной итерации (`runIssue`).
- `config.example.json` — шаблон. Скопируй в `config.json` (гитигнорится) и отредактируй список
  `issues` под актуальную задачу.

Рантайм-файлы (все гитигнорены, не коммитятся):
- `.claude/ralph/config.json` — реальный список задач + `maxIterations`/`maxTurns`/`branchPrefix`.
- `.claude/ralph/state.json` — снимок последнего прогона (диагностика, не источник правды —
  источник правды всегда GitHub).
- `.claude/ralph/run.lock` — PID активного прогона; `run.js` отказывается стартовать второй
  экземпляр поверх работающего.
- `.ralph-runs/issue-<n>/` — клон репозитория под конкретный issue. Удаляется при успехе
  (`DONE` → PR создан) и при `BLOCKED`; **оставляется** при любом сбое (`*_failed`) — путь
  печатается в лог для разбора.

## Что унаследовано без изменений от первой версии (проверено, работает)

- `dependsOn` + приоритет по порядку в списке (`classify()`).
- Stacked PR для зависимых issue: зависимый ответвляется от ветки ещё не смёрженной зависимости,
  не от `main`. Репозиторий настроен на `deleteBranchOnMerge: true`, чтобы GitHub сам ретаргетил
  такой PR на `main`, когда зависимость мёрджится.
- Лейбл `ralph-needs-prompt-change` — issue, требующий менять `apps/api/prisma/prompts`/
  `apps/api/knowledge-sources`, не реализуется автоматически (агент отвечает
  `BLOCKED-PROMPT-CHANGE`, контроллер сам ставит лейбл и комментарий), и транзитивно блокирует
  всё, что от него зависит.
- Мёрдж PR всегда делает человек — контроллер только создаёт PR (`Closes #<n>`), никогда не
  мёрджит.
- `maxIterations`/`maxTurns` — предохранители (сколько issue вообще обработать за прогон / сколько
  ходов агенту на одну итерацию).

## Запуск

```bash
cp .claude/ralph/config.example.json .claude/ralph/config.json
# отредактируй issues под актуальную задачу
node .claude/ralph/run.js --max-iterations 1
```

`--max-iterations` на командной строке переопределяет `maxIterations` из конфига — удобно для
разового проверочного прогона без правки файла.
