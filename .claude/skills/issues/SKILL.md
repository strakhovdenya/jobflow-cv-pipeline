# Issues Generator — JobFlow CV Pipeline

Прочитай план из файла: $ARGUMENTS

Если `$ARGUMENTS` не указан — спроси у пользователя путь к файлу плана
(`project-management/plan/PLAN-<kebab-name>.md`), не выдумывай его.
Если файл не найден — сообщи об этом и останови выполнение.

Для каждой фазы плана создай milestone, а для каждой задачи внутри фазы — Issue в GitHub,
используя `gh` CLI. Каждый созданный issue также добавляется в GitHub Project репозитория
(`gh project item-add`) — единая доска для всех эпиков, не только текущего.

Эти GitHub issues — рабочий трекер эпика для координации по фазам, они **не подменяют**
`docs/07_task_backlog.md` (нумерованные `TASK-XXX` записи) и не запускают реализацию сами по
себе — старт любой фазы всё равно идёт через обычный Plan-first / Branch-first /
Task-file-first protocol из корневого `CLAUDE.md`.

## Перед созданием — проект и проверка на дубли

- Найди GitHub Project репозитория: `gh project list --owner :owner`. В этом репозитории уже
  создан один Project — `JobFlow CV Pipeline` (`gh project list --owner strakhovdenya`, number
  `1`, https://github.com/users/strakhovdenya/projects/1), привязанный к репозиторию через
  `gh project link`. Используй его — не создавай новый Project без явного запроса пользователя.
  Если `gh project list` для владельца репозитория вернул пустой список (Project отсутствует или
  ещё не привязан) — сообщи об этом пользователю и спроси, создать ли новый (`gh project create
  --owner :owner --title "..."` + `gh project link <number> --owner :owner --repo :owner/:repo`),
  прежде чем продолжать.
- `gh` не даёт создавать issues автоматически идемпотентно — при повторном запуске скила на том
  же плане нужно самому не создавать дубли:
  - `gh api repos/:owner/:repo/milestones --paginate` — проверь, нет ли уже milestone с таким же
    заголовком (`Фаза N: название`) прежде чем создавать новый.
  - `gh issue list --search "in:title <текст задачи>" --state all` — проверь, нет ли уже issue с
    таким же заголовком (в рамках соответствующего milestone) прежде чем создавать новый. Если
    issue уже существует, но ещё не добавлен в Project — всё равно выполни для него шаг
    добавления в Project (шаг 4), не пропускай его вместе с созданием issue.

Если что-то уже существует — пропусти создание и сообщи об этом в итоговой сводке, не создавай
дубль и не спрашивай пользователя по каждому отдельному совпадению.

## Порядок действий

1. Прочитай файл плана целиком (все секции `### Фаза N: ...`).
2. Для каждой фазы создай milestone:
   ```
   gh api repos/:owner/:repo/milestones -f title="Фаза N: название" -f description="Цель фазы (из '**Цель:**' плана)"
   ```
3. Для каждой задачи (строка `- [ ] ...` под `**Задачи:**`) внутри фазы создай Issue, привязанный
   к её milestone:
   ```
   gh issue create --title "..." --body "..." --label "..." --milestone "Фаза N: название"
   ```
4. Добавь только что созданный (или найденный существующий) issue в GitHub Project (номер найден
   на шаге "Перед созданием"):
   ```
   gh project item-add <project-number> --owner :owner --url <issue-url>
   ```
   (`gh issue create` выводит URL созданного issue — используй его напрямую, не собирай вручную.)
5. После создания всех issues выведи пользователю сводку: сколько milestones/issues создано,
   сколько добавлено в Project, сколько пропущено как дубли, ссылки на созданные issues
   (`gh issue create` возвращает URL).

## Формат Issue

**Title**: текст задачи из плана дословно, без квадратных скобок `- [ ]`.

**Body**:
```markdown
Часть фазы **Фаза N: название** плана `<путь к файлу плана>`.

**Затрагивает:** {значение "**Затрагивает:**" фазы из плана}

{если у фазы есть "**Когда готова:**" в плане — включи её сюда как Definition of Done для этой
конкретной задачи, дословно}

---
Сгенерировано из `<путь к файлу плана>` (PRD: `<путь к PRD из шапки плана, если указан>`).
```

**Label**: выбирай только из уже существующих в репозитории лейблов (`gh label list`) — не
создавай новые лейблы без явного запроса пользователя. По умолчанию: `enhancement` для
задач реализации, `documentation` для задач, которые правят только `docs/`/`project-management/`
файлы без кода.

**Milestone**: заголовок фазы (`Фаза N: название`), созданный на шаге 2.

## Правила

- Не меняй и не удаляй сам файл плана — скил только читает его.
- Не создавай issues для фаз/задач, которых нет в файле плана — не придумывай новый скоуп.
- Один milestone на фазу, ровно так, как фазы разбиты в плане — не объединяй и не дроби их иначе.
- Если у задачи в плане нет отдельного пояснения кроме самого текста — Body может быть короче
  (без пустых секций), но ссылка на файл плана в конце обязательна всегда — это единственная
  прослеживаемость обратно к PRD.
- Не запускай `gh pr create`, не переключай ветки и не коммить ничего — это только issue-трекер,
  реализация кода в этот скил не входит.
