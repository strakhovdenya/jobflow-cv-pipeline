# Plan Generator — JobFlow CV Pipeline

Прочитай PRD: `$ARGUMENTS` — если это путь к файлу, читай напрямую; если это kebab-case имя
фичи, ищи в `project-management/prd/PRD-$ARGUMENTS.md`.

Если PRD-файл не найден — сообщи об этом и останови выполнение, не выдумывай содержимое PRD.

Создай план реализации и сохрани в файле `project-management/plan/PLAN-<kebab-name>.md` (то же
kebab-case имя фичи, что и у PRD-файла). Если нет папки `project-management/plan/` — создай её.

Этот план — черновая раскладка PRD на фазы, а не замена `project-management/CURRENT_TASK.md` и
не запись в `docs/07_task_backlog.md`. Финальные `TASK-XXX` (номер, точный `## Files likely
affected`, `## Acceptance criteria` в формате backlog) всё равно оформляются вручную по `##
2. Task Format` из `docs/07_task_backlog.md`, а старт реализации любой фазы всё равно идёт через
обычный Plan-first / Branch-first / Task-file-first protocol из корневого `CLAUDE.md` — этот
скилл их не подменяет и не ускоряет.

## Структура плана

```markdown
# Plan: {название фичи}

**PRD:** `project-management/prd/PRD-<kebab-name>.md`
**Дата:** {текущая дата}

## Фазы реализации

### Фаза 1: {название}
**Цель:** Что даёт эта фаза
**Затрагивает:** apps/api / apps/web / PostgreSQL (Prisma) / файловые артефакты (STORAGE_ROOT)
**Задачи:**
- [ ] Задача 1
- [ ] Задача 2

**Когда готова:** закрывает пункт(ы) `## Критерии готовности` PRD: "{дословная или близкая
цитата конкретного AC-пункта}". Не пиши расплывчатый критерий вроде "работает нормально" —
только то, что можно проверить и что явно ведёт к конкретному AC из PRD.

### Фаза 2: {название}
...

{Если фазы вместе затрагивают и apps/api, и apps/web (или их больше двух, и каждая — независимо
тестируемый шаг) — добавь после списка фаз одну строку: "Рекомендуется epic base branch:
`task/TASK-XXX-<epic-short-name>-base` (ADR-025), т.к. ...". Не создавай ветку и не выбирай номер
задачи — это отдельный ручной шаг, как в /prd.}
```

## Правила разбивки на фазы

- Каждая фаза должна давать рабочий результат.
- Фазы независимы, можно остановиться после любой.
- Первая фаза — как минимальный рабочий путь (Tracer Bullet).
- Не больше пяти задач в одной фазе.
- `apps/api` и `apps/web` одной фичи — разные фазы (не смешивай backend- и frontend-задачи в
  одной фазе).

## Самопроверка перед сохранением файла

Перед тем как записать файл плана — перечитай черновик и сверь с PRD:

- Каждая фаза закрывает конкретный пункт `## Критерии готовности` PRD — перепроверь, что ссылка
  верная (открой PRD и найди пункт дословно, не по памяти).
- Все AC из PRD в сумме покрыты какой-то фазой — ни один не потерян и не задвоен без причины.
- Любая ссылка на ADR/раздел `CLAUDE.md`/номер строки в другом файле — открыта и подтверждена, не
  оценена на глаз.

## Правила

- Читай PRD внимательно — план должен покрывать все пункты `## Критерии готовности` из PRD.
- Не добавляй задачи, которых нет в PRD (ни в `## В скоупе`, ни в `## Предполагаемое дробление на
  подзадачи`, если PRD его содержит) — этот скилл раскладывает PRD на фазы, не придумывает новый
  скоуп.
- Если PRD неполный или в нём остались открытые вопросы (`## Открытые вопросы` не пуст) — задай
  вопрос пользователю перед созданием плана, а не строй план поверх неопределённости.
- Этот скилл не создаёт и не редактирует код, ветки, коммиты, `CURRENT_TASK.md` или
  `docs/07_task_backlog.md` — только сам файл плана.
