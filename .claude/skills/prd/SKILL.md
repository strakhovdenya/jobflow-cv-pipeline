# PRD генератор — JobFlow CV Pipeline

Создай PRD (Product Requirements Document) для следующей фичи: $ARGUMENTS

Сохрани результат в файл `project-management/prd/PRD-$ARGUMENTS.md` (переведи название фичи на
английский и kebab-case, например `PRD-cover-letter-export.md`).

Если нет папки `project-management/prd/` — создай её.

Этот PRD — не GitHub Issue. Это документ уровня "что и зачем", который предшествует им: после
согласования PRD с пользователем следующий шаг — `.claude/skills/plan` (разбить PRD на фазы), затем
`.claude/skills/issues` (завести фазы/задачи как milestones/issues на GitHub — источник правды по
ADR-030). Для фичи, умещающейся в один PR (не эпик — см. "Режим эпика" ниже), задача заводится
как один GitHub Issue напрямую, тем же форматом (`.claude/skills/issues/SKILL.md`'s "Формат
Issue"), без промежуточного plan-файла. Не подменяй эти шаги — PRD не должен содержать детальный
implementation-план (это задача самого Issue, per `## GitHub Issue Authoring Rules` корневого
`CLAUDE.md`, на этапе Issue-first protocol).

## Перед тем как писать

Прочитай (кратко, только нужные секции — не файлы целиком):

- Корневой `CLAUDE.md` — разделы `## Repository Layout`, `## High-Level Architecture`,
  `## Architecture Rules`, `## Prompt Pipeline Rules`, `## Anti-Overclaiming Rules`.
- `project-management/DECISIONS.md` — проверь, не противоречит ли фича принятому ADR и не
  относится ли она к теме, уже закрытой решением (если противоречит — не игнорируй молча, вынеси
  в `## Открытые вопросы` секцию ниже).
- `docs/07_task_backlog.md` §1 "Key scope rules preserved in this backlog" — чтобы не предлагать
  фичу, которая тайно двигает P1/P2 в MVP scope.
- Открытые issues/milestones на GitHub Project `JobFlow CV Pipeline`
  (https://github.com/users/strakhovdenya/projects/1, `gh issue list`) — не дублирует ли фича то,
  что уже в работе или уже сделано.
- **Если фича уже описана как эпик/фаза** — найди её по правилам CLAUDE.md's `## Finding Epics
  and Phases` (`docs/05_epics.md` → `docs/06_roadmap.md` → выделенный методологический файл, если
  есть, например `docs/10_calibration_and_parity.md` для EPIC-24). Прочитай **весь** раздел этого
  эпика целиком (Goal/Business Value/Scope/Out of Scope/Dependencies/Acceptance Criteria), а не
  только Goal — это обязательный источник, а не справочный контекст: разделы "В скоупе"/"Не в
  скоупе"/"Критерии готовности" итогового PRD должны быть построены как явная сверка с этим
  списком пункт за пунктом, а не пересказом по памяти. Не доверяй
  `project-management/EPIC_PROGRESS.md` как источнику статуса (см. тот же раздел CLAUDE.md).

## Структура документа

```markdown
# PRD: {название фичи}

**Дата**: {текущая дата}
**Статус**: Draft
**Затрагиваемое приложение**: apps/api | apps/web | оба (см. CLAUDE.md Repository Layout)
**Связанный issue/backlog-пункт**: {ссылка на существующий GitHub issue, если уже есть, либо
"новая фича — ещё не заведена как issue"}

## Цель

Одно-два предложения: что и зачем это нужно пользователю проекта (соискателю, использующему
пайплайн для генерации таргетированных CV).

## Контекст и согласованность с проектом

- Какой слой пайплайна/модуль это затрагивает (см. Module Map в apps/api/CLAUDE.md или
  структуру apps/web/CLAUDE.md).
- Затрагивает ли это canonical-артефакты пайплайна (00_vacancy_source, 01_vacancy_analysis,
  01_skip_reason, 02_targeted_cv_content, 03_pre_pdf_check, 04_cv_export, 05_final_check,
  cover_letter) — если да, перечисли какие.
- Связанные ADR из DECISIONS.md (номер + одна строка сути), если фича продолжает или пересекается
  с уже принятым решением.

## Зависимости

Что должно уже быть DONE, прежде чем эта фича имеет смысл технически (не просто "было бы неплохо
сделать сначала", а реальная предпосылка). Если фича соответствует эпику из `docs/05_epics.md` —
скопируй сюда его `## Dependencies` список пункт за пунктом (номер эпика/фазы + текущий статус:
DONE/в работе/не начато), не пересказывай своими словами и не сокращай список. Если какая-то
зависимость ещё не DONE — это не повод молчать, вынеси конфликт в `## Открытые вопросы`. Если
фича не завязана на эпик и явных технических предпосылок нет — напиши "Явных зависимостей не
найдено".

## Пользовательские сценарии

- Пользователь {действие} -> {результат}

## В скоупе

Конкретный список того, что входит в эту итерацию фичи.

## Не в скоупе

Явно то, что не делаем сейчас (например: "cover letter остаётся Phase 2 — см. ADR-010", если
применимо). Если фича граничит с P1/P2-функциональностью, явно скажи, что P1/P2-часть остаётся
за скобками. Если фича соответствует эпику из `docs/05_epics.md` — каждый пункт его `## Out of
Scope` должен быть представлен здесь (своими словами нормально, пропускать пункты — нет).

## Влияние на state machine (если применимо)

Заполняй только если фича меняет `ApplicationWorkspace.status`, `reviewState`, `currentDecision`
или другой enum-переход. Формат — таблица, как того требует CLAUDE.md `## GitHub Issue Authoring
Rules`:

| Action | Precondition | Field A after | Field B after | Status after |
|---|---|---|---|---|

Если не применимо — напиши "Не применимо: фича не меняет состояние workspace."

## Влияние на модель данных

Новые/изменённые Prisma-модели или поля, ожидаемая необходимость миграции. Помни: PostgreSQL
хранит метаданные, файловая система — физические артефакты (ADR-002) — не предлагай хранить
большие сгенерированные тексты/PDF только в БД.

## API-поверхность

Новые/изменённые HTTP endpoints. Каждый новый endpoint в итоге потребует
`@ApiOperation({ summary: '...' })`, каждое новое/изменённое поле DTO — `@ApiProperty()` /
`@ApiPropertyOptional()` (ADR-019) — упомяни это как требование, не как факт (реализация будет в
самой задаче, не в PRD).

## Ключевые инварианты

Неочевидные правила, которые ограничивают реализацию этой фичи. Проверяй в первую очередь:

- Anti-overclaiming rules (CLAUDE.md `## Anti-Overclaiming Rules`) — если фича касается
  генерации/показа CV-контента.
- Prompt Pipeline Rules — если фича касается AI-шагов (человеческий review-гейт после Prompt 1,
  Prompt 2 только после approval, Prompt 3 — mandatory-but-skippable gate per ADR-026).
- Module boundary rules (ADR-017) — если добавляется новый NestJS-модуль/сервис.
- Filesystem root (`STORAGE_ROOT`) — код никогда не должен писать за его пределами.

## Технические ограничения

Известные ограничения, которые нужно учесть (например: AI provider abstraction — не привязываться
к конкретному SDK; unit-тесты не должны зависеть от реального AI provider — CLAUDE.md `## AI
Provider Rules` / `## Testing Rules`).

## Критерии готовности (Acceptance Criteria)

Проверяемые, конкретные пункты — этот список должен быть готов к прямому копированию в будущий
GitHub Issue `## Acceptance Criteria`.

- [ ] Критерий 1
- [ ] Критерий 2

Если фича соответствует эпику из `docs/05_epics.md` — каждый пункт его `## Acceptance Criteria`
должен быть представлен здесь. Любой критерий, которого нет в исходном эпике, но который ты
добавляешь сам (например, по прямому требованию CLAUDE.md, не упомянутому явно в эпике) —
помечай инлайн-пометкой вроде `*(добавлено этим PRD, не из docs/05_epics.md — обоснование: ...)*`,
чтобы при чтении было видно, что взято из источника, а что добавлено сверху.

## Test Requirement (набросок)

Какие типы тестов понадобятся (unit / e2e / manual UI verification per apps/web policy) — не
пиши тест-план в деталях, это решается в самом GitHub Issue.

## Открытые вопросы

Всё, что нужно уточнить у пользователя, прежде чем это можно будет оформить как задачу в backlog:
неясности в скоупе, потенциальные конфликты с существующим ADR, недостающие мокапы/данные.

## Документация, которую потребуется обновить

Если фича архитектурная (новый/удалённый/переименованный модуль, изменённый data flow, новый
HTTP endpoint, изменённый state machine, новое ADR-решение) — перечисли, что потребует обновления
по правилу CLAUDE.md `## Documentation Rules`: корневой `CLAUDE.md`, `apps/api/CLAUDE.md` /
`apps/web/CLAUDE.md`, `DECISIONS.md`, соответствующий `docs/*.md`.

## Предполагаемое дробление на подзадачи (только если это эпик)

{раздел появляется, только если см. "Режим эпика" ниже — иначе не включай его в файл вообще}

Черновой, кандидатный список тем для будущих задач/issues — не сами задачи, это разбивает
`.claude/skills/plan` на фазы, а `.claude/skills/issues` заводит как GitHub issues. Каждый
пункт — тема одной задачи, не сама задача:

1. {короткое название темы} — {одно предложение, что она покрывает и какой Acceptance Criteria
   из PRD выше в неё попадает}
2. ...

Если темы естественно зависят друг от друга по порядку (например, схема данных → backend endpoint
→ frontend) — перечисли их в этом порядке; это подсказка для последовательности, не жёсткое
требование.

Если эпик достаточно большой, чтобы потребовать `-base` интеграционную ветку (ADR-025) — явно
скажи это здесь одной строкой ("Рекомендуется epic base branch:
`task/ISSUE-<tracking-issue-n>-<epic-short-name>-base`, т.к. ..."), но не создавай ветку и не
выбирай номер — это отдельный ручной шаг.
```

## Режим эпика

Если фича по масштабу — это эпик (несколько логически завершённых кусков работы, которые не
имеет смысла закрывать одним PR — например, затрагивает и backend, и frontend, или состоит из
нескольких независимо тестируемых шагов), включи в документ секцию "## Предполагаемое дробление
на подзадачи" из шаблона выше. Если фича умещается в один PR — не включай эту секцию вообще
(не оставляй пустой заголовок).

Не уверен, эпик это или нет — спроси пользователя явно, а не угадывай.

Этот черновой список — материал для `.claude/skills/plan` (разбивка на фазы), а не готовые GitHub
issues. Финальные issues (с точным `## Затрагивает`, `## Acceptance Criteria` в формате
`.claude/skills/issues/SKILL.md`) заводятся тем скиллом из плана; этот скилл их не создаёт.

## Самопроверка перед сохранением файла

Перед тем как записать PRD-файл, перечитай собственный черновик и сверь его с источниками —
не полагайся на память о том, что ты только что прочитал:

- **Каждое утверждение о механике проекта** (инварианты, поведение сервиса, поведение миграций/
  seed-скриптов и т.п.) — перепроверь дословно по файлу-источнику, а не по пересказу. Особенно
  осторожно с формулировками из root `CLAUDE.md`'s `## High-Level Architecture` → `Key
  Invariants` — они пишутся точно намеренно (например "one active version per type at a time"),
  и перефразирование легко превращает их в противоположное по смыслу утверждение.
- **Каждая ссылка на диапазон строк** (`docs/05_epics.md`, `строки X–Y`) — открой файл и
  подтверди диапазон, не оценивай на глаз.
- **Если фича соответствует эпику** — построчно сверь итоговые `## В скоупе`, `## Не в скоупе`,
  `## Зависимости`, `## Критерии готовности` с оригинальными списками эпика: каждый пункт источника
  представлен, и любой пункт, добавленный сверх источника, явно помечен (см. правило выше).
- Если в процессе самопроверки нашлась неточность — исправь её до сохранения файла, не сохраняй
  черновик с известной ошибкой в расчёте на последующую правку.

## Правила

- Пиши конкретно — никакой воды.
- Критерии готовности должны быть проверяемыми (checkbox-формат, без расплывчатых формулировок
  типа "работает хорошо").
- Не описывай, КАК реализовывать (код, конкретные файлы, шаги) — только ЧТО и ЗАЧЕМ. HOW —
  предмет самого GitHub Issue, который пишется отдельно на этапе Issue-first protocol, уже на
  ветке задачи.
- Если описание фичи короткое или неоднозначное — задавай уточняющие вопросы до полного понимания,
  прежде чем создавать файл. В частности уточни: apps/api или apps/web (или оба), это MVP-scope
  или явно P1/P2, есть ли готовый мокап/референс.
- Явно проверяй фичу на конфликт с уже принятыми ADR в `DECISIONS.md` и с `docs/07_task_backlog.md`
  §1 scope rules. Если конфликт есть — не замалчивай и не переписывай решение сам, вынеси это в
  `## Открытые вопросы` и прямо спроси пользователя.
- Не переноси P1/P2-функциональность в MVP-скоуп без явного запроса пользователя (CLAUDE.md
  `## Documentation Rules`).
- Этот скилл не создаёт и не редактирует код, ветки, коммиты — только сам PRD-файл.
