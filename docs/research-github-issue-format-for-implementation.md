# Research: What a GitHub Issue Needs to Be Actually Implementable

**Дата**: 2026-08-19
**Контекст**: issues, созданные скилом `.claude/skills/issues/SKILL.md` из
`project-management/plan/PLAN-*.md`, оказались слишком тонкими для реальной разработки —
запрос на этот ресерч.

## 1. Проблема

Текущий формат issue (см. `.claude/skills/issues/SKILL.md` до этого изменения):

```markdown
Часть фазы **Фаза N: название** плана `<путь к плану>`.

**Затрагивает:** {из плана}

**Когда готова (фаза):** {AC-цитата из плана}

---
Сгенерировано из ...
```

Этого достаточно как трекер/чек-лист, но недостаточно чтобы **сесть и писать код** — нет ответа
на: какие именно файлы менять, что прочитать перед реализацией, какие неочевидные правила/инварианты
нельзя нарушить, что конкретно проверяется тестами, когда задача реально "done", и от чего она
зависит.

## 2. Что уже есть в проекте как рабочий эталон

В этом же репозитории уже существует формат, который решает ровно эту проблему —
`TASK-XXX` записи в `docs/07_task_backlog.md`. Найдено при исследовании прошлых закрытых задач
(EPIC-23/Phase 16, TASK-094–101): каждая запись содержит **Context, Files likely affected, Docs to
Read (с конкретными секциями/номерами строк), Key Invariants, Acceptance Criteria, Test
Requirement, Done Definition (явный список команд: `tsc --noEmit`, `lint`, `test`, `test:e2e`, CI
green), Dependencies (ссылки на другие TASK-XXX)**. Это не теория — это формат, которым в проекте
реально стабильно закрывают задачи (см. `project-management/completed-tasks/`).

Внешний ресерч (ниже) в основном **подтверждает уже используемый в проекте формат**, а не вводит
что-то принципиально новое — задача этого ресерча в том, чтобы перенести его поля в issue-формат,
который сейчас их не содержит.

## 3. Внешние best practices

### 3.1 Что делает issue actionable (GitHub-специфично)

- Issue должен содержать: чёткий заголовок, контекст/проблему, **конкретные шаги/файлы**, и
  **pass/fail критерии** ("all tests pass", конкретный порог) — не расплывчатое "работает
  нормально".
- **Guardrails/технические ограничения** явно прописаны в issue (что нельзя трогать, какие
  зависимости не добавлять) — предотвращает лишнюю работу и ре-дизайн в процессе ревью.
- Один issue должен быть самодостаточным: "one URL captures the problem statement, reproduction
  steps, and definition of done" — человек, зашедший в задачу впервые, должен разобраться за
  минуты, не читая соседние документы с нуля.
([Zenhub — GitHub Best Practices](https://www.zenhub.com/blog-posts/best-practices-for-github-issues),
[GitHub Blog](https://github.blog/developer-skills/github/how-to-create-issues-and-pull-requests-in-record-time-on-github/),
[GitHub Community Discussion #147722](https://github.com/orgs/community/discussions/147722))

### 3.2 INVEST + Definition of Ready / Definition of Done (Agile)

- **INVEST**: Independent, Negotiable, Valuable, Estimable, Small, Testable — тикет должен быть
  оцениваемым и тестируемым сам по себе, без скрытых зависимостей, о которых не сказано явно.
- **Definition of Ready** (минимум перед тем как брать в работу): понятная формулировка задачи,
  чёткие Acceptance Criteria, согласованная оценка объёма.
- **Definition of Done** ≠ Acceptance Criteria: DoD — это когда тикет физически можно закрыть
  (тесты прошли, задеплоено/смержено), AC — что именно должно быть верно в результате.
([Atlassian — Definition of Ready](https://www.atlassian.com/agile/project-management/definition-of-ready),
[Boost — INVEST criteria](https://www.boost.co.nz/blog/2021/10/invest-criteria/))

## 4. Итоговый рекомендуемый формат Issue Body

Синтез внутреннего эталона (TASK-XXX) + внешних практик (GitHub actionable issue + INVEST/DoR/DoD),
адаптированный под то, что уже есть в PRD/плане (не придумывать данные — переносить то, что уже
написано в PRD/плане в структурированном виде):

```markdown
## Контекст
{Цель фазы из плана + короткая связка с PRD/эпиком — почему это нужно}

## Затрагивает
{конкретные файлы/модули из "Затрагивает" фазы плана — по возможности точные пути, не только
apps/api целиком}

## Docs to Read
{конкретные секции/файлы, которые нужно прочитать перед реализацией — из "Docs to Read" PRD/плана,
ADR-ссылок, docs/10_calibration_and_parity.md секций и т.п. Не весь файл — секция/строки, если
известны}

## Key Invariants
{неочевидные правила, которые нельзя нарушить — из раздела PRD "Ключевые инварианты", применимые к
этой конкретной задаче}

## Acceptance Criteria
{чек-лист, дословно или близко к AC из PRD/плана, которые закрывает эта задача}

## Test Requirement
{что именно проверяется: юнит-тесты (если применимо), или "ручная верификация, запись в
TEST_LOG.md" — из PRD "Test Requirement"}

## Definition of Done
- [ ] Acceptance Criteria выше выполнены
- [ ] {явные команды из CLAUDE.md/apps/api CLAUDE.md, если задача код-центричная: `tsc --noEmit`,
      `lint`, `test`}
- [ ] Затронутые доки обновлены (если задача архитектурная — см. корневой CLAUDE.md
      "Documentation Rules")

## Dependencies
{ссылки на другие issues этого же эпика, которые должны быть закрыты раньше — "Depends on #NNN" /
"Blocks #NNN"}

---
Сгенерировано из `<путь к плану>` (PRD: `<путь к PRD>`).
```

## 5. Что сознательно не переносится

- **Оценка трудозатрат (story points/время)** — INVEST требует "Estimable", но в этом проекте нет
  практики оценки в очках/часах (весь процесс — Plan-first подтверждение объёма в чате, не формальная
  оценка) — не вводим то, чего нет в проектной методологии.
- **Guardrails как отдельная секция** — в этом проекте эта роль уже выполняется "Key Invariants" +
  "Не в скоупе" разделом PRD; не дублируем отдельным полем.
- **Скриншоты/GIF** — неприменимо, все задачи этого эпика не UI-related (apps/api + документация).
