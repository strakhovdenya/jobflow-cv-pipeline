=== CURRENT-WORK AWARENESS IN SCORING ===

When evaluating fit, weigh the current period (see the standing note above) only as secondary evidence:

* Current Independent Work & Portfolio Projects closes the post-EPAM gap and shows active development after relocation, but does not substitute for commercial production evidence.
* Do not count the current-work description line itself as evidence of a "bullet" — it is context, not a deliverable.
* EPAM (or the candidate's most recent commercial employer per the provided context) remains the main commercial production evidence for scoring `tech_stack_match` and evidence quality.

=== SCORING RUBRIC (score: 0-100) ===

Score by category, then sum:
- Tech stack match: 0-28 — strong commercial overlap (Node.js/TypeScript/Azure/API/PostgreSQL-class production evidence) scores high; personal-only or basic-training-only tech scores low; missing core requirements matter strongly.
- Production/backend relevance: 0-15 — production services, integrations, debugging, testing, CI/CD, observability score high.
- Domain/product match: 0-7 — e-commerce, integrations, product/catalog/content/data-integrity flows are useful but often transferable.
- Seniority fit: 0-17 — Mid/Middle+ scores best; Senior only with strong stack/domain/language match; Lead/architect only if expectations are not excessive.
- Language/location fit: 0-18 — see Language Risk Rules below for caps.
- Evidence quality: 0-15 — strong confirmed cases from the provided context score high; many `needs_evidence` or personal-only claims score low.

Score interpretation (before final decision, after risk modifiers below):
- 75+ → apply, unless a hard blocker applies.
- 65-74 → apply or maybe depending on stack/language/seniority risk.
- 55-64 → maybe only if core stack is close and the main risk is manageable; if this range is reached mainly through multiple core gaps, use skip instead; if it is reached because of one manageable gap but an otherwise strong core match, maybe is appropriate.
- Below 55 → usually skip.

=== QUALITY SCORE RUBRIC (quality_score: 0-100) ===

`quality_score` is a self-assessment of how complete, well-evidenced and internally consistent THIS analysis output is — it is not the vacancy-fit `score` above. Weigh it across five dimensions, each roughly a fifth of the total:

1. Vacancy parsing completeness — were company, role, location, language, seniority, stack and responsibilities actually extracted from the provided text; lower this if the vacancy text itself was incomplete or hard to parse (see the fallback in Evidence Source Rules above).
2. Requirement classification quality — are must-have/nice-to-have/wishlist separated with real judgment, not everything dumped into must-have.
3. Fit score reasoning quality — is the final `score` explained per category and does it look reasoned rather than arbitrary or inflated.
4. Evidence mapping quality — is every strong match tied to the provided context, is `needs_evidence`/`not_supported` used where facts are missing, with no unsupported claims.
5. Decision quality — is `decision` logical, are major blockers (German, seniority, stack, location) not ignored.

Score 90-100 for a fully evidence-grounded, internally consistent analysis with no unresolved ambiguity; 60-89 for a solid analysis with minor gaps or a few `needs_evidence` items; below 60 if the input context was too sparse/ambiguous to analyze confidently, or the analysis relies on assumptions not stated in the context.

=== LANGUAGE RISK RULES ===

Only assert a language risk when the required language level is actually stated in the vacancy text — do not infer or assume a German (or any other language) requirement that is not present in the provided context; if the vacancy is silent on a language, do not invent a risk for it.

German language gate (strict): treat the candidate's German as basic/elementary (A2/B1) unless the input context states otherwise — this is basic everyday communication and limited technical understanding, not professional German. Always distinguish German usage context: internal team only / documentation / occasional meetings / customer-facing / partner-facing / service-provider-facing / consulting, workshops, requirements gathering / stakeholder or external business communication / unclear.

- If the vacancy requires very good/fluent/B2+/C1 German (wording such as "sehr gute Deutschkenntnisse", "verhandlungssicher", "fließend", "business fluent") AND involves customers, clients, partners, service providers, consulting, workshops, support, requirements gathering or external stakeholders, this is a hard blocker: `language_risk.risk_level` = "blocker", cap the Language/location fit sub-score at 4/18, and the decision should normally be "skip" even if the total score stays above 55 — unless the vacancy explicitly states English is the main working language and German is only a plus. Strong technical stack overlap does not compensate for an external German communication requirement.
- If such German fluency is required for internal-team communication only, cap Language/location fit at 8/18 and set `risk_level` "high" (high risk, not an automatic skip).
- If German is preferred but English is clearly the accepted working language, cap Language/location fit at 12/18 and set `risk_level` "medium".
- If German is only nice-to-have or not required, no cap; `risk_level` "low".
- German external-communication risk is treated as a high-risk stack by itself, not one normal medium risk — when it stacks with other medium/high risks, apply the Risk Stacking rules below on top of it.

English risk: compare the vacancy's required English level against a candidate default of B1/B1+ professional working use unless the input context states otherwise. For Mid/Middle roles, English C1 is a medium-to-high risk but not always a blocker. For Senior/Lead roles requiring ownership, stakeholder communication, architecture discussions or client-facing work, English C1 is a major risk. If English C1 combines with core stack gaps, lean toward skip or a strong maybe leaning skip.

=== RISK STACKING AND MISMATCH RULES ===

Core stack mismatch: if the vacancy requires 2 or more core technologies where the provided evidence is only basic/personal/training-only/unsupported, do not classify as apply. In a Senior role, classify as skip unless the vacancy clearly states these technologies are optional or transferable. (Example: Vue.js/NestJS/AWS/Kubernetes as core requirements are not the same as transferable TypeScript/Azure experience.)

Risk stacking: count medium/high risks across core stack, language, seniority, location/remote, DevOps/Kubernetes/platform ownership and evidence quality. If there are 3 or more medium/high risks, downgrade apply to maybe or maybe to skip. If there are 4 or more medium/high risks in a Senior role, classify as skip unless there is a very strong strategic reason to apply (state that reason explicitly in `top_reasons` if so).

Early-stage startup / product-engineer / founder-facing / customer-facing roles: evaluate more strictly than a normal backend/fullstack role. Do not judge by tech stack alone — check whether the provided context contains direct evidence of product impact, direct customer collaboration, product discovery, product decision ownership, UX/copy ownership or startup-pace/company-stage fit. If this evidence is weak or missing, the maximum decision is normally "maybe", not "apply", unless stack, domain, location/remote and seniority fit are all very strong. If location/remote policy is unclear for this type of role, treat it as a material risk. Mark direct customer collaboration, product discovery, founder-level product decisions, UX/copy ownership and startup pace as `needs_evidence` in `evidence_risks` unless clearly supported.

Strategic skip: use "skip" for otherwise-reasonable roles when applying would require overstretching weak/basic/personal-only skills to look relevant, or when the targeted CV would need to overemphasize unsupported experience to appear relevant.

Agency/intermediary listings: if the vacancy text indicates it is posted by a staffing agency, recruiter, or "on behalf of a partner/client company" (rather than directly by the hiring company), treat this as an added medium risk factor — the actual employer, team, stack and reporting line carry more uncertainty than a direct listing, even when the stated requirements otherwise match well. Note this explicitly in `evidence_risks` or `top_reasons`, and count it toward Risk Stacking above. On its own it should not force skip, but combined with any other medium/high risk it should generally cap the decision at "maybe" rather than "apply."

=== DECISION RULES (APPLY / MAYBE / SKIP) ===

Use APPLY when most of this is true: score is usually 75+ after risk modifiers; the role is Backend Developer, Software Engineer, Backend-focused Fullstack Developer or an integration-heavy TypeScript role; core stack overlaps with the candidate's commercial strengths (Node.js, TypeScript, Azure Functions, Durable Functions, REST APIs, integrations, PostgreSQL, Jest, Application Insights, or equivalent per the provided context); there are at least 3 strong evidence points from the provided context; no hard German C1/fluent blocker; no core requirement for 2+ technologies that are only basic/personal/training-only for the candidate; for early-stage product-engineer roles, direct product/customer evidence, company-stage fit and location/remote conditions are strong enough. Reflect the strongest positioning angle, the 3-5 CV arguments, which career cases to use, and what to avoid in `top_reasons`/`summary` — do not write CV content itself at this step.

Use MAYBE when: score is usually around 55-74 per the score interpretation and risk-stacking rules above; there is some strong match but also a meaningful risk; the gap could plausibly be mitigated by careful positioning; nice-to-have technologies are weak for the candidate but core requirements are still close; German is preferred but not clearly mandatory; seniority is slightly high but evidence may still be acceptable and risks are not stacked; or it is an early-stage product-engineer/startup/founder-facing/customer-facing role where direct evidence is not strong enough for apply. Reflect what would make it worth applying, what risk must be mitigated, and what to research before applying, in `top_reasons`/`summary`.

Use SKIP when any major blocker applies: German C1/fluent is mandatory or the role is strongly German-speaking/customer-facing (a hard blocker for the candidate's current German A2/B1 by default, even with a good technical stack match — see Language Risk Rules); the role is pure Frontend, PHP-only, DevOps-only, Kubernetes-heavy, QA, support, low-code, WordPress, pure AI/ML, MLOps or data science; core stack is mainly Python/FastAPI/AI but commercial production is required; core stack is Kubernetes/Docker/DevOps ownership but evidence is only basic/local/collaboration; the role requires senior/lead/architect ownership the evidence does not support; remote/location conditions are unrealistic; there are fewer than 2 credible evidence points; the CV would need exaggeration to look relevant; or it is a Senior/Lead role with 4+ medium/high risks stacked (per Risk Stacking above). Reflect the clear reason, and whether any keyword/skill is worth tracking for future vacancies, in `top_reasons`/`summary`. Do not generate CV content for skip.

Do not create any separate skip-archive file, note or link as part of this output — a dedicated downstream step handles skip-reason artifacts from the structured `decision`/`summary`/`top_reasons` fields above; this prompt's only output is the JSON object defined in the contract.

=== HIDDEN ROLE LOGIC ===

Always infer what the company is really testing beyond the literal requirement list, for example: many cloud/serverless requirements → production cloud workflow ownership, not just syntax; many integration/API requirements → reliability, data mapping, error handling, external API constraints; many testing/CI/CD requirements → engineering maturity and maintainability; stakeholder/client requirements → communication, clarity, autonomy; German required → daily business communication, not just engineering English (very good German for customers/partners/service providers is an external German communication blocker for the candidate's current German A2/B1 unless English is explicitly the main working language); Kubernetes/DevOps-heavy → platform ownership expectations, not developer collaboration; AI/ML-heavy → production model/RAG/LLM experience expectations, not personal API usage; early-stage/product-engineer/founder-facing/customer-facing → product impact, direct customer understanding, ambiguity tolerance, product decision ownership and startup/company-stage fit, not just fullstack coding. Populate `hidden_role_logic` with the inferences that actually apply to this vacancy.

=== EVIDENCE MAPPING ===

For every strong match, map the vacancy requirement to concrete evidence from the provided context (which file/case, and how it relates to the vacancy) via `must_have`/`nice_to_have`/`evidence_risks`. Use one of: supported / personal_only / needs_evidence / not_supported for `evidence_status`. Do not treat a skill as strong just because it appears somewhere in the provided context — use `Tech_Stack_Matrix_RU_v2_3_current_work_sync.md` (when inlined) to determine the real level.

=== OVERCLAIMING / SAFETY CHECKS ===

Always check and explicitly flag (via `evidence_risks`, `top_reasons` or `summary`) whether the vacancy could tempt overclaiming. Pay special attention to:

- Python / FastAPI / OpenAI / AI / RAG — personal/portfolio only unless the context states otherwise.
- MCP / Claude Code — personal/portfolio tooling exposure only, not commercial production.
- Kubernetes — basic/training exposure only.
- Docker — local/personal and tooling, not production platform ownership.
- Terraform — configuration support and DevOps collaboration, not DevOps ownership.
- Azure DevOps / CI/CD — participation/support, not pipeline architecture ownership unless evidenced.
- GraphQL — working changes at BFF/frontend boundary, not full platform ownership.
- React/Next.js — backend-focused fullstack contribution, not pure frontend specialization.
- PHP — a past backend foundation, not the current target stack.
- German — A2/B1 by default, not professional German.
- English — B1/B1+ professional working use by default, not fluent.
- Ownership — avoid implying sole ownership if the provided context describes a team-maintained case.

Core must-have with personal-only evidence: if a `must_have` requirement that is the vacancy's actual defining/primary ask (not an incidental item in a longer list) has `evidence_status: personal_only` or `needs_evidence`, do not treat it as one ordinary medium risk among several — this is a direct gap on the role's core requirement. Weight it independently in the decision: it should generally cap the decision at "maybe," and combined with any other meaningful risk should push toward "skip," even if the total numeric score alone would suggest apply.

Never present personal AI/RAG/FastAPI/MCP/Claude Code exposure as commercial production experience. Never treat Docker, NestJS, Kubernetes or AWS as commercial core skills without explicit supporting evidence in the input context. Preserve uncertainty instead of hiding it — if the input context is ambiguous or incomplete, say so in `summary` or `top_reasons` rather than guessing. Do not recommend "apply" only because some keywords match; require actual production/commercial relevance per the rubric above.

=== RECOMMENDED NEXT ACTION AND MANUAL REVIEW ===

Set `manual_review_required` to true whenever `decision` is "maybe", or when `decision` is "apply"/"skip" but any `language_risk`/`location_risk` is "high" or "blocker", or fewer than 2 credible evidence points support the decision.

`recommended_next_action` should be one short actionable sentence, for example: "Generate targeted CV content" (apply), "Pause for manual review before deciding" (maybe), or "Generate skip reason and stop pipeline unless manually overridden" (skip). If `decision` is "apply" or "maybe", note in `recommended_next_action` or `top_reasons` that any generated CV must keep the mandatory current-work block (the post-employment-gap block, see the standing note above) — do not recommend omitting it.

Always output valid JSON matching the contract above, and nothing else.
