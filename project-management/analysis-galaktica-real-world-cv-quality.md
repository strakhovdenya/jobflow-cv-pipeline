## Category A — Confirmed code bugs (not AI/prompt issues)

### A1. Certifications never actually render (blind type cast)

`apps/api/src/document-export/prompt2-to-cv-content.mapper.ts:102`:
```ts
certifications: cv.certifications as CvCertification[],
```
Prompt 2's real output shape for a certification is `{ title, include, reason }`
(`targeted-cv-content.schema.ts` has no stricter type than `unknown[]` for this field). The
renderer's `CvCertification` (`cv-content.schema.ts:76`) requires `{ name, issuer?, date?, priority }`.
The `as` cast bypasses structural checking at compile time; at runtime every certification renders
as an empty `<div class="cert-item"></div>` (verified directly in this workspace's
`04_cv_export.html` — confirmed empty divs under a real `Certifications` heading), and the mapper
never filters by `include: true`, so even excluded certifications would attempt to render.

**Impact:** every CV this pipeline has ever exported has a broken/empty Certifications section.
**Fix shape:** map `title → name`, drop `include: false` entries, decide `priority` (constant or
derived), before this reaches `CvContent`.

### A2. Static candidate-profile config ships literal placeholder/broken data

`apps/api/src/document-export/candidate-profile.config.ts` — `CANDIDATE_PROFILE_CONFIG`:
```ts
education: [{ institution: 'Placeholder University', degree: 'Placeholder Degree', dates: 'Placeholder dates' }],
languages: [
  { language: 'English', level: 'Professional working proficiency' },
  ...
  { language: 'German', level: 'A2/B1', notes: 'Learning — see language risk notes' },
],
links: [],
volunteering: [],
```
This is the exact content that ended up on the real exported PDF: `Placeholder University` /
`Placeholder Degree` / `Placeholder dates` verbatim, English overstated as generic "Professional
working proficiency" instead of the real, already-established `B1/B1+, professional working use`
(the correct wording exists in every golden-dataset `manual-cv.md`), and — worst — an internal
authoring note (`"Learning — see language risk notes"`) leaking onto the public CV as if it were
real content next to "German".

**This is not an AI defect.** No prompt run touches this file; it is static, hand-authored
configuration that was apparently left with stub values (likely from initial scaffolding) and never
updated with the real profile data that demonstrably already exists elsewhere in this project
(`knowledge-sources/`, golden-dataset `manual-cv.md` files).

**Impact:** every CV this pipeline has ever exported carries fabricated education and an internal
process note as public content — a correctness/professionalism defect more severe than anything
Prompt 2/3 have been calibrated against so far, and one that cannot be fixed by prompt engineering
since it doesn't go through any prompt.

`links: []` / `volunteering: []` being always-empty is lower-severity and may be intentional
(volunteering is already rendered inside `current_work_block` per the established convention,
`links` may just be genuinely unused) — flagged for confirmation, not assumed as a bug.

## Category B — Architectural gap: Prompt 3 cannot see the data Category A is about

Confirmed directly from this run's own `03_pre_pdf_check.json` → `overall_notes`:

> "Language-level fields are not present in the supplied CV content, so German and English
> proficiency could not be independently validated here."

Root cause, confirmed in code: `Prompt3InputBuilderService.buildPrompt3Input()`
(`apps/api/src/pipeline/prompt3/prompt3-input-builder.service.ts:97-98`) sends only
`02_targeted_cv_content.json` — the raw Prompt 2 output, which per its own schema
(`targeted-cv-content.schema.ts`) has **no** `candidate`/`education`/`languages`/`links`/
`volunteering` fields. Those are merged in only inside `prompt2-to-cv-content.mapper.ts`, which runs
during `export-cv` — **after** Prompt 3 has already produced its verdict.

**Consequence:** even after A1/A2 are fixed, Prompt 3 (the pipeline's own pre-PDF safety check) is
structurally blind to the entire candidate-profile-sourced portion of every exported CV — it cannot
flag an overstated language level, a bad education line, or any future placeholder/config defect
in that data, no matter how the prompt text is worded. This is a data-flow gap, not a
prompt-wording gap, and needs a code change (either include a static-profile snapshot in Prompt 3's
input context, or add a separate deterministic validation step) rather than another `PromptTemplate`
version.

## Category C — Prompt 2 wording gaps (confirmed via this run's raw JSON)

### C1. Prompt 2's own JobFlow bullet template still contains the exact BOP-violating jargon Prompt 3 has to clean up every run

`apps/api/prisma/prompts/prompt2_v4.txt:77` (the literal quoted bullet Prompt 2 is told to use):
> "...evidence-based claim validation and deterministic PDF export; implemented human-in-the-loop
> AI workflow concepts, Evidence Guard, prompt versioning, artifact traceability, token/cost
> tracking and backend HTML-to-PDF export without AI token usage."

This is the same wording Prompt 3's audit-vocabulary rule and 16-pattern list exist specifically to
remove (`evidence-based claim validation`, `human-in-the-loop AI workflow concepts`, `artifact
traceability`, `backend HTML-to-PDF export without AI token usage` are 4 of the 16 listed
patterns). Confirmed this run: Prompt 3 did have to correct this exact bullet again
(`current_work_block.bullets[2].text`, `selected_projects[0].bullets[1].text`) — the pipeline is
paying an AI call every single run to clean up wording that Prompt 2's own template hard-codes.
**Fix belongs in `prompt2_v4.txt`'s own template text**, not another Prompt 3 iteration.

### C2. No rule preventing JobFlow (or any current-work item) from being duplicated into `selected_projects`

This run's `02_targeted_cv_content.json` has `selected_projects[0]` = JobFlow again
(`project_type: "current_work_project"`, `include: true`), fully duplicating the bullet already
present in `current_work_block`. The established convention (every golden-dataset `manual-cv.md`)
explicitly omits Selected Projects entirely when JobFlow is already in current-work — but
`prompt2_v4.txt` never states this as a rule; it only says (line 95) that JobFlow "remains the
primary current portfolio signal" when deciding whether to include *other* personal projects,
without saying JobFlow itself must not also appear in `selected_projects`. The schema's own
`project_type: "current_work_project"` enum value seems to anticipate this case existing, without
clarifying when (if ever) it's appropriate.

### C3. Repeated defensive/audit-style disclaimer, not caught as a pattern by Prompt 3 §6.1

The phrase pattern "...; this is portfolio work/exposure, not commercial production[experience]."
appears **three separate times** in this run's raw content (`summary[3]`, one `current_work_block`
bullet, one `selected_projects` bullet) — each grammatically distinct, so no single literal string
match, but semantically the same repeated meta-commentary. Prompt 3 v4's §6.1 (added specifically
to catch "meta-commentary about the CV... rather than about the work itself" and "over-explaining
limitations") corrected the individual audit-vocabulary words inside each sentence (`exposure`,
`commercial production experience`) but did **not** flag the cross-section repetition itself as a
finding — a genuine true-positive miss for §6.1, valuable because the golden dataset never exercised
this pattern (its cases don't repeat a disclaimer three times).

## Category D — Prompt 3 coverage gaps identified from this real case

- **D1 (= C3 above):** §6.1 doesn't yet reason about a phrase *pattern* repeated across sections —
  only about a single sentence in isolation.
- **D2:** Nothing in §0-§7 checks for the same project/content appearing in two different sections
  (`current_work_block` vs `selected_projects`) — a distinct, checkable defect from C3's wording
  issue and from C2's Prompt 2 root cause. Even if Prompt 2 is fixed at the source (C2), Prompt 3
  arguably should still catch a recurrence as a safety net, the same way it already catches other
  wording regressions.
- **D3 (= Category B):** structurally cannot validate education/language content until the data
  reaches it.

## Candidate items for `/plan` + `/issues`

Rough severity ordering, for whoever scopes the next PRD/plan from this file:

1. **A1 (certifications mapping bug)** — small, isolated, high-confidence fix; every CV affected.
2. **A2 (placeholder candidate-profile data)** — small in code terms (replace static values with
   real ones) but requires sourcing the correct real values (education, honest English level,
   remove the leaked note) — likely a 10-minute config fix once someone confirms the values
   editorially, but blocks every real application sent through this pipeline until fixed.
3. **B (Prompt 3 blind to candidate-profile data)** — real architecture decision needed: either
   feed a static-profile snapshot into Prompt 3's input context, or add a separate deterministic
   check (no AI call needed, since these are static values, not generated content) that validates
   `candidate-profile.config.ts` doesn't contain obvious placeholder markers before allowing export.
   The deterministic-check option may be strictly better here — Category A2 is static data, not an
   AI-generation problem, so a cheap non-AI guard (e.g. reject known placeholder strings) might
   catch this class of bug more reliably than teaching Prompt 3 to review it.
4. **C1 (Prompt 2's own template still has old BOP jargon)** — small, isolated prompt text fix,
   same `PromptTemplate` versioning discipline as the Prompt 3 rounds (new `prompt2_v5.txt`, `v4`
   kept inactive).
5. **C2 (JobFlow duplicated into Selected Projects)** — small prompt-wording fix, same file.
6. **C3/D1 (repeated disclaimer pattern not caught)** and **D2 (no cross-section duplication
   check)** — both are Prompt 3 §6.1/new-section extensions; bundle into one `prompt3_v5.txt` round
   if pursued, following the same re-run-both-golden-cases-plus-this-real-case verification
   discipline established in ISSUE-250.
7. Confirm A2's `links: []`/`volunteering: []` are intentional before doing anything with them.

Not proposing exact issue boundaries here — that's the next skill's job (`/prd` or `/plan`/`/issues`
directly, depending on how the user wants to scope this).
