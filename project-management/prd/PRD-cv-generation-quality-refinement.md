## User Scenarios

- **Любая вакансия:** экспорт содержит каноническую вводную строку CIW дословно; Prompt 3 её не переписывает.
- **Backend-вакансия с Home Budget в Selected Projects:** обзор портфолио сохраняет общий факт про другие приложения (например, тесты в CI). Prompt 3 удаляет из обзора только конкретный механизм, цифру или функцию выбранного проекта.
- **Full-stack вакансия с AI как nice-to-have (S3):**
  - строка Tech CIW содержит то, что называют bullets блока, и технологии JobFlow, названные вакансией, — по одной метке на технологию и без версий;
  - стеки невыбранных приложений не сваливаются в эту строку;
  - Docker в EPAM отсутствует или указан с ограничением «local development».
- **Вакансия с LLM-интеграцией (S5):** в строке Tech CIW нет Claude Code / OpenAI Codex, если bullets блока их не называют.
- **Вакансия без AI (S1):**
  - в строке Tech CIW нет AI-технологий, если bullets блока их не называют;
  - обзор не пишет «public deployments», если публичное приложение среди представленных одно.
- **Немецкая вакансия без указания рабочего языка (S5):** письмо на немецком и не заявляет немецкий выше подтверждённого уровня. Английская вакансия (S1) получает английское письмо.
- **Владелец проводит финальную валидацию:** восстанавливает недостающие оценки требований до чтения новых CV, по одному одобряет сценарии, получает сравнение D↔C по матрице протокола §4.

Prompt 3 не получает `cv_rules` (только `tech_stack` и `career_cases`), поэтому в Prompt 3 канон приводится явно, вместе с указанием, что цитаты шаблона блока в источниках устарели.
2. **F2.** Единое определение дубля в Prompt 2 (правила обзора) и в Prompt 3 (§0.1):
   - дубль — то же достижение того же проекта: тот же механизм, цифра или функция;
   - общая практика или технология, верная для представленных обзором приложений, — не дубль;
   - если принадлежность неясна, проверенный факт не удаляется: замечание идёт в `overall_notes`.
3. **F3.** Область строки Tech CIW (композитная запись периода, а не запись одного проекта):
   - технологии, которые называют bullets блока: Node.js/React независимой работы, технологии выбранных facet'ов JobFlow, технологии, названные в обзоре и в дополнительном доказательстве;
   - плюс технологии записи JobFlow в registry, которые вакансия называет (правило «inclusion is mandatory» в пределах доказательств JobFlow);
   - **не** весь `techStack` JobFlow: технология JobFlow, которую не называют ни bullets блока, ни вакансия, в строку не попадает. В Baseline B строка S1/S2 (16 позиций) — это почти полный список JobFlow плюс Node.js/React; новая область уже;
   - **без** объединения стеков невыбранных приложений;
   - одна метка на технологию, без версий и без деталей, различающих проекты; существенные ограничения из доказательств сохраняются;
   - AI-технологии — только если их называют bullets блока; какие AI-факты попадают в bullets, решают существующие правила AI weight/kind;
   - без числового лимита.

   **Граница с общими правилами `tech_stack`.** Общие правила Prompt 2 (гейт прослеживаемости, «inclusion is mandatory», «never remove an evidence-backed technology», порядок по релевантности) для записей работодателей и Selected Projects не меняются. Для композитной записи CIW «доказательства записи» определяются как перечисленное выше, и правило «never remove» действует внутри этой области. Это сказано в самих общих правилах Prompt 2, чтобы два правила не противоречили друг другу. Prompt 3 согласован с этим: нормализованная метка не считается нарушением canonical-term.

   **Узкое исключение из правила canonical terms Prompt 2** (сейчас стр. 54 запрещает и сокращённые формы во всех `tech_stack`). В строке Tech CIW можно опустить только номер версии и уточнение в скобках, которое лишь различает проекты. Название пишется как в доказательствах; подмена технологии, сокращение или расширение названия и потеря существенного ограничения запрещены; в остальных полях правило не меняется.
4. **F5.** Факты обзора верны для приложений, которые обзор действительно представляет после выбора Selected Projects:

5. **F6.** Правило записи Selected Projects явно подчиняет её `tech_stack` существующему общему правилу порядка: состав — из `techStack` записи registry, порядок — по релевантности вакансии, а не порядок registry. Правило ISSUE-278 против произвольного усечения сохраняется. Правила точности и атрибуции, существенных ограничений доказательств и AI-позиционирования стоят выше сохранения состава: например, AI-инструмент записи (OpenAI Codex у Home Budget) не показывается в вакансии без упоминания AI. Релевантность сама по себе ничего не удаляет. Фильтрации и лимитов нет.

## Key Invariants

- Все гарантии Career Evidence Refresh сохраняются:
  - только проверенные доказательства;
  - коммерческое ≠ личное;
  - сильные коммерческие доказательства приоритетны, где релевантны;
  - `cvEligible` — единственный допуск, архив исключён;
  - структура CIW, ровно один bullet JobFlow;
  - отбор портфолио по вакансии;
  - AI weight и kind не смешиваются, нет AI в вакансии без AI;
  - метаданные credentials;
  - вход письма = экспортированный CV;
  - design = ATS по содержанию;
  - лимит страниц;
  - правила B1.
- Канонические frame-поля CIW одинаковы во всех CV. Prompt 3 исправляет их только при фактической или safety-ошибке, никогда — по стилю.
- Каноническая вводная строка задаётся в `cv_rules`. Prompt 2 и Prompt 3 повторяют её дословно, тест это проверяет.
- Prompt 3 не удаляет проверенный факт как дубль, если не установлено, что это то же достижение того же проекта.
- `tech_stack` любой записи содержит только технологии, прослеживаемые до доказательств этой записи. Правило ISSUE-278 против усечения и правило порядка действуют для записей работодателей и Selected Projects без изменений. Строка CIW — композитная запись, её область — видимое содержание блока и технологии JobFlow, названные вакансией (In Scope п. 3).
- Нормализация меток (без версий и без деталей, различающих проекты) не удаляет материальные ограничения из доказательств.
- Язык письма не повышает подтверждённый уровень владения языком. Поле `language` совпадает с фактическим языком письма. Контракт manual note (ADR-034) и совместимость с историческими `cover_letter.json` сохраняются.
- Завершённая валидация не означает успеха инициативы: вердикт по целям отделён от отчёта о процедуре; блокирующий дефект или материальная регрессия останавливает прогоны до записанного решения владельца.
- Базис сравнения D↔C — эффективный контент (Baseline C — replay без повторного экспорта). Метрики экспорта C берутся из файлов Baseline B, где S3 содержит дефект B1; улучшение B1 не приписывается инициативе.
- Экспорт детерминирован, без `AiRun` (ADR-012). Prompt 3 не блокирует экспорт (ADR-031). Переходы статусов не меняются (ADR-038).
- В тестах нет реальных AI-вызовов. Fixtures синтетические (anti-literal), кроме существующих real-file наборов активных источников. Тест согласованности берёт канон из `cv_rules`, а не из литерала в тесте.
- Исходные артефакты валидации (VAL/, workspaces A и B) не перезаписываются и не удаляются. Приватный текст CV не публикуется.
- **Variation point:** правила генерации, проверки и письма меняются через существующие границы — новую версию `PromptTemplate` (seed, ADR-039) и новую версию knowledge source (`ACTIVE_KNOWLEDGE_SOURCES` + `register-knowledge-sources`). Новых модулей, интерфейсов и runtime-механизмов нет.
