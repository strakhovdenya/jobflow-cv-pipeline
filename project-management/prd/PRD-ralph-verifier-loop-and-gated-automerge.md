# PRD: Ralph ↔ Verifier Loop and Gated Auto-Merge (EPIC-30)

**Дата**: 2026-09-26
**Статус**: Draft
**Затрагиваемое приложение**: ни одно — фабрика (пакет `dark-factory` после EPIC-28) и её
подключение в jobflow; `apps/api`/`apps/web` не меняются
**Связанный issue/backlog-пункт**: новая фича — ещё не заведена как issue. Предпосылки: EPIC-27
(`PRD-verifiable-spec-and-independent-verifier.md`), EPIC-28 (`PRD-dark-factory-extraction.md`,
трекер #491), #399, #506.

## Цель

Владелец запускает Ralph на очередь issue, и задачи низкого риска доходят до ветки назначения без
его участия: Ralph сам исправляет замечания верификатора и CI, а PR сливается автоматически только
тогда, когда детерминированная проверка подтверждает, что он в разрешённом классе и все сигналы
зелёные на текущем коммите. Всё остальное по-прежнему мержит человек.

## Контекст и согласованность с проектом

- Сейчас Ralph заканчивает работу на создании PR («Мёрдж PR всегда делает человек»,
  `.claude/ralph/README.md`; `docs/12_ai_software_factory.md` §7: «the **merge** stay with a
  human», и там же следующий шаг — «guarded auto-merge: CI, CodeQL and Verifier all green for the
  current head commit, re-checked right before merging, with an opt-out label»).
- На PR #505 и #508 (2026-09-26) верификатор давал FAIL 3–4 круга подряд; каждое замечание
  разбирал и чинил человек. Без цикла «замечание → исправление → повторный прогон» автономный
  режим останавливается на первом FAIL.
- Верификатор уже отдаёт машиночитаемые сигналы, на которые можно опереться: вердикт считает
  скрипт, а не модель (ADR-041 п. 2); `risk_zones` — закрытый enum (`auth`, `secrets`, `ci`,
  `migrations`, `fs_shell_sinks`, `state_machine`, `dependencies`, `adr_034_manual_note`, `none`;
  амендмент ADR-041 от 2026-09-24); `out_of_scope_files` делает вердикт FAIL (амендмент ISSUE-443);
  упавшая CI-проверка делает вердикт FAIL (амендмент ISSUE-435). EPIC-27 добавляет `NEEDS_HUMAN`,
  заморозку спеки, сканер подделки тестов и trusted-список обязательных проверок.
- EPIC-27 и EPIC-28 явно оставили это за скобками: «Автомерж … — отдельный эпик»,
  «Сделать верификатор обязательным … остаётся отдельным решением владельца» (EPIC-27, «Не в
  скоупе»); «Конкретные новые элементы (… шаги Ralph …) — отдельные эпики после EPIC-28»,
  «Автомерж, обязательность верификатора — отдельные решения владельца по каждому проекту»
  (EPIC-28, «Не в скоупе»).
- Canonical-артефакты пайплайна (`00_vacancy_source` … `cover_letter`) не затрагиваются.
- Связанные ADR: ADR-025 (epic base branch и её branch protection), ADR-030 (issues — источник
  правды, ветки `task/ISSUE-<n>-...`), ADR-041 (верификатор и его амендменты), ADR-035 (test
  evidence комментарием на issue).

## Пользовательские сценарии

- Владелец включает этап A (enforce верификатора, `Acceptance Verifier` — обязательная проверка) →
  Ralph открывает PR, получает FAIL верификатора или красный CI, сам исправляет и пушит, пока не
  PASS или не кончится бюджет → владелец смотрит дифф и мержит, помечая, был ли вердикт верным.
- Порог этапа A достигнут, владелец включает этап B1 → PR подзадачи эпика, прошедший проверку
  допуска, сливается в epic base branch автоматически; ветку `-base` в `main` мержит владелец после
  ревью эпика целиком.
- Порог этапа B1 достигнут, владелец включает этап B2 → PR низкого риска сливается в `main`
  автоматически.
- PR не проходит проверку допуска (рисковая зона, файл вне allowlist, ручная проверка в issue,
  лейбл `no-automerge`) → остаётся открытым, в PR — комментарий со списком причин.
- Владелец обнаружил дефект в автоматически слитом PR и ставит ему метку ложного PASS → автомерж
  выключается до повторного прохождения порога; следующие PR снова ждут человека.
- Верификатор вернул `NEEDS_HUMAN` или Ralph исчерпал попытки исправления → PR остаётся открытым,
  issue получает лейбл блокировки и комментарий, Ralph переходит к следующей issue.

## В скоупе

1. **Цикл исправления после PR.** После создания или обновления PR Ralph ждёт итоговые сигналы
   на текущем head-коммите (CI и `Acceptance Verifier`), читает отчёт верификатора и упавшие
   проверки как недоверенные данные, запускает агента-исправителя с этим входом, прогоняет
   проверки границы агента (#398) и финальный гейт, пушит и повторяет. Ограничение — отдельный
   бюджет попыток и времени на PR. `NEEDS_HUMAN`, исчерпанный бюджет, BLOCKED исправителя —
   остановка с лейблом и комментарием.
2. **Проверка допуска к автомержу** — детерминированный код (не модель), выдающий «разрешено /
   запрещено + список причин» по:
   - вердикту `PASS` на текущем head-коммите; результат для старого коммита не считается;
   - зелёным обязательным проверкам из trusted-списка EPIC-27;
   - `risk_zones` = ровно `["none"]`;
   - отсутствию `## Manual verification (owner, not gated)` и лейбла `manual-verified` в issue;
   - изменённым файлам внутри allowlist путей из профиля проекта, вне denylist (для jobflow по
     умолчанию запрещены: `.github/`, `scripts/`, `.claude/`, `.husky/`,
     `apps/api/prisma/migrations/`, `apps/api/prisma/prompts/`, `apps/api/knowledge-sources/`,
     `package.json`/lockfile-и);
   - неизменной замороженной спеке issue;
   - PR открыт Ralph из ветки `task/ISSUE-<n>-...`, у PR и issue нет лейбла `no-automerge`;
   - ветке назначения, разрешённой текущим этапом (B1 — только epic base branch, B2 — также
     `main`).
3. **Автомерж.** Контроллер повторяет проверку допуска непосредственно перед слиянием и сливает
   merge-коммитом с `expectedHeadSha`; если голова PR или сигналы изменились — не сливает.
4. **Учёт исходов и порог.** Владелец помечает PR после своего ревью: ложный PASS / ложный FAIL /
   верно. Скрипт метрик (расширение #484) считает по ним:
   - этап A → B1: не меньше 20 PR от Ralph на этапе A, 0 ложных PASS, доля ложных FAIL ≤ 20 %;
   - B1 → B2: не меньше 20 PR, автоматически слитых в epic base branch, и 0 дефектов, найденных
     при ревью base → `main` *(порог B2 предложен этим PRD — см. «Открытые вопросы»)*;
   - любой ложный PASS после включения этапа автоматически запрещает автомерж (проверка допуска
     его учитывает), пока порог не пройден заново.
5. **Выключатели.** Этап включается trusted-настройкой профиля проекта на default-ветке, а не
   кодом; лейбл `no-automerge` на PR или issue запрещает автомерж для него; одна настройка
   выключает автомерж целиком.
6. **Настройка GitHub для этапов** описана и проверяется `factory doctor` (EPIC-28): enforce
   верификатора, `Acceptance Verifier` среди обязательных проверок `main` и каждой epic base
   branch (ADR-025), разрешённый auto-merge в репозитории.
7. **Документация и ADR:** новый ADR, отменяющий правило «мёрдж всегда делает человек» для
   допущенного класса; обновление `docs/12_ai_software_factory.md` §7 и документации фабрики;
   профили jobflow и cards с автомержем выключенным по умолчанию.

## Не в скоупе

- Автомерж PR, не созданных Ralph (ручные PR, Dependabot).
- Автомерж в зонах из denylist и в любой `risk_zones`, кроме `none`, — их всегда мержит человек.
- Автоматическое создание или правка issue (планирование остаётся у человека, `docs/12` §7).
- Автомерж ветки `-base` в `main` на этапе B1.
- Изменение правил вердикта верификатора (EPIC-27) и новых проверок верификатора.
- Продуктовый код `apps/api`/`apps/web`, PostgreSQL/Prisma, `STORAGE_ROOT`.
- Деплой после мержа.
- Выбор механизма песочницы — решается в #506.

## Влияние на state machine (если применимо)

Не применимо: фича не меняет состояние workspace. Жизненный цикл PR, которым управляет
контроллер Ralph:

| Событие | Условие | Действие контроллера | Итог |
|---|---|---|---|
| PR создан / запушен фикс | — | ждёт CI и верификатор на новом head | ожидание |
| Сигналы получены | FAIL или красный CI, попытки есть | запускает исправителя, гейт, push | ожидание |
| Сигналы получены | `NEEDS_HUMAN`, попытки исчерпаны или исправитель BLOCKED | лейбл + комментарий | PR открыт, ждёт человека |
| Сигналы получены | PASS, допуск запрещён | комментарий с причинами | PR открыт, ждёт человека |
| Сигналы получены | PASS, допуск разрешён | повторная проверка допуска, merge с `expectedHeadSha` | слит |
| Перед merge | голова или сигналы изменились | не сливает | ожидание |

## Влияние на модель данных

Не применимо: PostgreSQL и Prisma не затрагиваются. Исходы ревью и решения о допуске хранятся в
GitHub (лейблы, комментарии, статусы) и в артефактах CI; трекинг-файлы в репозитории не
заводятся (ADR-030).

## API-поверхность

Не применимо: HTTP-эндпоинты приложения не меняются.

## Ключевые инварианты

- **Решает код, не модель.** Допуск к автомержу вычисляется детерминированным скриптом по
  сигналам GitHub и отчёту верификатора, как вердикт в ADR-041 п. 2. Модель не выдаёт поле
  «можно мержить».
- **Fail closed.** Отсутствующий, устаревший (другой head SHA) или нечитаемый сигнал запрещает
  автомерж.
- **Проверка непосредственно перед слиянием.** Между решением и слиянием голова PR не должна
  меняться; merge выполняется с `expectedHeadSha`.
- **Недоверенный вход.** Отчёт верификатора, логи CI и комментарии PR передаются исправителю как
  данные, не инструкции (как тело issue после #398). Исправитель работает с теми же правами и
  проверками границы, что и реализатор.
- **Конфигурация — только с default-ветки.** Этап, allowlist/denylist путей и выключатели
  читаются из trusted-профиля на default-ветке; PR не может расширить собственный допуск.
- **Человек — единственный, кто повышает этап.** Переход A → B1 → B2 — действие владельца после
  выполнения порога; скрипт может только запретить автомерж, не включить его.
- **Автомерж не обходит branch protection.** Слияние идёт через обычные обязательные проверки;
  никаких admin-override.

## Технические ограничения

- Фабрика работает на Windows у оператора и в CI на Linux (EPIC-28): ожидание сигналов и
  повторные прогоны не должны зависеть от платформенных особенностей.
- Ожидание CI и верификатора занимает минуты (прогон верификатора — около 4–5 минут на PR
  2026-09-26); цикл исправления должен укладываться в бюджет времени задачи из #398 или иметь
  собственный.
- Верификатор бывает шумным (ложный FAIL по `bad reference` на #508); цикл исправления не должен
  тратить все попытки на шум — бюджет и остановка по повторяющемуся замечанию.
- Учёт ложных PASS зависит от разметки владельцем; без неё порог не считается пройденным.
- `GITHUB_TOKEN` не читает classic branch protection (PRD EPIC-27, «Технические ограничения»), поэтому
  список обязательных проверок берётся из trusted-файла, а не из настроек защиты.

## Критерии готовности (Acceptance Criteria)

- [ ] После FAIL верификатора или красной обязательной проверки Ralph запускает исправителя с
      отчётом как недоверенными данными, пушит исправление и ждёт новых сигналов; тест
      контроллера с подменёнными агентом и GitHub проходит сценарий FAIL → фикс → PASS.
- [ ] `NEEDS_HUMAN`, исчерпанный бюджет попыток или BLOCKED исправителя останавливают цикл с
      лейблом и комментарием на issue; тест на каждый из трёх случаев.
- [ ] Проверка допуска запрещает автомерж, называя причину, для каждого случая: вердикт не PASS;
      вердикт для другого head SHA; красная или отсутствующая обязательная проверка; `risk_zones`
      не `["none"]`; `## Manual verification` в issue; файл в denylist или вне allowlist;
      изменённая замороженная спека; лейбл `no-automerge`; ветка назначения не разрешена этапом;
      зафиксированный ложный PASS после включения этапа. Тест на каждый случай и тест разрешения.
- [ ] Отсутствующий или нечитаемый вход проверки допуска даёт «запрещено» (тест).
- [ ] Автомерж сливает только с `expectedHeadSha`, а при сменившейся голове не сливает (тест).
- [ ] Скрипт метрик по разметке владельца выводит число PR, ложных PASS, ложных FAIL и
      выполнение порогов A → B1 и B1 → B2 (тест на фикстурах).
- [ ] Профиль проекта по умолчанию: автомерж выключен; включение этапа — только изменение
      trusted-профиля на default-ветке (тест: PR, меняющий этап в своей ветке, не влияет на свой
      допуск).
- [ ] `factory doctor` сообщает о несоответствии настроек GitHub включённому этапу: не включён
      enforce, `Acceptance Verifier` не среди обязательных проверок ветки назначения, auto-merge
      запрещён в репозитории (тест).
- [ ] ADR о допущенном классе автомержа принят; `docs/12_ai_software_factory.md` §7 и документация
      фабрики описывают этапы, порог, выключатели и откат.

## Test Requirement (набросок)

Unit-тесты ядра фабрики на двух фикстурных профилях (как требует EPIC-28): цикл исправления с
подменёнными агентом и GitHub API, проверка допуска по каждому условию, скрипт метрик на
фикстурах, `factory doctor`. Ручная проверка владельцем: этап A на реальных PR jobflow до
порога — это эксплуатация, а не критерий приёмки эпика.

## Открытые вопросы

1. **Порог B1 → B2.** PRD предлагает: 20 PR, автоматически слитых в epic base branch, и 0
   дефектов при ревью base → `main`. Подтвердить или задать свой.
2. **Разметка исходов ревью.** Лейблы на PR (`verifier-false-pass`, `verifier-false-fail`,
   `verifier-correct`) или ответ владельца в комментарии. Лейблы проще считать скриптом.
3. **Бюджет цикла исправления.** Число попыток на PR (например, 3) и отдельный лимит времени;
   останавливаться ли на повторении того же замечания в двух прогонах подряд.
4. **Allowlist путей для jobflow.** По умолчанию `apps/**` и `docs/**` за вычетом denylist выше;
   входит ли `project-management/**` (CHANGELOG, PRD).
5. **Номер эпика.** EPIC-29 занят (`PRD-pipeline-step-atomicity-and-recovery.md`); этот PRD
   использует EPIC-30.

## Предполагаемое дробление на подзадачи (только если это эпик)

1. **Ожидание сигналов PR** — контроллер получает CI и вердикт верификатора для текущего head и
   различает «ещё идёт», «устарело», «готово»; основа для AC о цикле.
2. **Шаг «исправление по замечаниям»** в конвейере Ralph — исправитель на отчёте верификатора и
   упавших проверках, бюджет, остановки; AC о цикле и остановках.
3. **Проверка допуска** — детерминированный скрипт со всеми условиями и причинами; AC о допуске
   и fail closed.
4. **Автомерж** — повторная проверка и слияние с `expectedHeadSha`; AC о слиянии.
5. **Разметка и метрики** — лейблы исходов, расширение скрипта #484, пороги; AC о метриках и
   откате.
6. **Профиль, выключатели, `factory doctor`** — настройки этапа, лейбл `no-automerge`, проверка
   настроек GitHub; AC о профиле и doctor.
7. **ADR и документация**, включение этапа A в jobflow; AC о документации.

Порядок: 1 → 2 → 3 → 4, затем 5 и 6 параллельно, 7 последней. Работа идёт в репозитории
`dark-factory` (задачи 1–6) и одним PR в jobflow (профиль, ADR, `docs/12`), как фазы 6–7 EPIC-28;
epic base branch в jobflow не нужна.
