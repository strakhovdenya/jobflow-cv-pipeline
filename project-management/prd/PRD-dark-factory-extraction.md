# PRD: Dark Factory Extraction (EPIC-28)

**Дата**: 2026-09-26 (обновлено 2026-10-11: слой контекста проекта, доставка пакета Claude Code,
golden eval, статус зависимостей — ISSUE-641)
**Статус**: Draft
**Затрагиваемое приложение**: ни одно из `apps/*`. Затрагивает репозиторную инфраструктуру двух
проектов (`strakhovdenya/jobflow-cv-pipeline`, `strakhovdenya/cards`) и новый репозиторий фабрики.
**Связанный issue/backlog-пункт**: трекер эпика #491. Новый эпик **EPIC-28**, следует за EPIC-27
(`PRD-verifiable-spec-and-independent-verifier.md`, issues #464–#489).

## Цель

Вынести всё, что относится к AI software factory (скиллы `prd`/`plan`/`issues`/`task-lifecycle`,
хуки, Ralph, Acceptance Verifier, контракт issue), в один переиспользуемый versioned-пакет, который
подключается к любому проекту — сначала к jobflow и cards — через конфигурацию, без копирования и
расхождения кода между проектами.

## Пользовательские сценарии

Пользователь — владелец, ведущий несколько проектов.

- Владелец подключает фабрику к новому проекту: кладёт профиль и trusted-конфиги, подключает
  пакет по закреплённой версии, запускает `factory doctor` → получает список того, чего не хватает
  (лейблы, секрет, переменная модели, branch protection), и после исправления — рабочий цикл
  PRD → план → issues → Ralph → PR → верификатор.
- Владелец исправляет баг Ralph в репозитории фабрики → выпускает версию → каждый проект получает
  исправление PR-ом, поднимающим закреплённую версию, а не переносом кода руками.
- Владелец меняет промпт верификатора → эталонные наборы PR обоих проектов показывают, не
  появились ли ложные PASS.
- PR в проекте пытается изменить код верификатора или его конфиг → не может: ядро закреплено по
  версии, конфиг читается с default-ветки.

17. **Слой контекста проекта.** Ядро (скиллы, хуки, Ralph) одинаково во всех проектах, а контекст

    - **правило «путь → скиллы»**: таблица записей `путь`, `расширения файлов`, `метка`, `скиллы`
      плюс общий базовый набор (замена `scripts/required-skills.js` jobflow). Это единственный
      источник для skill gate хука и для промпта Ralph (`missingRequiredSkills`): интерактивная

      правило записано только текстом в его `CLAUDE.md`);
    - **набор устанавливаемых скиллов**: метаскиллы (замена списка `SKILLS` в
      `setup-metaskills.js` обоих проектов) и проектные скиллы, которые остаются в проекте;
    - **файлы правил и описания проекта** (корневой и app-level `CLAUDE.md` и т.п.): промпты Ralph
      и агентов фабрики называют их явно. В интерактивной сессии `CLAUDE.md` загружает сам Claude
      Code, а в клоне Ralph и CI агент получает список из профиля, а не полагается на авто-загрузку;
    - **overlay шаблонов документов**: проект добавляет свои секции в шаблоны PRD, плана и issue
      (jobflow — state machine, модель данных, API; cards — схема Supabase, UI), не меняя текст
      скилла;
    - **параметры хуков**: команды lint/typecheck по путям и признаки «doc-only». Разбор Bash-команды
      (`git commit`/`git push` по сегментам, а не подстрокой) — в ядре и одинаков для всех проектов.

    Правило overlay для всего слоя то же, что для контракта issue (п. 7): проект добавляет, но не
    убирает базовое — базовые секции шаблонов и проверки хуков ядра. Набора скиллов в ядре нет:
    таблица «путь → скиллы» целиком принадлежит профилю, ядро только применяет её.
18. **Доставка пакета Claude Code в проект** (уточнение п. 6 и «Открытых вопросов» п. 3 по
    документации Claude Code, 2026-10-11):
    - пакет ставится npm-зависимостью (п. 2 «Открытых вопросов»); `postinstall` копирует скиллы и
      агентов фабрики и метаскиллы из профиля в `.claude/skills/<name>` и `.claude/agents/<name>`
      обычными каталогами (не ссылками), как сейчас делает `setup-metaskills.js`. Сами каталоги
      `.claude/skills/` и `.claude/agents/` содержат отслеживаемые файлы проекта, поэтому в
      `.gitignore` перечисляется каждая копия по имени (как сейчас метаскиллы), а не каталог целиком;
    - если имя копии совпадает с отслеживаемым файлом или каталогом проекта, setup-скрипт его не
      удаляет и не перезаписывает, а сообщает о конфликте (`factory doctor` показывает его же).
      Локальные копии скиллов фабрики в jobflow (`prd`, `issues`, `task-lifecycle` и т.д.)
      удаляются из git в Фазе 6 до перехода на копии из пакета;
    - setup-скрипт ведёт список установленных им копий (в файле из `.gitignore`) и удаляет копии,
      которых больше нет в профиле или пакете, — иначе Claude Code продолжит загружать устаревший
      скилл;
    - `postinstall` не меняет отслеживаемые файлы проекта, в том числе `.claude/settings.json` (в
      нём разрешения и хуки проекта). Записи хуков фабрики проект добавляет в свой
      `.claude/settings.json` сам; `factory doctor` проверяет, что они есть;
    - хук ссылается на скрипт в пакете через `CLAUDE_PROJECT_DIR` в shell form, как уже работает в
      jobflow: `node "$CLAUDE_PROJECT_DIR/node_modules/dark-factory/hooks/<hook>.js"`. Exec form
      (`command` + `args`) рекомендуется документацией, но раскрытие `${CLAUDE_PROJECT_DIR}` в
      `args` не проверено запуском; переход на неё — только после теста;
    - хуки-гейты (closure gate, skill gate, гейт тела issue) fail closed: если скрипт хука не найден
      или упал (например, пакет не установлен в свежем клоне), действие блокируется. В Claude Code
      блокирует только код выхода 2, а падение `node` даёт 1 и действие пропускает, поэтому запись
      хука-гейта превращает любой сбой в код 2. Хуки lint/typecheck остаются неблокирующими, как
      сейчас;
    - состав хуков ядра: closure gate (`git commit`/`git push` и тело issue для
      `gh issue create|edit` и `mcp__github__issue_write`), skill gate, skill marker (PostToolUse
      `Skill`, без него skill gate не видит загруженных скиллов), lint, typecheck;
    - хук находит профиль по фиксированному пути относительно `CLAUDE_PROJECT_DIR`; отдельного
      механизма передачи пути проекта нет.

## Ключевые инварианты

- **Ядро без литералов проекта.** В коде ядра нет путей, имён CI-проверок, логинов, моделей,
  номеров issue/ADR, доменных зон риска и команд конкретного проекта. Проверяется автоматически:
  тест ядра прогоняет Ralph и верификатор на двух фикстурных профилях (монорепо и один пакет).
- **Граница доверия ADR-041 сохраняется.** PR проекта не может изменить ни код верификатора (ядро
  закреплено по SHA/тегу и не берётся из `node_modules` проекта), ни его конфиг (читается с
  default-ветки). `OPENAI_API_KEY` — только в job, вызывающем модель.
- **Вердикт вычисляет код, fail closed** — как в ADR-041 и EPIC-27; невалидный профиль или конфиг —
  FAIL, не молчаливый дефолт.
- **Ralph: агент без git/gh** — принцип обоих проектов (ADR-001 cards, `.claude/ralph/README.md`
  jobflow) сохраняется в ядре.
- **Особенности проекта не теряются при выносе.** Каждая строка таблицы различий выше становится
  параметром профиля с текущим значением проекта; поведение jobflow и cards после перевода то же,
  что до.
- **Обновление ядра в проекте — только PR с явной сменой версии.** Никаких плавающих ссылок
  (`@main`, `latest`).
- **Расширение без правки ядра.** Новый шаг Ralph или новая проверка верификатора подключается
  регистрацией и настройкой в профиле; существующие шаги и проверки при этом не меняются. Новый
  элемент по умолчанию выключен и не меняет поведение проектов, пока профиль его не включит.
- **Независимость сторон EPIC-27** (скилл и верификатор связаны только контрактом) сохраняется и в
  пакете.
- **Один источник правила «путь → скиллы».** Skill gate хука и промпт Ralph читают одну и ту же
  таблицу профиля; второго списка скиллов в коде хука или Ralph нет.
- **Overlay проекта только добавляет.** Ни профиль, ни overlay не могут убрать базовую секцию
  шаблона, базовую секцию контракта issue, запрещённую формулировку или проверку хука ядра.
  Набор скиллов к этому правилу не относится: он целиком задаётся профилем.
- **Установка пакета не меняет отслеживаемые файлы проекта.** `postinstall` пишет только в
  копии, перечисленные в `.gitignore` по имени, и при конфликте имени с отслеживаемым файлом
  останавливается с сообщением; `.claude/settings.json`, `CLAUDE.md`, профиль и trusted-конфиги
  правит только проект.
- **Хуки-гейты fail closed.** Отсутствующий пакет, отсутствующий профиль или падение скрипта
  хука-гейта блокируют действие, а не пропускают его.
- **Контекст проекта не попадает в ядро.** Описание проекта, правила, секции шаблонов и списки
  скиллов живут в проекте (профиль, `CLAUDE.md`, overlay); текст скиллов и промптов ядра на них
  ссылается, но не содержит их.

## Технические ограничения

- `drop-sudo` в `openai/codex-action` можно выполнить один раз на job, пин v1.11 (ADR-041,
  амендмент ISSUE-449) переносится в reusable workflow без изменений.
- Reusable workflow не может сам подписаться на `workflow_run` проекта: обёртка на `workflow_run`
  остаётся в проекте.
- Формат пакета Claude Code проверен по документации Claude Code 2026-10-11 (страницы `hooks`,
  `headless`, `plugins/loading`, `plugins/manifest-reference`; запуском не проверялось):
  - хук получает `CLAUDE_PROJECT_DIR` — «корень проекта, где стартовала сессия». В клоне Ralph и
    в CI `claude` поэтому запускается из корня рабочей копии; это закрепляется тестом ядра, а не
    принимается на веру (для CI в документации отдельно не сказано);
  - для хуков с путём документация рекомендует exec form (`command` + `args`, без shell);
    раскрытие `${CLAUDE_PROJECT_DIR}` в `args` запуском не проверено, поэтому по умолчанию —
    shell form, как сейчас в jobflow. На Windows `.cmd`/`.bat`-обёртки из `node_modules/.bin` в
    exec form не запускаются, поэтому скрипт в любом случае вызывается через `node` напрямую;
  - хук, ссылающийся на `node_modules`, падает, если зависимости не установлены. Блокирует только
    код выхода 2, а падение `node` — код 1, то есть без явной обработки хук-гейт пропускает
    действие (fail open). Поэтому хуки-гейты переводят сбой в код 2 (п. 18 скоупа), а
    `factory doctor` дополнительно проверяет установку пакета;
  - хуки из `.claude/settings.json` проекта и из плагина объединяются, а не перекрывают друг
    друга; одинаковый обработчик из двух settings-файлов запускается один раз;
  - Claude Code plugin в `-p` без `--bare` загружается вместе со своими хуками, скиллами и
    агентами, но плагин, включённый только в проектном `.claude/settings.json`, на машине без
    установки не скачивается («enabled in project settings but isn't installed here»), а плагин из
    репозитория требует доверия к папке, которого `-p` не даёт. Для клонов Ralph и CI это
    дополнительная настройка на каждой машине — поэтому доставка через npm (п. 18 скоупа).
- Windows: владелец запускает Ralph и хуки на Windows (пути `D:\...`, инциденты `EBUSY`/`EPERM` в
  обоих README). Ядро обязано работать на Windows и Linux (CI).
- Тесты ядра — без сети и без реального AI (как `Testing Rules` обоих проектов).
- Перевод контракта issue меняет имена секций (например `Контекст` → `Context`). Линтер и
  верификатор должны принимать оба варианта в течение переходного периода, иначе issue, созданные
  до перевода, станут невалидными; как долго держать старые имена — решается в задаче перевода.
- Верификатор берёт скрипты из checkout фабрики по тегу, записанному в `package.json` проекта на
  default-ветке; тег из головы PR не используется (иначе PR мог бы подменить версию верификатора).
