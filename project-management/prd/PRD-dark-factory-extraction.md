# PRD: Dark Factory Extraction (EPIC-28)

**Дата**: 2026-09-26
**Статус**: Draft
**Затрагиваемое приложение**: ни одно из `apps/*`. Затрагивает репозиторную инфраструктуру двух
проектов (`strakhovdenya/jobflow-cv-pipeline`, `strakhovdenya/cards`) и новый репозиторий фабрики.
**Связанный issue/backlog-пункт**: новая фича — ещё не заведена как issue. Новый эпик **EPIC-28**,
следует за EPIC-27 (`PRD-verifiable-spec-and-independent-verifier.md`, issues #464–#489).

## Цель

Вынести всё, что относится к AI software factory (скиллы `prd`/`plan`/`issues`/`task-lifecycle`,
хуки, Ralph, Acceptance Verifier, контракт issue), в один переиспользуемый versioned-пакет, который
подключается к любому проекту — сначала к jobflow и cards — через конфигурацию, без копирования и
расхождения кода между проектами.

## Контекст и согласованность с проектом

Сравнение jobflow (HEAD `b3bf4f0`) и cards (HEAD `75ca9ae`, 2026-09-23), сделанное чтением обоих
репозиториев:

**Как фабрика попала в cards.** `cards/.claude/ralph/README.md` прямо пишет: «Механизм перенесён из
проекта `jobflow-cv-pipeline`». Копия разошлась: из 10 файлов `.claude/ralph/` ни один не совпадает
(например, `core.js` — 470 строк против 697, `workspace.js` — около 590 различающихся строк diff).

**Исправления уже переносились руками в обе стороны.** Оба проекта независимо лечили одни и те же
баги: обрезание первой строки `git status --porcelain` (`gitPorcelainStatus()` есть в обоих),
retry чтения при `DEL_RALPH` (`MARKER_READ_RETRY_DELAYS_MS` в jobflow, `READ_RETRY_DELAYS_MS` в
cards), синхронизация lockfile. В README cards записано: «Урок для переноса этого механизма в другой
проект…». Без общего ядра каждый урок придётся переносить вручную.

**Точки различия (будущие настройки профиля), найденные в коде:**

| Что | jobflow | cards |
|---|---|---|
| Структура | два приложения `apps/api`, `apps/web` (ADR-023) | один пакет в корне |
| Установка зависимостей в клоне | по приложению (`workspace.js`, цикл по `['apps/api','apps/web']`) | один `npm install` в корне |
| Гейт перед коммитом | `GATE_COMMANDS` по затронутым приложениям (`determineTouchedApps`) | `runVerificationChecks()`: `npm run check` + `npm run build` |
| Пропуск ревью для doc-only | нет отдельного гейта | `hasCodeChanges()` / `DOC_ONLY_PATH_PATTERNS` |
| Защищённые пути агента | `apps/api/prisma/prompts/**`, `apps/api/knowledge-sources/**` | `docs/**` (SQL-миграции Supabase) |
| Вердикт «нужен человек» | `BLOCKED-PROMPT-CHANGE`, лейбл `ralph-needs-prompt-change` | `BLOCKED-DB-CHANGE`, лейбл `ralph-needs-db-change` |
| Трекер tech-debt | `TECH_DEBT_TRACKER_ISSUE = 334` | `TECH_DEBT_TRACKER_ISSUE = 1` |
| Обязательные скиллы в issue | `API_SKILLS`/`WEB_SKILLS`, `missingRequiredSkills()` | нет |
| Ограничения окружения в промпте | нет docker/Postgres | прод на Vercel, общий Supabase, нет dev-сервера |

**Чего в cards нет совсем:** Acceptance Verifier (ADR-041), CodeQL в CI (в `ci.yml` три job:
`Check (lint + format + types)`, `Test (unit)`, `Build`), скиллы `task-lifecycle` и `epic-discovery`, skill gate. Скилл
`issues` короче (175 строк против 315) и без раздела о проверяемости для верификатора. Хук
`scripts/pre-commit-gate-hook.js` ловит `git commit` регулярным выражением по всей строке
(`/\bgit\s+commit\b/`) — это тот же класс бага, который в jobflow исправлен на разбор сегментов
команды (`echo git commit` перехватывался; PR #446).

Canonical-артефакты пайплайна CV не затрагиваются.

Связанные ADR jobflow: ADR-023 (монорепо `apps/*`), ADR-030 (issues как источник правды), ADR-035
(test evidence в комментариях), ADR-041 (верификатор), ADR-042 (EPIC-27, в работе). ADR cards:
ADR-001 (Ralph не мёрджит), ADR-002 (схема Supabase — только человек).

## Зависимости

- **EPIC-27 закрыт или закрыт по существу** (issues #464–#489). Выносить нужно отлаженную версию:
  контракт issue, заморозка спеки, детерминированные проверки. В EPIC-27 уже действует правило
  «никаких литералов проекта в коде фабрики», которое снижает объём переделки при выносе.
- Доступ сессии к `strakhovdenya/cards` на запись (сейчас только чтение).
- Новый репозиторий фабрики создан владельцем (см. «Открытые вопросы»).

## Пользовательские сценарии

Пользователь — владелец, ведущий несколько проектов.

- Владелец подключает фабрику к новому проекту: кладёт профиль и trusted-конфиги, подключает
  пакет по закреплённой версии, запускает `factory doctor` → получает список того, чего не хватает
  (лейблы, секрет, переменная модели, branch protection), и после исправления — рабочий цикл
  PRD → план → issues → Ralph → PR → верификатор.
- Владелец исправляет баг Ralph в репозитории фабрики → выпускает версию → каждый проект получает
  исправление PR-ом, поднимающим закреплённую версию, а не переносом кода руками.
- Владелец меняет промпт верификатора → эталонные наборы PR обоих проектов показывают, не
  появились ли ложные PASS.
- PR в проекте пытается изменить код верификатора или его конфиг → не может: ядро закреплено по
  версии, конфиг читается с default-ветки.

## В скоупе

1. **Репозиторий фабрики** с тремя частями: ядро верификатора, ядро Ralph, пакет Claude Code
   (скиллы, агенты, хуки). Versioned-релизы с changelog.
2. **Профиль проекта** — один файл с описанием особенностей проекта (структура приложений, команды
   установки и проверки, doc-only шаблоны, защищённые пути и соответствующий вердикт/лейбл,
   обязательные скиллы по путям, ограничения окружения для промпта агента, номер трекера
   tech-debt, ID Project, шаблон веток, язык скиллов, пути к PRD/планам/ADR) и JSON-схема профиля.
3. **Trusted-конфиги верификатора** в проекте (`owners`, `required-checks`, `allowed-models`,
   `tampering-scan`, контракт issue с overlay проекта) — формат из EPIC-27, закреплённый схемой.
4. **Верификатор как reusable workflow** (`workflow_call`) в репозитории фабрики, закреплённый по
   SHA; в проекте — обёртка на `workflow_run`.
5. **Ralph как пакет** с конфигом проекта; все точки различия из таблицы выше — параметры профиля.
6. **Скиллы, агенты и хуки** как пакет Claude Code; проектные значения (пути документов, ID
   Project, ADR) — из профиля, не из текста скилла.
7. **Контракт issue: ядро + overlay проекта.** Overlay может добавлять секции и запрещённые
   формулировки, но не убирать базовые.
8. **`factory doctor`** — проверка готовности проекта.
9. **Перевод jobflow на пакет** без изменения поведения (эталонный набор PR из EPIC-27 даёт те же
   вердикты).
10. **Подключение cards**: профиль, trusted-конфиги, верификатор, скиллы из пакета, Ralph из
    пакета; исправление бага подстрочного совпадения в хуке cards приходит вместе с общим хуком.
11. **Эталонный набор PR для cards** (минимум 3 случая) по формату EPIC-27.
12. **Документация фабрики**: как подключить проект, как обновить версию, как добавить точку
    настройки.
13. **Перевод текстов фабрики на английский**: скиллы `prd`/`plan`/`issues`/`task-lifecycle`/
    `epic-discovery`, агенты, промпты Ralph, README фабрики; контракт issue (имена секций) — с
    переходным периодом, см. «Технические ограничения».
14. **CodeQL в CI cards** и его включение в trusted-список обязательных проверок cards.

## Ключевые инварианты

- **Ядро без литералов проекта.** В коде ядра нет путей, имён CI-проверок, логинов, моделей,
  номеров issue/ADR, доменных зон риска и команд конкретного проекта. Проверяется автоматически:
  тест ядра прогоняет Ralph и верификатор на двух фикстурных профилях (монорепо и один пакет).
- **Граница доверия ADR-041 сохраняется.** PR проекта не может изменить ни код верификатора (ядро
  закреплено по SHA/тегу и не берётся из `node_modules` проекта), ни его конфиг (читается с
  default-ветки). `OPENAI_API_KEY` — только в job, вызывающем модель.
- **Вердикт вычисляет код, fail closed** — как в ADR-041 и EPIC-27; невалидный профиль или конфиг —
  FAIL, не молчаливый дефолт.
- **Ralph: агент без git/gh** — принцип обоих проектов (ADR-001 cards, `.claude/ralph/README.md`
  jobflow) сохраняется в ядре.
- **Особенности проекта не теряются при выносе.** Каждая строка таблицы различий выше становится
  параметром профиля с текущим значением проекта; поведение jobflow и cards после перевода то же,
  что до.
- **Обновление ядра в проекте — только PR с явной сменой версии.** Никаких плавающих ссылок
  (`@main`, `latest`).
- **Независимость сторон EPIC-27** (скилл и верификатор связаны только контрактом) сохраняется и в
  пакете.

## Технические ограничения

- `drop-sudo` в `openai/codex-action` можно выполнить один раз на job, пин v1.11 (ADR-041,
  амендмент ISSUE-449) переносится в reusable workflow без изменений.
- Reusable workflow не может сам подписаться на `workflow_run` проекта: обёртка на `workflow_run`
  остаётся в проекте.
- Формат пакета Claude Code (plugin: состав, подключение, как хуки получают путь проекта) нужно
  подтвердить по документации Claude Code на этапе issue — в этом PRD он не проверялся.
- Windows: владелец запускает Ralph и хуки на Windows (пути `D:\...`, инциденты `EBUSY`/`EPERM` в
  обоих README). Ядро обязано работать на Windows и Linux (CI).
- Тесты ядра — без сети и без реального AI (как `Testing Rules` обоих проектов).
- Перевод контракта issue меняет имена секций (например `Контекст` → `Context`). Линтер и
  верификатор должны принимать оба варианта в течение переходного периода, иначе issue, созданные
  до перевода, станут невалидными; как долго держать старые имена — решается в задаче перевода.
- Верификатор берёт скрипты из checkout фабрики по тегу, записанному в `package.json` проекта на
  default-ветке; тег из головы PR не используется (иначе PR мог бы подменить версию верификатора).

## Критерии готовности (Acceptance Criteria)

*(Эпик не описан в `docs/05_epics.md`; все пункты добавлены этим PRD.)*

- [ ] В репозитории фабрики есть ядро верификатора, ядро Ralph и пакет скиллов/агентов/хуков;
      тесты ядра зелёные в CI фабрики на Linux и Windows.
- [ ] JSON-схема профиля проекта описывает каждую точку различия из таблицы «Контекст»; невалидный
      профиль отклоняется с сообщением, называющим поле.
- [ ] Тест ядра прогоняет Ralph-контроллер (с подменённым агентом) и верификатор (с фикстурным
      отчётом модели) на двух профилях — монорепо и один пакет — без изменения кода ядра.
- [ ] Поиск по коду ядра не находит `apps/api`, `apps/web`, `jobflow`, `cards`, `supabase`,
      `prisma` вне фикстур тестов и примеров профилей, а `strakhovdenya` — вне метаданных пакета
      (`package.json`, README).
- [ ] Верификатор подключается к проекту обёрткой на `workflow_run`, вызывающей reusable workflow
      фабрики по SHA; скрипты верификатора берутся из checkout фабрики, не из проекта.
- [ ] Контракт issue: overlay проекта, удаляющий базовую секцию или запрещённую формулировку,
      отклоняется линтером.
- [ ] `factory doctor` сообщает об отсутствующих: профиле, trusted-конфигах, лейблах
      (`spec-approved`, `manual-verified`, `factory-cross-change`, лейблы блокировки Ralph),
      секрете `OPENAI_API_KEY`, переменной `VERIFIER_MODEL`, обёртке верификатора.
- [ ] jobflow переведён на пакет: локальные копии скиллов, хуков, Ralph и скриптов верификатора
      удалены или заменены ссылкой на пакет; эталонный набор PR jobflow даёт те же вердикты, что до
      перевода.
- [ ] cards подключён: профиль с параметрами из таблицы «Контекст», верификатор, скиллы и Ralph из
      пакета; `echo git commit` в Bash не перехватывается хуком cards (тест).
- [ ] Эталонный набор cards содержит минимум 3 PR с ожидаемыми вердиктами.
- [ ] CI cards содержит CodeQL, и он входит в trusted-список обязательных проверок cards.
- [ ] Скиллы, агенты, промпты Ralph и README фабрики написаны по-английски; линтер принимает и
      русские, и английские имена секций контракта (тест).
- [ ] Документация фабрики описывает подключение проекта, обновление версии и добавление новой
      точки настройки; в обоих проектах есть ссылка на неё.

## Открытые вопросы

Все решены с владельцем 2026-09-26 (переносить в `Key Invariants` задач как `Resolved decision`):

1. **Где живёт фабрика:** отдельный репозиторий `strakhovdenya/dark-factory` (создаёт владелец).
   jobflow и cards — равные потребители. Отвергнуто: каталог внутри jobflow.
2. **Доставка кода фабрики** (Ralph, скрипты верификатора, хуки): npm-зависимость из GitHub по
   тегу (`"dark-factory": "github:strakhovdenya/dark-factory#vX.Y.Z"`); обновление — смена тега в PR.
   Верификатор берёт свои скрипты не из `node_modules` проекта, а из checkout репозитория фабрики по
   тому же тегу. Отвергнуто: vendoring скриптом, git submodule.
3. **Скиллы, агенты, хуки Claude Code:** раскладываются setup-скриптом на `postinstall` (как сейчас
   `setup-metaskills.js`), работают в клонах Ralph и в CI. Отвергнуто: Claude Code plugin — не
   проверен для неинтерактивного `claude -p`.
4. **Язык:** тексты фабрики (скиллы, промпты Ralph, README и руководства фабрики) переводятся на
   английский. Проектные документы (ADR, PRD, `CLAUDE.md`, уже созданные issue) не переводятся.
   Следствие: новые PRD, планы и issue скиллы будут писать по-английски. Отвергнуто: оставить
   русский; язык как настройка профиля с двумя наборами текстов.
5. **cards:** верификатор подключается в режиме advisory, как в jobflow; в CI cards добавляется
   CodeQL и входит в trusted-список обязательных проверок cards. Владелец заводит в cards секрет
   `OPENAI_API_KEY` и переменную `VERIFIER_MODEL`.
6. **Порядок:** эпик начинается после закрытия EPIC-27; выносится уже отлаженная версия.
