# PRD: Verifiable Spec and Independent Verifier (EPIC-27)

**Дата**: 2026-09-26
**Статус**: Draft
**Затрагиваемое приложение**: ни одно из `apps/*` — репозиторная инфраструктура AI software
factory: `.claude/skills/issues/`, `.claude/ralph/`, `scripts/`, `.github/verifier/`,
`.github/workflows/`, `docs/12_ai_software_factory.md`, `project-management/DECISIONS.md`
**Связанный issue/backlog-пункт**: новая фича — ещё не заведена как issue. Новый эпик
**EPIC-27**, в `docs/05_epics.md` пока не описан (см. «Документация, которую потребуется обновить»).
Смежная открытая issue: #452 (вернуть `openai/codex-action` на исправленную версию) — не
дублируется, остаётся отдельной.

## Цель

Сделать две половины фабрики (`issues`-скилл, который пишет спеку, и Acceptance Verifier, который
принимает PR по этой спеке) независимыми и связанными только общим машинно-проверяемым контрактом:
спека проверяема по построению и не может быть изменена исполнителем после одобрения, а всё, что
можно решить кодом, решает код, а не модель.

## Контекст и согласованность с проектом

Источник: анализ `issues`-скилла и верификатора в сессии 2026-09-26. Подтверждено чтением кода:

- Верификатор читает **текущее** тело issue (`gh issue view` в `.github/workflows/acceptance-verifier.yml`,
  шаг `Collect inputs`), а `issues`-скилл («Формат Issue» → `## Affects») велит исполнителю по ходу
  работы расширять `Affects` через `gh issue edit`; контроллер Ralph сам правит тело issue
  (`checkOffAcceptanceCriteria` в `.claude/ralph/github.js`). Спека мутабельна для стороны, которую
  по ней проверяют.
- Лейбл `manual-verified` засчитывается по факту наличия (`Compute verdict and comment`), без
  проверки того, кто его поставил.
- Полнота отчёта проверяется только по числу пунктов (`countIssueItems`/`checkCoverage` в
  `scripts/acceptance-verdict.js`); текст пункта в отчёте пишет модель.
- `out_of_scope_files` составляет модель; ADR-041 (амендмент ISSUE-443, п. 3) сам называет
  детерминированное сравнение с `## Affects` «possible later hardening».
- CI-провалы проверяются по принципу «нет упавших = ок»; отсутствие обязательной проверки ловится
  только для хардкоднутого CodeQL (`parseCiFailures`).
- Формат issue описан в трёх местах: прозой в `.claude/skills/issues/SKILL.md`, в
  `.github/verifier/prompt.md` и регулярными выражениями в `countIssueItems`.
- Хук на `gh issue create|edit` (`scripts/git-closure-gate-hook.js`) проверяет только, что скилл
  `issues` загружен, но не качество тела.
- Ослабление тестов (`test_tampering`) определяет только модель.

Canonical-артефакты пайплайна (00–05, cover_letter) не затрагиваются.

Связанные ADR:
- ADR-030 — GitHub Issues как источник правды для задач; этот эпик ужесточает их формат.
- ADR-035 — test evidence как комментарий на issue; не меняется.
- ADR-041 и его амендменты — независимый верификатор, вердикт вычисляет скрипт, fail closed,
  файлы верификатора берутся с default-ветки. Эпик продолжает ADR-041, не отменяет ни одного его
  пункта; новые правила оформляются новым ADR-042 (см. «Документация»).
- ADR-025 — epic base branch; для этого эпика не рекомендуется (см. последний раздел).

## Пользовательские сценарии

Пользователь здесь — владелец проекта, управляющий фабрикой.

- Владелец просит завести issue → скилл пишет тело с ID пунктов и способом проверки каждого,
  независимый ревьюер спеки ищет непроверяемые и «формально выполнимые» пункты, линтер проверяет
  формат → `gh issue create` проходит только с валидным телом.
- Владелец ставит на issue лейбл `spec-approved` → workflow фиксирует хеш тела; Ralph берёт в работу
  только одобренные issue.
- Исполнитель (Ralph или интерактивная сессия) правит тело одобренной issue → верификатор ставит
  FAIL «spec changed after approval», пока владелец заново не поставит `spec-approved`.
- Агент ставит `manual-verified` или `spec-approved` сам → лейбл не засчитывается.
- PR трогает файл, которого нет в `## Affects` → FAIL вычисляет скрипт, а не модель.
- Обязательная CI-проверка не запустилась или ещё идёт → FAIL.
- В диффе появился `.only`/`.skip`/понижение `coverageThreshold` → FAIL от сканера, независимо от
  мнения модели.
- Модель дала FAIL по семантическому пункту → второй независимый прогон; при расхождении вердикт
  `NEEDS_HUMAN`, не PASS.
- Ralph выполняет issue со скрытыми сценариями → агент их не видит, CI гоняет их на PR и роняет
  вердикт при провале.
- Владелец меняет промпт верификатора → прогоняет эталонный набор прошлых PR и видит, не появилось
  ли ложных PASS.

## В скоупе

**A. Общий контракт issue.**
1. Один файл-контракт формата issue, на который ссылаются и скилл, и верификатор; ни один из них не
   дублирует правила формата у себя.
2. Стабильные ID у каждого проверяемого пункта: `AC-n`, `DOD-n`, `TR-n`, `INV-n`.
3. Тип пункта (`behavior`, `doc`, `config`, `ci`, `absence`) и способ проверки (`Verify:`) у каждого
   пункта `AC`/`DOD`/`TR`.
4. Детерминированный линтер тела issue (`scripts/issue-lint.js`) с unit-тестами.

**B. Скилл пишет по контракту.**
5. Шаблон и правила `issues`-скилла приведены к контракту: убран мета-пункт DoD «Acceptance
   Criteria выше выполнены», условные пункты разрешаются при создании, в DoD — имена CI-проверок.
6. Правило негативных сценариев: у каждого `behavior`-пункта есть хотя бы один негативный или
   граничный случай в форме Given/When/Then.
7. Шаг независимого ревью спеки (агент со свежим контекстом) перед `gh issue create`.
8. Хук на `gh issue create|edit` блокирует тело, не прошедшее линтер.

**C. Верификатор проверяет по контракту.**
9. Предварительный шаг в `verify`: линтер тела issue; невалидная спека — FAIL без вызова модели.
10. В схеме отчёта обязательный `id` пункта; скрипт требует точного совпадения множества ID с issue и
    берёт текст пункта из issue, а не из отчёта.
11. Каждый `INV-n` получает явный статус (`PASS`/`FAIL`/`N/A`).
12. Ссылки получают `kind` (`impl`, `test`, `doc`, `config`); PASS по `behavior`-пункту требует
    ссылок `impl` и `test`.
13. Пункты типов `ci` и `absence` решает скрипт (по `ci.json` и по checkout), а не модель.
14. Переходный режим для issue без ID: проверка по старому пути (подсчёт пунктов) с пометкой
    «legacy format» в комментарии.

**D. Спека заморожена, лейблы авторизованы.**
15. Лейбл `spec-approved`: при его установке workflow сохраняет хеш нормализованного тела issue.
16. Верификатор сравнивает хеш текущего тела с зафиксированным; расхождение — FAIL.
17. `spec-approved` и `manual-verified` засчитываются, только если их поставил владелец из списка.
18. Ralph берёт в работу только issue с действующим `spec-approved`.
19. Скилл и task-lifecycle больше не велят исполнителю расширять `Affects` самому: расширение
    скоупа — через владельца и повторное одобрение.

**E. Детерминированные проверки вместо модели.**
20. Сравнение изменённых файлов с путями и glob-шаблонами `## Affects` — в скрипте; список модели
    становится подсказкой.
21. Обязательные проверки берутся из trusted-списка на default-ветке; каждая должна быть и быть
    `success`.
22. Сканер ослабления тестов по диффу; модель остаётся вторым слоем.

**F. Надёжность и аудит вердикта (P2).**
23. Происхождение в комментарии верификатора: head SHA, хеш тела issue, коммит промпта/схемы/скрипта,
    модель, версия Codex CLI.
24. Второй независимый прогон модели (отдельный job) только когда FAIL вызван пунктами, которые
    судила модель, или невалидным отчётом; расхождение прогонов — вердикт `NEEDS_HUMAN`.
25. `VERIFIER_MODEL` обязан входить в trusted-список разрешённых моделей
    (`.github/verifier/allowed-models.json`); смена модели идёт через PR.
26. Эталонный набор прошлых PR с ожидаемыми вердиктами и ручной workflow, прогоняющий на нём текущий
    промпт; отчёт считает ложные PASS и ложные FAIL.
27. Метрики качества спек: доля `UNVERIFIABLE` и число перезапусков верификатора на issue.

**G. Holdout-сценарии для Ralph (P2).**
28. Каталог скрытых сценариев в этом же репозитории, по номеру issue.
29. Контроллер Ralph убирает этот каталог из клона агента и не даёт ему попасть в коммит агента.
30. CI-job запускает сценарии issue с default-ветки против головы PR; его провал роняет вердикт.

**H. Разделение сторон.**
31. CI-проверка: PR не может одновременно менять сторону спеки (`issues`-скилл, контракт,
    `issue-lint.js`) и сторону верификатора (`.github/verifier/**`, `acceptance-verdict.js`,
    `acceptance-verifier.yml`) без отдельного лейбла владельца.

## Ключевые инварианты

- **Вердикт вычисляет код** (ADR-041 п. 2). Новые проверки добавляют причины FAIL в скрипт; модель
  не получает поля вердикта. `NEEDS_HUMAN` — не PASS.
- **Fail closed.** Отсутствующий или нечитаемый вход новой проверки (хеш спеки, список обязательных
  проверок, результат линтера, отчёт второго прогона) — FAIL, никогда не молчаливый пропуск.
- **Файлы верификатора — только с default-ветки** (ADR-041, амендмент ISSUE-424 п. 1): контракт,
  линтер, сканер, список владельцев и holdout-сценарии, которые исполняет CI, читаются из trusted
  checkout, а не из головы PR.
- **Ключ OpenAI — только в job, который вызывает модель**; job с правом записи в PR ключа не имеет.
  Второй прогон — отдельный job с тем же ограничением.
- **Недоверенные значения** (тело issue, ветка, пути из `## Affects`, пути из отчёта модели) доходят
  до shell только через `env:`, до файловой системы — только с проверкой containment (корневой
  `CLAUDE.md`, Security Rules). Glob из `## Affects` — данные, не код.
- **Хеш спеки не ломается от отметки чекбоксов.** Контроллер Ralph отмечает `- [ ]` → `- [x]`;
  нормализация тела перед хешированием должна это учитывать, иначе каждый DONE Ralph будет давать
  «spec changed».
- **Авторство лейбла проверяется по событиям timeline**, не по наличию лейбла; бот и токен агента
  не являются владельцем.
- **Независимость сторон.** Скилл не читает промпт верификатора, верификатор не читает скилл; общий
  у них только контракт.
- **Обратная совместимость переходного режима.** Issue без ID продолжают проверяться; ни одна
  открытая issue не становится непроверяемой из-за этого эпика.
- **Пин `openai/codex-action`** и комментарий к нему (ADR-041, амендмент ISSUE-449) сохраняются в
  любом job, вызывающем модель.
- **Бутстрап:** PR, меняющий файлы верификатора, судится версией с default-ветки (ADR-041); это
  ожидаемо и не является дефектом фазы.

## Технические ограничения

- `drop-sudo` в codex-action можно выполнить один раз на job — второй прогон возможен только
  отдельным job (ADR-041, амендмент ISSUE-449 п. 4).
- `workflow_run`-job не привязан к PR: результаты публикуются комментарием и commit status
  `Acceptance Verifier`.
- Скрипты — CommonJS без зависимостей, тесты — `scripts/*.spec.js`, запускаются `npm run test:scripts`
  (CI-проверка `Test (scripts)`).
- `GITHUB_TOKEN` не читает classic branch protection, поэтому список обязательных проверок задаётся
  trusted-файлом (см. «Открытые вопросы»).
- Хук скилл-гейта не видит правки через shell (ограничение CLAUDE.md); хук на `gh issue create|edit`
  видит только вызовы через Bash tool; вызовы GitHub MCP нужно добавить в matcher хука.

## Критерии готовности (Acceptance Criteria)

*(Эпик не описан в `docs/05_epics.md`; все пункты добавлены этим PRD по результатам анализа
2026-09-26.)*

**Контракт и линтер**
- [ ] Существует один файл-контракт формата issue; `.claude/skills/issues/SKILL.md` и
      `.github/verifier/prompt.md` ссылаются на него и не содержат собственного описания формата
      секций и ID.
- [ ] `scripts/issue-lint.js` отклоняет тело без обязательных секций, без ID, с повторяющимися ID, с
      пунктом `AC`/`DOD`/`TR` без типа или без `Verify:`, с условным пунктом и с запрещёнными
      формулировками вне `## Manual verification (owner, not gated)`; каждый случай покрыт тестом в
      `scripts/issue-lint.spec.js`.
- [ ] Хук на `gh issue create|edit` и на создание/правку issue через GitHub MCP блокирует тело, не
      прошедшее линтер; поведение покрыто тестом.

**Скилл**
- [ ] Шаблон скилла не содержит мета-пункта «Acceptance Criteria выше выполнены» и условных пунктов;
      DoD называет CI-проверки по имени.
- [ ] Скилл требует негативный или граничный Given/When/Then-случай у каждого `behavior`-пункта и
      описывает шаг независимого ревью спеки перед созданием issue.
- [ ] Скилл и `task-lifecycle` не предписывают исполнителю править `## Affects`; расширение скоупа
      идёт через владельца и повторный `spec-approved`.

**Верификатор**
- [ ] Невалидная по линтеру спека даёт FAIL без вызова модели.
- [ ] Отчёт с множеством ID, не равным множеству ID issue, даёт FAIL; текст пунктов в комментарии
      берётся из issue.
- [ ] Каждый `INV-n` присутствует в отчёте со статусом `PASS`/`FAIL`/`N/A`.
- [ ] PASS по `behavior`-пункту без ссылки `impl` и ссылки `test` даёт FAIL.
- [ ] Пункты `ci` и `absence` решаются скриптом; модель по ним не судит.
- [ ] Issue без ID проверяется по старому пути, комментарий помечен «legacy format».

**Заморозка и лейблы**
- [ ] Установка `spec-approved` владельцем фиксирует хеш нормализованного тела; изменение тела
      после этого даёт FAIL «spec changed after approval»; отметка чекбоксов этого не вызывает.
- [ ] `spec-approved` и `manual-verified`, поставленные не владельцем из trusted-списка, не
      засчитываются.
- [ ] Ralph не берёт в работу issue без действующего `spec-approved`.

**Детерминированные проверки**
- [ ] Изменённый файл вне путей и glob-шаблонов `## Affects` даёт FAIL, вычисленный скриптом.
- [ ] Отсутствующая, незавершённая или неуспешная проверка из trusted-списка обязательных проверок
      даёт FAIL; хардкод CodeQL в `parseCiFailures` заменён этим списком.
- [ ] Сканер ослабления тестов ловит как минимум `.only`, `.skip`/`xit`/`xdescribe`, понижение
      `coverageThreshold`, добавленные `eslint-disable`/`@ts-ignore`/`@ts-expect-error`,
      `continue-on-error` и `if: false` в workflow и уменьшение числа `expect(` в spec-файле.

**P2**
- [ ] Комментарий верификатора содержит head SHA, хеш тела issue, коммит файлов верификатора,
      модель и версию Codex CLI.
- [ ] Второй прогон выполняется только при FAIL от модельных пунктов или невалидном отчёте; при
      расхождении прогонов вердикт `NEEDS_HUMAN`, commit status не `success` при
      `VERIFIER_ENFORCE=true`.
- [ ] `VERIFIER_MODEL`, отсутствующий в `.github/verifier/allowed-models.json`, даёт FAIL.
- [ ] Эталонный набор содержит как минимум PR #434, #446 и #463 с ожидаемыми вердиктами; ручной
      workflow прогоняет на нём текущий промпт и выводит ложные PASS/FAIL.
- [ ] Скрипт по запросу выводит по каждой issue долю `UNVERIFIABLE` и число прогонов верификатора,
      собирая их из комментариев верификатора через GitHub API.
- [ ] Holdout-сценарии issue отсутствуют в клоне агента Ralph и не попадают в его коммит; CI-job
      исполняет их с default-ветки, и его провал даёт FAIL вердикта.

**Разделение и документация**
- [ ] PR, одновременно меняющий сторону спеки и сторону верификатора без лейбла владельца, получает
      красную CI-проверку.
- [ ] ADR-042 описывает контракт, заморозку, авторизацию лейблов, `NEEDS_HUMAN` и holdout;
      `docs/12_ai_software_factory.md` и `docs/05_epics.md` (EPIC-27) обновлены.

## Открытые вопросы

Всё решено с владельцем 2026-09-26 (перенести в `Key Invariants` соответствующих issue как
`Resolved decision`):
- Скоуп: всё, включая P2.
- Заморозка: лейбл `spec-approved` + хеш; повторное одобрение — повторной установкой лейбла.
- Линтер: в хуке `gh issue create|edit` и как preflight в `verify`.
- Старые issue: переходный режим.
- Holdout: в этом же репозитории, скрыты только от Ralph.
- Второй прогон: только при FAIL от модели; расхождение — `NEEDS_HUMAN`.

- Хеш одобренной спеки хранится в маркированном комментарии `github-actions[bot]` на issue;
  удалённый или отсутствующий комментарий — FAIL.
- Список владельцев для авторизации лейблов — trusted-файл в `.github/verifier/` на default-ветке
  (под CODEOWNERS).
- Список обязательных CI-проверок — trusted-файл в `.github/verifier/` на default-ветке; он заменяет
  хардкод CodeQL в `parseCiFailures`. `GITHUB_TOKEN` не читает classic branch protection, поэтому
  сверку файла с настройками ветки владелец делает вручную.
- Хук `gh issue create|edit` расширяется на создание/правку issue через GitHub MCP; окончательный
  гарант валидности спеки — preflight-линтер в `verify`.
- Модель верификатора: `VERIFIER_MODEL` сейчас `gpt-6-luna` (псевдоним, наличие датированной версии
  не подтверждено), поэтому вместо требования snapshot — trusted-список разрешённых моделей. Обновление модели
  провайдером под тем же именем этим не ловится — ограничение принято.
- Метрики (п. 27) собирает скрипт по запросу из комментариев верификатора через GitHub API, без
  отдельного хранилища.

Открытых вопросов не осталось.

## Предполагаемое дробление на подзадачи (только если это эпик)

Порядок важен: каждая следующая тема опирается на контракт из первой.

1. **Контракт issue и линтер** — файл-контракт, ID, типы пунктов, `issue-lint.js` с тестами
   (AC «Контракт и линтер», кроме хука).
2. **Скилл по контракту** — шаблон, негативные сценарии, ревью спеки, хук на `gh issue create|edit`
   (AC «Скилл», хук).
3. **Верификатор по контракту** — preflight-линтер, `id`/`kind` в схеме, `INV`, `ci`/`absence`
   скриптом, legacy-режим (AC «Верификатор»).
4. **Заморозка спеки и авторизация лейблов** — `spec-approved`, хеш, авторство лейблов, фильтр Ralph,
   правка скилла про `Affects` (AC «Заморозка и лейблы», последний пункт «Скилл»).
5. **Детерминированные проверки** — `Affects`, обязательные проверки, сканер тестов (AC
   «Детерминированные проверки»).
6. **Надёжность вердикта** — provenance, второй прогон и `NEEDS_HUMAN`, список разрешённых моделей (AC P2
   первые три).
7. **Эталонный набор и метрики** — golden set PR, ручной workflow, метрики (AC P2 четвёртый и
   пятый).
8. **Holdout-сценарии для Ralph** (AC P2 последний).
9. **Разделение сторон и документация** — CI-проверка разделения, ADR-042, docs (AC «Разделение и
   документация»).

Epic base branch (ADR-025) **не рекомендуется**: файлы верификатора читаются с default-ветки
(`workflow_run`), поэтому каждая фаза начинает защищать следующие PR только после мержа в `main`;
переходный режим держит `main` согласованным после каждой фазы.
