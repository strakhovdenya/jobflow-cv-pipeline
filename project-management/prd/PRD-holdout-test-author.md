# PRD: Holdout Test Author — скрытые от Ральфа тесты, которые пишет отдельный агент

**Дата**: 2026-10-11
**Статус**: Draft (отложено; к работе не берётся, пока владелец не снимет отметку)
**Затрагиваемое приложение**: ни одно из `apps/*`. Затрагивает фабрику (Ralph, Acceptance Verifier, CI). Реализуется в репозитории `strakhovdenya/dark-factory` после EPIC-28, а не в jobflow.
**Связанный issue/backlog-пункт**: #485, #486, #487 (бывшая Фаза 8 EPIC-27, перенесены сюда); тесты пишет новый агент — ещё не заведён как issue.

## Цель

Дать независимую от исполнителя проверку результата Ральфа: тест, который не видел агент, пока писал код, запускается в CI против его PR. Тест пишет не Ральф и не владелец вручную, а отдельный агент со своими правилами и контекстом, а владелец проверяет результат до запуска Ральфа.

## Контекст и согласованность с проектом

**Слой.** Фабрика: контроллер Ральфа (`.claude/ralph/`, после EPIC-28 — ядро Ральфа в `dark-factory`), CI-workflow, trusted-конфиги `.github/verifier/`. Артефакты пайплайна CV (`00_`…`05_`) не затрагиваются.

## Пользовательские сценарии

- Владелец помечает issue меткой (имя метки — открытый вопрос) → контроллер запускает автора тестов → в main приходит PR с `.holdout/ISSUE-<n>/` → владелец проверяет и мёрджит.
- После мёрджа Ральф берёт issue; в его клоне каталога `.holdout/` нет; агент-реализатор о тестах не знает.
- На PR Ральфа CI запускает сценарии с default-ветки; падение любого роняет вердикт верификатора.
- Владелец видит, что тест некорректен (падает на правильном решении) → правит его или отклоняет PR автора.

## В скоупе

1. Формат каталога `.holdout/ISSUE-<n>/`, `manifest.json` и `.holdout/runners.json`, валидатор и построитель плана запуска (бывший #485).
2. Сокрытие `.holdout/` от клона реализатора без попадания удаления в его коммит (бывший #486).
3. CI-job `Holdout scenarios`, берущий сценарии с default-ветки, и запись в trusted-список обязательных проверок (бывший #487).
4. **Агент-автор тестов** (новое): отдельный шаг конвейера Ральфа со своим промптом, правами и клоном; вход — тело issue и документация, выход — PR в main с `.holdout/ISSUE-<n>/`.
5. Шлюз «тест одобрен владельцем и смёржен» между шагом автора и запуском реализации.
6. Включение по метке на issue, а не для всех задач.

## Ключевые инварианты

- Сценарий пишется вне клона, сессии и ветки реализатора и коммитится в main до того, как Ральф взял issue; сокрытие каталога защищает только запущенного агента (INV-8 бывшего #485).
- Автор тестов не видит работы реализатора, а реализатор не видит тестов.
- CI читает манифест, сценарии, `runners.json` и скрипт планирования только с default-ветки (ADR-041).
- Job `Holdout scenarios` без секретов, `permissions: contents: read`, команды запускаются массивами аргументов.
- Пути из манифеста — недоверенные данные: абсолютные пути и `..` запрещены, `target` проверяется по шаблонам из `runners.json`.
- Никаких литералов проекта в коде фабрики: пути приложений, раннеры, имена проверок читаются из `.holdout/runners.json`, `.github/verifier/*.json` или профиля (инвариант EPIC-27, подтверждён EPIC-28).
- Автор тестов тестирует поведение на публичной границе (контракты из issue), а не внутренние имена, которых реализация ещё не создала: иначе тест падает на правильном решении.
- **Точка вариативности:** шаг конвейера Ральфа «автор тестов» и раннеры тестов. Меняются через существующие границы EPIC-28: реестр шагов конвейера Ральфа и `.holdout/runners.json`. Новая абстракция не вводится; правило добавления шага — из PRD EPIC-28.

## Технические ограничения

- Агент-автор использует провайдерную абстракцию фабрики, а не SDK напрямую; тесты фабрики — с подменённым агентом, без реальных AI-вызовов.
- Шаг делится на два прогона с паузой на владельца (PR в main нужно смёржить до реализации); одним непрерывным прогоном это не сделать.
- Дополнительный запуск модели на issue: включение только по метке.
- Windows: владелец запускает Ральфа на Windows; клон и sparse-checkout проверять там.

## Критерии готовности (Acceptance Criteria)

- [ ] Формат `.holdout/ISSUE-<n>/manifest.json` и `.holdout/runners.json` описан в `.holdout/README.md`; валидатор отклоняет `source` вне каталога issue, абсолютные пути, `..` и `target` вне шаблонов.
- [ ] План запуска строится для каждого раннера из `runners.json` без зашитых путей приложений.
- [ ] Контроллер Ральфа убирает `.holdout/` из рабочего дерева клона реализатора; сразу после подготовки клона `git status --porcelain` пуст, а `git add -A` и коммит агента не включают `.holdout/`.
- [ ] CI-job `Holdout scenarios` берёт сценарии с default-ветки, копирует их в `target` поверх головы PR и исполняет по плану; ненулевой код любой команды плана роняет job.
- [ ] Для ветки без номера issue и для issue без каталога сценариев job успешен и печатает `no holdout scenarios`.
- [ ] `Holdout scenarios` входит в trusted-список обязательных проверок: провал или отсутствие роняет вердикт верификатора.
- [ ] Агент-автор тестов запускается как отдельный шаг конвейера Ральфа по метке на issue, в отдельном клоне, с промптом, ограничивающим вход телом issue и документацией.
- [ ] Результат агента-автора приходит PR в main; запуск реализации невозможен, пока PR не смёржен.
- [ ] Тест фабрики с подменённым агентом проверяет: автор не получает дифф реализатора, реализатор получает клон без `.holdout/`.
- [ ] Коды фабрики не содержат литералов проекта (пути приложений, имена CI-проверок, логины, раннеры).
- [ ] ADR о holdout и авторе тестов записан в `DECISIONS.md` (новый ADR или амендмент ADR-042 — открытый вопрос); `docs/12_ai_software_factory.md` обновлён.

## Test Requirement (набросок)

- Unit-тесты валидатора и планировщика (`node --test`), включая негативные пути и сопоставление `*`/`**`.
- Тесты контроллера Ральфа с подменённым агентом: сокрытие каталога, отсутствие каталога в коммите, шлюз «PR автора смёржен».
- CI-проверка `Holdout scenarios` на PR без сценариев.
- Ручная проверка владельцем: тестовая issue с заведомо падающим сценарием, `Holdout scenarios` краснеет, верификатор даёт FAIL. Не gated.

4. Как оценивать качество тестов автора: golden-набор в духе EPIC-31 или только ревью владельца?
5. Что делать, если реализация правильная, а тест автора ложно падает: правка теста новым PR в main или переопределение владельцем?
