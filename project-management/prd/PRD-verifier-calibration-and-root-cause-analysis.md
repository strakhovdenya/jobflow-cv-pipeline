# PRD: Калибровка фабрики — разбор первопричин вердиктов верификатора (EPIC-31)

**Дата**: 2026-09-30
**Статус**: Draft
**Затрагиваемое приложение**: ни одно из `apps/*` — репозиторная инфраструктура AI software
factory (`.github/verifier/`, `.github/workflows/`, `scripts/`, документация фабрики)
**Связанный issue/backlog-пункт**: новая фича — ещё не заведена как issue. Смежные: #483 (golden
set, закрыт), #484 (скрипт метрик верификатора, открыт — зависимость), EPIC-30
(`PRD-ralph-verifier-loop-and-gated-automerge.md`, не заведён), EPIC-28 (трекер #491).

## Цель

**При корректно поставленной и корректно выполненной задаче верификатор почти всегда даёт PASS,
а при некорректной реализации почти всегда даёт FAIL.**

Сейчас почти каждый PR получает FAIL, и непонятно, кто в этом виноват: issue, исполнитель,
верификатор или инфраструктура. Фича превращает каждый вердикт в измеримый ответ на вопрос «что
чинить». Независимый Calibration Judge классифицирует первопричину по фиксированной таксономии.
Владелец подтверждает разбор, а расширенный golden-набор измеряет ошибки верификатора в обе
стороны. Изменения issue-контракта, скилла `issues`, промпта или детерминированного слоя
верификатора делаются по данным, а не по ощущениям.

Цель — не «больше PASS». Метрика всегда состоит из пары «ложный PASS / ложный FAIL», и ложный
PASS весит больше.

**Реальный флоу работы — несколько кругов на один PR.** Верификатор дал вердикт → владелец
читает отчёт → ИИ получает отчёт и исправляет код (тело issue — крайне редко и только с апрувом
владельца, через переутверждение `spec-approved`) → пуш → верификатор перезапускается.
Верификатор задуман как список ошибок, которые надо исправить. Но сейчас он находит новые ошибки
и на 2-м, и на 3-м круге, и PR не сходится. Поэтому единица анализа — **круг** (один прогон
верификатора), а не PR. Главный вопрос калибровки: называет ли верификатор все настоящие ошибки
на первом круге, или они всплывают по одной.

## Контекст и согласованность с проектом

## Пользовательские сценарии

- Верификатор завершил прогон на PR `task/ISSUE-<n>-*` → Calibration Judge автоматически
  разбирает этот круг, и в PR обновляется отдельный комментарий: первопричина, ответственный
  компонент, контрфактуал, рекомендация. Вердикт и статус `Acceptance Verifier` не меняются.
- ИИ исправил код по отчёту и запушил → верификатор прогоняется снова (2-й круг) → Judge
  сравнивает круг с предыдущим и помечает каждую находку: исправлена, настоящая новая, поздняя
  (была в коде раньше, но не названа), регрессия от фикса или ложная. В комментарии растёт
  таблица кругов. Исправляющий ИИ этот разбор не получает, только отчёт верификатора, как
  сейчас.
- Владелец видит, что после 3-го круга всплывают поздние находки → по доказательствам Judge
  проверяет, существовали ли дефекты в предыдущих кругах при тех же требованиях. Подтверждённые
  поздние находки указывают на неполноту верификатора; смена статуса сама по себе этого не
  доказывает.
- Владелец запускает разбор вручную для уже закрытого PR → данные по прошлым FAIL набираются
  сразу, без ожидания новых PR.
- Владелец в конце работы над PR ставит **один** сводный лейбл исхода: `verifier-correct`,
  `verifier-false-fail` или `verifier-false-pass`. Для метрик отдельно подтверждает оценки
  кругов и диагнозы находок: командой `/calibration round=2 expected=PASS`, `/calibration
  round=2 cause=ISSUE_DEFECT subtype=BAD_VERIFY_CLAUSE` или `/calibration round=3 finding=F-7
  class=FALSE_FINDING`. Если согласен со всеми уже существующими разборами, использует
  `/calibration confirm=all snapshot=<hash>` — команда привязывается к показанному в комментарии
  точному набору и хэшам разборов на момент её создания. Размечать каждый круг отдельно в этом
  случае не нужно. Лейбл не подтверждает причины автоматически; команда от не-владельца
  игнорируется.

- Владелец запускает агрегат по набору PR → видит:
  - матрицу «правильный вердикт × вердикт верификатора» по подтверждённым кругам (correct PASS /
    ложный FAIL / correct FAIL / ложный PASS), отдельно `NEEDS_HUMAN` и технические сбои;
  - среднее и максимальное число кругов до PASS;
  - долю поздних находок, регрессий от фикса и ложных находок;
  - распределение первопричин по компонентам и частоту подтипов;
  - выполнение порогов цели и подтипы, набравшие ≥ 3 подтверждённых случая.
- Подтип набрал 3 подтверждённых случая → владелец заводит системное изменение (правило
  контракта, скилла `issues`, промпта или новую детерминированную проверку) со ссылкой на эти
  случаи. Один воспроизводимый критический дефект, особенно ложный PASS, допускает исправление
  сразу.
- Владелец меняет промпт или схему верификатора → запускает golden eval и видит ложные PASS и
  ложные FAIL на парных кейсах.

## В скоупе

**A. Таксономия и схема разбора.** Фиксированная машиночитаемая таксономия в trusted-конфиге на
default-ветке:
- `primary_cause`: `ISSUE_DEFECT`, `IMPLEMENTATION_DEFECT`, `VERIFIER_FALSE_FAIL`,
  `VERIFIER_FALSE_PASS`, `VERIFIER_INSTABILITY`, `DETERMINISTIC_RULE_DEFECT`, `INFRA_FAILURE`,
  `MIXED`, `INSUFFICIENT_EVIDENCE`;
- `responsibility`: `issue_authoring`, `implementation`, `verifier`, `deterministic_verifier`,
  `infrastructure`, `mixed`, `unknown`;
- подтипы дефекта issue: `AMBIGUOUS_REQUIREMENT`, `MISSING_REQUIREMENT`,
  `CONTRADICTORY_REQUIREMENTS`, `WRONG_AFFECTS`, `BAD_VERIFY_CLAUSE`,
  `VERIFY_DOES_NOT_PROVE_REQUIREMENT`, `OVERCONSTRAINED_IMPLEMENTATION`,
  `MISSING_NEGATIVE_CASE`, `MISSING_EDGE_CASE`, `STALE_CODE_ASSUMPTION`,
  `UNVERIFIABLE_REQUIREMENT`;
- подтипы дефекта верификатора: `MISREAD_REQUIREMENT`, `MISREAD_CODE`, `BAD_REFERENCE`,
  `OVERSTRICT_INTERPRETATION`, `UNDERSTRICT_INTERPRETATION`, `INVENTED_REQUIREMENT`,
  `NONDETERMINISTIC_JUDGMENT`, `PROMPT_DEFECT`, `SCHEMA_DEFECT`, `REFERENCE_CHECK_DEFECT`,
  `DETERMINISTIC_CHECK_DEFECT`;
- выходной JSON разбора: `observed_verdict`, `independent_expected_verdict`
  (`PASS`/`FAIL`/`UNDECIDABLE`), `primary_cause`, `responsibility`, `confidence` (уверенность в
  классификации, не в вердикте), `issue_defects[]`, `implementation_defects[]`,
  `verifier_defects[]` (с `recommended_change_target`: `prompt` / `schema` /
  `deterministic_checker` / `reconciliation` / `reference_validation` / `none`),
  `correct_verifier_findings[]`, `counterfactual` (`fix_issue_only` / `fix_implementation_only`
  / `fix_verifier_only` → `RESOLVES` / `DOES_NOT_RESOLVE` / `UNKNOWN`), `systemic_lessons[]`,
  `golden_case_recommendation`. Каждая находка имеет устойчивый `finding_id`, ссылается на ID
  пункта issue (`AC-n`/`INV-n`/`TR-n`/`DOD-n`) или `null` и содержит доказательства на
  конкретном SHA либо ссылки на входной JSON/лог. Один пункт issue может иметь несколько
  находок; первопричина и `reasons[].source` хранятся раздельно. Схема включает переходы
  статусов критериев, классы дефектов и статус подтверждения владельцем; нехватка данных не
  требует выбора уверенного диагноза.

**B. Правила атрибуции (промпт Judge).** Решающие правила записаны явно:
- утверждённое issue неоднозначно, противоречиво или его `Verify:` не доказывает требование →
  `ISSUE_DEFECT`, с указанием конкретного дефекта контракта;
- верификатор добавил требование, которого нет в issue или действующей trusted-политике → дефект
  верификатора (`INVENTED_REQUIREMENT`), а не автоматически `ISSUE_DEFECT`;
- согласованное расширение требований владельцем — изменение спецификации, а не доказательство
  дефекта предыдущей версии issue;
- требование однозначно, а реализация ему противоречит → `IMPLEMENTATION_DEFECT`;
- реализация соответствует issue и обязательной trusted-политике, а верификатор дал
  необоснованный FAIL → `VERIFIER_FALSE_FAIL`. Ложная отдельная находка при других настоящих
  блокирующих дефектах не делает итоговый FAIL ложным;
- технический сбой или отсутствие обязательного доказательства отделяется от семантического
  дефекта реализации; обоснованный fail-closed отказ не считается ошибкой верификатора;
- при нехватке данных ставится `INSUFFICIENT_EVIDENCE` вместо догадки; `MIXED` — только если
  изменения независимо нужны минимум в двух компонентах.

Порядок анализа фиксирован: сначала восстановить контракт issue, затем независимо оценить
реализацию, и только потом читать отчёты верификатора. Это два изолированных вызова модели:
первый не получает текущие или прошлые отчёты верификатора, разборы Judge и self-report
исполнителя; второй получает зафиксированный результат первого и полный пакет. Первая оценка не
переписывается после ознакомления с выводами верификатора. Детерминированные доказательства
отделены от модельных суждений. Рекомендации конкретны: это точное правило, а не «сделать
критерии яснее». Judge не рекомендует ослабить проверку ради одного PR и не предлагает хаков под
один PR. За основу промпта берётся черновик из исходных заметок владельца.

**B2. Круги и классы находок.** Кругом считается одна завершившаяся попытка workflow
верификатора на PR, в том числе попытка с техническим сбоем. Его два внутренних модельных
прогона относятся к одному кругу. Ключ круга — `repository` + `verifier_run_id` +
`verifier_run_attempt`; повторный запуск Judge на том же круге создаёт ревизию разбора, а не
новый круг.

Для круга фиксируются `base_sha`, `head_sha`, `issue_body_sha256` из provenance (ADR-042,
ISSUE-480) и тип изменения задачи относительно предыдущего круга:
- `code` — изменился только `head_sha`;
- `issue` — изменился только `issue_body_sha256`; наличие повторного approval проверяется
  отдельно;
- `both` — изменилось и то, и другое;
- `none` — `head_sha` и `issue_body_sha256` не изменились; это не гарантия одинаковых входов.

Отдельно сохраняется fingerprint значимых входов: base/head SHA, issue hash, trusted verifier
SHA, версии/хэши промпта, схемы, скриптов и конфигов, модель и параметры, CI snapshot, approval
и авторизованные исключения. Идентификатор запуска не входит в fingerprint. Если вход
отсутствует, это явно отмечается, fingerprint не признаётся полным. Сопоставимость равна
`COMPARABLE`, `INPUTS_CHANGED` или `UNKNOWN`; сравнение семантики CI snapshot не зависит от
порядка элементов и технических временных меток. Изменения значимых входов показываются отдельно
от типа задачи.

Скрипт вычисляет **переход статуса критерия** по ID: прежний статус → текущий статус либо
`NOT_REPORTED`. Смена FAIL → PASS не доказывает исправление дефекта. При `none` смена статуса
отмечается как `FLIP`; приписывать её `VERIFIER_INSTABILITY` можно только при сопоставимых
значимых входах и отсутствии иного объяснения.

Judge отдельно определяет **судьбу конкретного дефекта** по устойчивому `finding_id`:
- `INITIAL` — настоящий дефект обнаружен в первом наблюдаемом круге; предыдущего круга нет,
  поэтому он не объявляется ни новым, ни поздним;
- `RESOLVED` — доказано устранение дефекта, а не только изменение оценки модели;
- `PERSISTING` — тот же дефект подтверждён в обоих кругах;
- `NEW_REAL` — подтверждённый новый дефект появился после изменения, не связанного с
  исправлением предыдущей находки;
- `LATE_FINDING` — дефект уже существовал в предыдущем круге при применимых тогда требованиях,
  но верификатор его не назвал;
- `FIX_REGRESSION` — подтверждённый новый дефект внесён изменением, исправлявшим предыдущую
  находку;
- `FALSE_FINDING` — заявленная ошибка не подтверждается требованиями и доказательствами;
- `UNKNOWN` — доказательств для определения судьбы или причинной связи недостаточно.

`FLIP` — характеристика перехода оценки, а не класс судьбы дефекта. Для первого круга
подтверждённая настоящая находка получает `INITIAL`, при нехватке доказательств — `UNKNOWN`.
Класс сохраняется для каждого круга: позднее `RESOLVED` не стирает факт `LATE_FINDING` при
первом обнаружении. Метрики происхождения используют класс первого обнаружения, текущее
состояние — последний доказанный класс. По одному AC-ID находки не объединяются: сравниваются
механизм дефекта и доказательства. Изменение процитированных строк — вспомогательный факт, а не
доказательство появления или исправления ошибки. При изменении смысла критерия история требует
явного сопоставления версий; новая норма не применяется задним числом.

Всё, что вычислимо без модели (переходы статусов, тип изменения, fingerprint/сопоставимость,
изменение процитированных строк), считается скриптом. Модель решает реальность дефекта,
сопоставление находок и причинную связь с изменениями. Круг с типом `issue` или `both` — повод
исследовать причину правки, но не автоматический диагноз `ISSUE_DEFECT`.

  `openai/codex-action`, sandbox read-only, существующий `OPENAI_API_KEY`), новых секретов нет;
- получает issue, `spec-lint.json`, diff, список файлов, `verdict.json`/`verdict2.json`,
  `refs-problems*.json`, `absence.json`, `scope.json`, `ci.json`, результат tampering scan,
  provenance, итоговый вердикт и комментарий верификатора, а также комментарий исполнителя
  (Ralph) с AC self-report (ADR-035), если он есть. Полный пакет содержит снимки issue,
  approval, авторизации исключений, trusted-политики и сведения о завершении jobs для исходного
  круга. Текущие API-данные не подставляются вместо исторических без отметки о неполноте;
- стадия 1 получает контракт, код и доступные исходные доказательства/политику без выводов
  верификатора, Judge и исполнителя. Стадия 2 получает зафиксированный результат стадии 1 и
  полный пакет. Вызовы изолированы; размещение в jobs учитывает одноразовый `drop-sudo` экшена;
- разбирает **каждый круг**. На вторую стадию дополнительно идут вердикт, JSON разбора и
  provenance предыдущего круга, diff между `head_sha` кругов и изменения версии issue/политики;
  несопоставимость или неполнота входов не скрывается;
- публикует один обновляемый на месте комментарий в PR: таблица всех кругов (номер, `head_sha`,
  тип изменения, вердикт, классы находок) и разбор последнего круга. JSON разбора **каждого**
  круга лежит в скрытом блоке комментария и в артефакте CI, так что история кругов не теряется
  при обновлении комментария. Каждый разбор имеет ревизию и хэш; обновление одного круга
  сохраняет остальные, повторная доставка события не добавляет круг, конкурентные публикации не
  затирают историю. Подтверждение владельца относится к конкретной ревизии;
- не пишет commit status и не меняет лейблы, вердикт и комментарий верификатора;
- **не передаёт разбор исправляющему ИИ.** В калибровочный период тот получает только отчёт
  верификатора, как сейчас (решение владельца 2026-09-30): Judge наблюдает флоу, а не влияет на
  него.

**D. Парные golden-кейсы с мутацией patch-файлом** (решение владельца 2026-09-30). В golden
добавляются реальные корректные PR как `expected: PASS` и **пары мутаций**: каталог кейса
ссылается на `base_sha`/`head_sha` корректного PR и содержит `mutation.patch` — одну намеренную
порчу. Корректность исходного кейса подтверждается ревью владельца против issue и
trusted-политики, а не прежним PASS верификатора. В `case.json` фиксируются expected verdict,
ожидаемый criterion ID (или `null` для правила без ID) и reason code; для пары указывается
ожидаемый механизм обнаружения.

Eval-workflow накладывает патч на `head_sha` перед прогоном. После мутации заново строятся diff
от `base_sha` до результирующего дерева, список файлов, scope, tampering и другие проверки,
зависящие от кода; учитываются добавленные файлы. Исходный head SHA и хэш
мутации/результирующего дерева хранятся раздельно, синтетический кейс не выдаётся за реальный
проверенный commit. Если патч не накладывается или пакет неконсистентен, кейс считается `run
failure`.

CI в этом offline eval — явно замороженная фикстура для изолированной проверки верификатора, а
не результат запуска мутированного кода. Код PR/мутации не исполняется в доверенной среде.
Фиксируются также версии issue/политики и состояния approval/исключений, влияющие на verdict;
текущие API-значения их не заменяют. Измерение CI, который сам ловит мутацию, этим eval не
заявляется.

Виды порчи: убран обязательный negative/edge-тест; неверный тип; нарушен `INV`; изменена только
одна сторона cross-layer; добавлен файл вне `## Affects`. Цель — не меньше 5 пар, чтобы golden
eval измерял обе стороны ошибки. Для FAIL-кейса проверяется не только verdict, но и ожидаемая
причина: FAIL от сломанного входа или посторонней причины не считается успешным обнаружением
мутации.

**E. Разметка владельца** (решение владельца 2026-09-30: эталон — разметка после ревью, заранее
записанных ожиданий для обычных задач нет):
- один лейбл исхода на весь PR, общий с EPIC-30, остаётся сводкой: `verifier-correct` — все
  оценённые круги дали верный verdict; `verifier-false-fail` — был хотя бы один необоснованный
  итоговый FAIL; `verifier-false-pass` — был PASS при реальном блокирующем дефекте. Ложная
  отдельная находка при других настоящих причинах FAIL учитывается отдельно;
- если в истории есть и ложный FAIL, и ложный PASS, сводка — `verifier-false-pass`, а оба
  события сохраняются в покруговой разметке. Последний авторизованный лейбл определяет текущую
  сводку, но не удаляет исторические факты и не заменяет оценку кругов;
- `/calibration round=<N> expected=<PASS|FAIL|UNDECIDABLE>` подтверждает ожидаемый verdict
  конкретного круга. Отдельно команда `cause=<primary_cause> [subtype=<подтип>]` подтверждает
  или исправляет первопричину; `finding=<finding_id> class=<класс>` — конкретную находку. ID
  критерия разрешён как сокращение только если в круге ему соответствует ровно одна находка;
- `/calibration confirm=all snapshot=<hash>` подтверждает ожидаемые verdict и диагнозы всех уже
  существующих разборов, которые владелец просмотрел. Команда ссылается на зафиксированный
  список ключей кругов и хэшей ревизий. Для этого комментарий содержит снимок манифеста
  разборов, а команда принимает его `snapshot=<hash>`; если точный снимок нельзя восстановить,
  подтверждение отклоняется. Новый круг или изменённый разбор требует нового подтверждения;
- один лейбл не подтверждает причины, классы и expected verdict всех кругов автоматически.
  Подтверждение ожидаемого verdict и подтверждение диагноза хранятся раздельно. Без необходимых
  подтверждений разбор остаётся `unconfirmed`, даже если на PR есть лейбл;
- лейбл и команда засчитываются, только если их поставил владелец из
  `.github/verifier/owners.json` и это не бот — тот же механизм, что у `manual-verified`
  (ADR-042, ISSUE-473). Для одного поля конкретной ревизии побеждает последняя авторизованная
  команда; неверная или неоднозначная команда не применяется. История исправлений сохраняется.

Правильный verdict заранее записан только у golden-кейсов (`case.json` → `expected`). Эталон
обычного круга — подтверждение владельца после ревью, а не независимый вывод Judge сам по себе.

**F. Агрегат калибровки** — новый режим `scripts/verifier-metrics.js` после #484. По списку PR
он выводит:
- матрицу «правильный verdict × verdict верификатора» по кругам с подтверждённым expected
  verdict. `NEEDS_HUMAN`, `UNDECIDABLE`, технические сбои и отсутствующий verdict показываются
  отдельно;
- ложный PASS: круги с expected FAIL и observed PASS / все подтверждённые семантически дефектные
  круги с валидной приёмкой; ложный FAIL: круги с expected PASS и observed FAIL / все
  подтверждённые корректные круги с валидной приёмкой. Обоснованный отказ по
  инфраструктуре/недостающим входам не смешивается с семантической оценкой кода; режим и причины
  исключения явно выводятся;
- `NEEDS_HUMAN` / все круги с валидным официальным verdict; технические сбои / все завершившиеся
  попытки; долю неполных и неподтверждённых разборов;
- число кругов до первого PASS для сошедшихся PR (среднее, максимум, распределение); отдельно
  число несошедшихся PR и их наблюдённые круги. Долю сошедшихся за 1–2 круга по всем PR выборки;
- долю поздних находок: уникальные подтверждённые дефекты с `LATE_FINDING` при первом
  обнаружении / все уникальные подтверждённые настоящие дефекты с известной историей, включая
  `INITIAL`. `UNKNOWN` исключается из доли и показывается отдельно; последующие
  `PERSISTING`/`RESOLVED` не стирают происхождение и не добавляют новый дефект;
- долю регрессий от фикса среди тех же дефектов; ложных находок среди всех подтверждённых
  находок; `FLIP` среди сопоставимых повторных кругов `none`; кругов с изменением issue среди
  кругов, имеющих предыдущий круг. Для каждого показателя явно указаны числитель и знаменатель;
- распределение `primary_cause` и `responsibility`, частоту подтипов и долю
  `INSUFFICIENT_EVIDENCE`. Подтверждённые диагнозы отделены от гипотез Judge;
- выполнение порогов цели (п. G); подтипы с ≥ 3 подтверждёнными независимыми случаями и номерами
  PR. Повтор того же дефекта в нескольких кругах и каскадные симптомы не увеличивают число
  случаев.

Лейбл исхода служит сводкой PR; в численные пороги идут только соответствующие подтверждённые
оценки кругов/находок. Неоценённые PR и круги показываются отдельно. При нулевом знаменателе
выводится «нет данных», а не 0 % и не «порог выполнен». Данные читаются из GitHub API по
запросу; файлов истории в репозитории нет.

**G. Пороги цели и процессные правила** (в документации фабрики):
- **цель достигнута**, когда одновременно (решение владельца 2026-09-30):
  - на последних ≥ 20 размеченных владельцем PR с подтверждёнными оценками кругов: 0 ложных
    PASS, ложных FAIL ≤ 10 %, `NEEDS_HUMAN` ≤ 10 %; знаменатели — из п. F. Для выбранных PR
    подтверждены все доступные применимые оценки кругов; пропуски показываются и не считаются
    молчаливым согласием;
  - на тех же PR поздних находок ≤ 10 % от уникальных настоящих дефектов с известной историей;
    доля неизвестной истории показывается рядом;
  - на последнем прогоне golden eval: 0 ложных PASS, 0 ложных FAIL, 0 run failures и 0
    несовпадений ожидаемой причины по всем кейсам;
  - для каждого порога есть ненулевой знаменатель; без данных цель не объявляется достигнутой.
    Это критерий калибровочного пилота, а не доказательство безопасности автомержа/деплоя. Для
    выбранного окна показываются версии policy/model и полнота разметки; результаты разных
    версий не выдаются за оценку одной текущей версии;
- правило повторяемости: 1 случай подтипа — записать, 2 — наблюдать, ≥ 3 подтверждённых —
  системное изменение (контракт, скилл `issues`, промпт или детерминированная проверка). Если
  подтип — объективное модельное решение, первым вариантом рассматривается перенос его в
  детерминированный код. Исключение: один воспроизводимый критический дефект, особенно ложный
  PASS или нарушение trust boundary, допускает немедленное отдельное issue с доказательствами и
  парным regression case; ожидать ещё два инцидента не требуется;
- калибровочный набор: 20–30 небольших задач разных типов, преимущественно из существующего
  бэклога. Типы: локальное поведение; поведение с negative/edge-кейсом; cross-layer
  `apps/api`↔`apps/web`; config; docs; `absence`; `ci`; рефакторинг без изменения поведения;
  миграция; security; удаление старого поведения; багфикс с регрессионным тестом. Прогон набора
  — это эксплуатация, а не критерий приёмки эпика;
- режим после достижения цели: Judge запускается только на FAIL, `NEEDS_HUMAN`, расхождениях
  двух прогонов верификатора и на случайной выборке PASS.

## Не в скоупе

- Изменение вердикта, статуса `Acceptance Verifier`, правил верификатора и его промпта. Правки
  по рекомендациям Judge заводятся отдельными issue по правилу п. G.
- Автомерж (EPIC-30) и автодеплой. Пороги п. G меряют точность верификатора; EPIC-30 может
  использовать их данные, но условия включения автомержа решаются там.
- Автоматическое применение рекомендаций Judge: правка скилла, контракта, промпта или создание
  issue.
- Заранее записанное ожидание исхода для обычных задач: эталоном служит разметка после ревью.
- Хранение истории в файле репозитория (`calibration-history.jsonl` и т.п.).
- Оценка людей: `responsibility` указывает компонент фабрики, а не автора.
- Разбор PR не из `task/ISSUE-*` и PR из форков.
- Продуктовый код `apps/api`/`apps/web`, PostgreSQL/Prisma, `STORAGE_ROOT`, AI-пайплайн резюме.
- Вынос в пакет `dark-factory` (EPIC-28).

## Ключевые инварианты

- **Judge не влияет на вердикт.** Он не пишет commit status, не меняет лейблы и комментарий
  верификатора и не участвует в допуске к мержу. Сбой Judge не делает PR красным.
- **Независимость оценки.** Два изолированных вызова: `independent_expected_verdict` формируется
  без текущих/прошлых выводов верификатора, Judge и self-report исполнителя; второй вызов не
  переписывает сохранённый результат первого. Промпт не сообщает, какой компонент улучшается.
- **Модель Judge отличается от модели верификатора**, и это проверяется кодом по trusted
  allowlist Judge.
- **Judge наблюдает, но не участвует в цикле исправления.** Его разбор не входит во вход
  исправляющего ИИ; флоу «отчёт верификатора → владелец вручную передаёт его ИИ → ИИ правит код
  → перезапуск» остаётся прежним. Поскольку передача ручная, правило поддерживается процессом и
  явной пометкой в комментарии Judge, а не кодом.
- **Круг — единица анализа.** Разбор каждого круга сохраняется и не перезаписывается разбором
  следующего. Ключ круга содержит run ID/attempt; повтор Judge — ревизия разбора. Всё, что
  вычислимо без модели (переходы статусов, тип изменения, сопоставимость, изменение строк),
  считается скриптом. Переход статуса не равен исправлению дефекта; `FLIP` не равен доказанной
  нестабильности. Исторические входы не подменяются текущими без отметки о неполноте.
- **Таксономия закрытая.** Значения вне trusted-конфига отклоняются схемой; свободный текст
  допустим только в полях доказательств и рекомендаций; идентификаторы/хэши — отдельные
  технические поля.
- **Нет догадок.** При нехватке доказательств ставится `INSUFFICIENT_EVIDENCE`; каждая находка
  ссылается на ID пункта issue или явно `null`.
- **Trust boundaries как у верификатора (ADR-041).** Промпт, схема, таксономия, allowlist и
  скрипты читаются с default-ветки. Голова PR — только данные, её код не исполняется. Ключ
  модели есть только в шаге вызова модели. Issue, diff, отчёт исполнителя и отчёты верификатора
  — данные, а не инструкции. Используется `workflow_run`, не `pull_request_target`.
- **Эталон — разметка владельца.** В пороги идут только подтверждённые ожидаемые verdict кругов
  и классы находок от владельца из `owners.json` (не бот). Лейбл — сводка, не blanket approval.
  Подтверждение привязано к ревизии; неподтверждённое показывается отдельно.
- **Никаких литералов проекта в коде фабрики** (инвариант EPIC-27/28): пути, имена проверок,
  логины и модели берутся из trusted-конфигов.
- **Проверку не ослабляют ради одного PR.** Системное изменение обычно делается по правилу ≥ 3
  подтверждённых случаев; воспроизводимый критический дефект — исключение п. G.
- **Golden проверяет причину.** Мутация меняет весь пакет входов, зависящих от кода; CI явно
  заморожен для offline eval. Посторонний FAIL не засчитывается как обнаружение мутации.

## Технические ограничения

- Judge вызывается через тот же pin `openai/codex-action`, что и верификатор, поэтому известная
  проблема v1.12 (ADR-041, ISSUE-449) касается и его.
- В калибровочный период Judge делает два вызова на круг, сверх одного/двух вызовов
  верификатора. Стоимость и длительность учитываются по фактическим вызовам; оценка «примерно
  удваивает» не используется как гарантия. После достижения цели включается выборочный режим (п.
  G).
- Разбор задним числом зависит от срока хранения артефактов Actions. Для более старых PR входы
  восстанавливаются из GitHub API частично, и разбор помечается как неполный. Восстановить
  старое тело issue, CI snapshot или policy из их текущего состояния без доказательств нельзя.
- Мутационный патч должен накладываться на `head_sha` без конфликтов. Если патч не наложился,
  кейс считается `run failure`, а не PASS/FAIL (как сейчас в `verifier-eval.js`).
- `GITHUB_TOKEN` не читает classic branch protection (EPIC-27); это учитывается при сборе
  входов.

## Критерии готовности (Acceptance Criteria)

- [ ] Таксономия лежит в trusted-конфиге. Схема разбора отклоняет значения `primary_cause`,
      `responsibility` и подтипов вне конфига (тест на каждое поле).
- [ ] Разбор, в котором находка не ссылается ни на ID пункта issue, ни на `null`, отклоняется
      схемой (тест).
- [ ] Workflow Judge запускается после завершения верификатора для PR `task/ISSUE-*` и вручную
      по номеру PR, а для PR из форка и для других веток не запускается (проверка конфигурации
      workflow).
- [ ] Workflow Judge не имеет прав на commit status и лейблы, и его падение не меняет статус
      `Acceptance Verifier` (проверка конфигурации workflow).
- [ ] Промпт, схема, таксономия, allowlist и скрипты Judge читаются с default-ветки, а ключ
      модели доступен только шагу вызова модели (проверка конфигурации workflow).
- [ ] Модель Judge, совпадающая с моделью верификатора или отсутствующая в allowlist Judge, даёт
      ошибку разбора, а не разбор (тест).
- [ ] Независимая оценка строится первым из двух изолированных вызовов. Во входе нет текущих или
      прошлых отчётов верификатора/Judge и self-report исполнителя; второй вызов получает
      сохранённый результат первого и полный пакет, но не переписывает первый результат (тест
      сборщика входов и конфигурации workflow).
- [ ] Отсутствующий или нечитаемый вход помечается в разборе как отсутствующий, а не
      додумывается (тест).
- [ ] Комментарий Judge в PR один и обновляется на месте. Он содержит таблицу всех кругов
      (номер, `head_sha`, тип изменения, вердикт, классы находок), разбор последнего круга
      (первопричина, ответственный компонент, контрфактуал, дефекты с ID пунктов, рекомендации)
      и JSON разбора каждого круга в скрытом блоке. После разбора круга N разборы кругов 1…N−1 в
      комментарии сохраняются (тест рендера).
- [ ] Круг идентифицируется run ID/attempt; повтор Judge не добавляет круг. Тип изменения
      (`code`/`issue`/`both`/`none`) определяется по head SHA и issue hash, отдельно вычисляется
      сопоставимость значимых входов. Изменение policy/CI при `none` не считается доказанной
      нестабильностью (тесты на типы, повтор события, изменённые и отсутствующие входы).
- [ ] Скрипт вычисляет переходы статусов по ID, включая `NOT_REPORTED`, и изменения цитированных
      строк. FAIL → PASS не присваивает дефекту `RESOLVED`; `FLIP` отделён от судьбы дефекта
      (тесты на фикстурах двух кругов).
- [ ] Схема принимает классы дефектов
      `INITIAL`/`RESOLVED`/`PERSISTING`/`NEW_REAL`/`LATE_FINDING`/
      `FIX_REGRESSION`/`FALSE_FINDING`/`UNKNOWN`; переход оценки хранится отдельно. Устойчивый
      `finding_id` отличает разные ошибки одного критерия; неизвестная история не требует
      уверенного класса (тесты схемы и сопоставления).
- [ ] Исторический пакет содержит доступные снимки issue, CI, policy, approval и исключений;
      отсутствующий снимок явно отмечается. Текущие API-данные не выдаются за исторические
      (тесты сборщика).
- [ ] Ревизии разбора имеют хэш; повтор и конкурентная публикация не теряют другие круги,
      подтверждение старой ревизии не распространяется на новую (тесты хранения/публикации).
- [ ] Комментарий Judge — отдельный комментарий со своим маркером. Он не меняет комментарий
      верификатора и начинается с явной пометки, что это калибровочный разбор, а не список
      исправлений (тест рендера). Документация фабрики описывает правило ручного флоу:
      исправляющему ИИ передаётся только отчёт верификатора.
- [ ] Golden-кейс может содержать `mutation.patch`; после наложения пересчитываются diff от base
      SHA, список файлов (включая добавленные), scope и tampering. Исходный SHA и результирующее
      дерево различимы; конфликт/неконсистентность — `run failure`. CI/approval и исключения —
      явно замороженные фикстуры, а не текущие API-данные (тесты).
- [ ] Eval проверяет expected verdict и ожидаемые criterion ID/reason code. FAIL из-за
      постороннего дефекта входов не засчитывается как обнаружение мутации (тест).
- [ ] Golden-набор содержит не меньше 5 пар «корректный PR `PASS` / мутация `FAIL`», покрывающих
      убранный negative/edge-тест, нарушенный `INV`, одностороннее cross-layer изменение и файл
      вне `## Affects`; корректность исходных кейсов подтверждена владельцем, ожидаемый механизм
      обнаружения указан. `scripts/verifier-eval.js` считает ложные PASS/FAIL, run failures и
      несовпадения ожидаемой причины.
- [ ] Лейбл и `/calibration` засчитываются только от владельца из `owners.json`, не бота.
      Последний авторизованный лейбл — сводка; он не подтверждает круги автоматически и не
      стирает сочетание false FAIL/false PASS. Команды подтверждают expected verdict и диагноз
      раздельно; `confirm=all` относится только к зафиксированным ревизиям. Неоднозначный
      criterion ID отклоняется; команда `round=<N>` меняет только круг N (тесты авторизации,
      ревизий и команд).
- [ ] Режим калибровки `scripts/verifier-metrics.js` по списку PR выводит матрицу «правильный ×
      наблюдаемый вердикт», доли ложных PASS/FAIL и `NEEDS_HUMAN`, число кругов до PASS, доли
      `LATE_FINDING`/`FIX_REGRESSION`/`FALSE_FINDING`/`FLIP`, распределение
      `primary_cause`/`responsibility`, частоты подтипов, выполнение порогов п. G и подтипы с ≥
      3 независимыми подтверждёнными случаями. Для каждой доли показаны числитель/знаменатель;
      неподтверждённые оценки, UNKNOWN, несошедшиеся PR и технические сбои видны отдельно.
      Нулевой знаменатель — «нет данных», не выполненный порог; повтор дефекта не увеличивает
      число случаев (тесты на фикстурах).
- [ ] Документация фабрики описывает цель и её пороги, таксономию, разметку владельца, правило
      «≥ 3 случая → системное изменение», калибровочный набор и режим после достижения цели.
- [ ] ADR о Calibration Judge принят: advisory-статус, отдельная модель, trust boundaries,
      эталон — разметка владельца, хранение в GitHub.

## Test Requirement (набросок)

Unit-тесты на фикстурах без сети и без реальной модели:
- валидация схемы и таксономии, проверка модели по allowlist;
- сборка исторических входов и provenance, fingerprint/сопоставимость (включая отсутствие любых
  прошлых/текущих выводов и self-report при независимой оценке);
- переходы статусов отдельно от судьбы дефекта, finding ID, UNKNOWN и несопоставимые круги;
- рендер комментария, сохранение ревизий, идемпотентность и конкурентное обновление;
- авторизация лейблов и `/calibration`, отдельные подтверждения и фиксация ревизий;
- режим калибровки `verifier-metrics.js`, знаменатели, дедупликация и отсутствие данных;
- наложение `mutation.patch`, пересборка входов и проверка ожидаемой причины на парах PASS/FAIL.

Кроме того — проверка конфигурации workflow: триггеры, права, trusted checkout, доступ к ключу.
Ручной `workflow_dispatch` Judge на нескольких прошлых PR и прогон golden eval делает владелец,
это не gated-критерий.

## Открытые вопросы

Решения владельца 2026-09-30 (не пересматривать):
1. История хранится в комментарии PR (скрытый JSON) и артефакте CI, агрегат читается через
   GitHub API. Файла в репозитории нет.
2. Модель Judge — отдельная модель OpenAI, не `VERIFIER_MODEL`.
3. Эталон — разметка владельца после ревью. Заранее записанных ожиданий для обычных задач нет.
4. Разметка — сводный лейбл исхода плюс `/calibration` для подтверждения/исправления expected
   verdict и причин. Подтверждения привязаны к конкретным ревизиям, лейбл их не заменяет.
5. Мутации golden-кейсов хранятся как `mutation.patch` в каталоге кейса.
6. Сначала делается #484 как есть, агрегат калибровки — новый режим того же скрипта.
7. Делается в jobflow сейчас, перенос в `dark-factory` — в рамках EPIC-28.
8. Цель — точность верификатора (п. «Цель»), а не деплой. Пороги: 0 ложных PASS, ложных FAIL ≤
   10 %, `NEEDS_HUMAN` ≤ 10 % на ≥ 20 размеченных PR, golden eval без ошибок.

9. Единица анализа — круг (run ID/attempt). Judge разбирает каждый круг; владелец ставит один
   сводный лейбл на PR, подтверждает просмотренные разборы через `confirm=all` либо отдельные
   оценки и исправляет несогласие через `/calibration round=<N>`. Новые ревизии не
   подтверждаются старой командой автоматически.
10. Разбор Judge не передаётся исправляющему ИИ в калибровочный период.

11. Отчёт верификатора исправляющему ИИ владелец передаёт **вручную**, в сессии. Поэтому правило
    «разбор Judge не во входе» — процессное, а не проверяемое кодом. Его поддерживают отдельный
    комментарий Judge с явной пометкой «калибровочный разбор, не список исправлений» и описание
    правила в документации фабрики.
12. Порог поздних находок — ≤ 10 % от уникальных подтверждённых настоящих дефектов с известной
    историей; неизвестная история показывается отдельно. Пороги — критерии пилота, не допуск к
    деплою.
13. Переход статуса, судьба дефекта и сопоставимость входов — отдельные измерения.
14. Порог ≥ 3 случаев не задерживает исправление одного воспроизводимого критического дефекта.
15. Мутационный eval замораживает CI как фикстуру и пересчитывает входы, зависящие от кода;
    успешным считается обнаружение по ожидаемой причине, не произвольный FAIL.

Остаются для плана:
- Конкретная модель Judge и её значение в allowlist (выбирается при реализации из доступных в
  аккаунте).
- Срок хранения артефактов верификатора: хватает ли значения по умолчанию для разбора задним
  числом.
- Какие PR брать для первых 5 golden-пар (кандидаты — PR с PASS после ISSUE-482).

## Приложение А: черновик промпта Calibration Judge (из заметок владельца, 2026-09-30)

Исходный материал для промптов Judge (задача «Промпт Judge и рендер комментария», Фаза 1). По
решению владельца Judge работает в две стадии двумя отдельными вызовами модели: стадия 1 (шаги
1–2 ниже, без отчётов верификатора) и стадия 2 (шаги 3–4, с результатом стадии 1 и отчётами
верификатора). Выходной JSON ниже — исходный вариант; финальные поля задаёт схема из
`.github/calibration/`. Классы находок между кругами добавляются в Фазе 2.

```text
You are the Calibration Judge for an automated software factory.
You are NOT an acceptance verifier and you MUST NOT change the acceptance verdict.

Your job is to perform a post-run root-cause analysis of the complete task lifecycle:
- Was the GitHub Issue sufficiently precise and independently verifiable?
- Did the implementation correctly satisfy the Issue as written?
- Did the Acceptance Verifier evaluate the Issue and implementation correctly?
- If something failed, which component should be improved?
You are evaluating the factory, not the developer.

Treat deterministic evidence separately from model judgments.
Do not assume that a verifier FAIL means the implementation is wrong.
Do not assume that an implementation satisfying the tests means the Issue is satisfied.
Do not optimize for producing PASS. Your objective is to identify the most likely root cause.

Step 1 - Reconstruct the contract.
Read the frozen Issue and mandatory trusted policy without looking at verifier conclusions.
Stage 1 is an isolated model call: exclude all current/prior verifier reports, Judge analyses and
implementer self-reports. Preserve its output unchanged before starting Stage 2. For every Key
Invariant,
Acceptance Criterion, Test Requirement and Definition of Done determine: what behavior is
literally required; what evidence is supposed to prove it; whether the requirement has only one
reasonable interpretation; whether the supplied Verify: mechanism actually proves the requirement;
whether a reasonable implementation agent could satisfy the wording while violating the author's
likely intention; whether the requirement demands information that is not present in the Issue or
repository. Do not silently add requirements that are merely implied by good engineering practice.

Step 2 - Evaluate the implementation independently.
Verify provenance and evidence availability before drawing conclusions. Current API state is not
historical evidence. For each requirement determine: SATISFIED, NOT_SATISFIED, AMBIGUOUS_SPEC,
INSUFFICIENT_EVIDENCE. Missing reports after an infrastructure failure do not prove bad code.
Do not copy the Acceptance Verifier's status. Reach an independent conclusion.

Step 3 - Inspect the verifier.
Only after Steps 1 and 2, in a separate isolated call, read the verifier reports and the saved
Stage 1 output. Do not overwrite Stage 1. A false individual finding does not make an overall FAIL
false if other valid blockers remain. Explain primary failures separately from cascading symptoms.
For every verifier failure determine whether
it is supported by: the literal Issue; repository evidence; deterministic checks; or an
interpretation introduced by the verifier. Pay particular attention to: requirements inferred but
not written; overly strict interpretations; incorrect code interpretation; missing or incorrect
references; unstable conclusions between verifier runs; claims contradicted by deterministic
evidence; requirements that are impossible to verify from the available repository state.

Step 4 - Assign root cause. Choose exactly one primary_cause.
Use ISSUE_DEFECT only when the approved contract has a demonstrable ambiguity, contradiction,
missing necessary requirement, or a Verify clause that does not prove its requirement.
A verifier demanding something absent from both the Issue and mandatory trusted policy is a
verifier defect (INVENTED_REQUIREMENT), not automatically an Issue defect.
An owner-approved scope change does not prove the previous Issue was defective.
Use IMPLEMENTATION_DEFECT when the Issue was sufficiently precise and the implementation
demonstrably violated it.
Use VERIFIER_FALSE_FAIL when the Issue is sufficiently precise, the implementation satisfies it,
but the verifier rejected it.
Use VERIFIER_FALSE_PASS when the implementation violates the Issue but the verifier accepted it.
Use VERIFIER_INSTABILITY only when runs disagree on comparable significant inputs and no other
explanation is supported. Equal head SHA and Issue hash alone do not prove comparability.
Track criterion status transitions separately from defect history. FAIL to PASS is not proof of
RESOLVED. Match defects by stable finding IDs, mechanism and evidence, not criterion ID alone.
Use INITIAL for a confirmed real finding in the first observed round; do not call it late or new
without a previous round. Preserve the first-detection classification when later rounds mark a
defect PERSISTING or RESOLVED. Use UNKNOWN when evidence does not establish defect history. Do not
apply newly added requirements to
older rounds. A changed quoted line alone does not prove when a defect appeared.
Use DETERMINISTIC_RULE_DEFECT only when a deterministic verifier rule itself produces an incorrect
result.
Use INFRA_FAILURE for failures unrelated to the Issue, implementation semantics, or verifier
judgment. A justified fail-closed response to missing evidence is not a verifier false rejection.
Use MIXED only when at least two causes independently require changes.
Use INSUFFICIENT_EVIDENCE rather than guessing.

Improvement recommendations: produce them only when supported by the observed failure. For Issue
improvements, give an exact proposed change to the issue-authoring rules.
Bad: "Make acceptance criteria clearer."
Good: "For behavior criteria involving rejection paths, require the AC to specify the externally
observable error/result and require a negative test reference."
For verifier improvements, identify whether the change belongs to: prompt; schema; deterministic
checker; reconciliation; reference validation; no change.
Do NOT recommend weakening a verifier rule merely to make this PR pass.
Prefer converting repeated objective judgments from model logic into deterministic checks when
they can be computed reliably.
Do NOT recommend repository-specific hacks for a single PR unless the rule is clearly
generalizable.

Counterfactual check - before the final answer, answer internally:
If only the Issue were improved, would the failure probably disappear?
If only the implementation were corrected, would it disappear?
If only the verifier were corrected, would it disappear?
Use these counterfactuals when choosing the primary cause.

confidence is confidence in the root-cause classification, not in the verifier verdict.
If evidence does not allow reliable attribution, use INSUFFICIENT_EVIDENCE.
Never invent missing evidence. Every finding needs a stable finding_id, criterion ID or null,
and evidence tied to the relevant SHA/input/log. Owner confirmation is separate from model confidence;
a PR label does not confirm all diagnoses. Repeated rounds of one defect are not independent cases.
```
