# Plan: Verifiable Spec and Independent Verifier (EPIC-27)

**PRD:** `project-management/prd/PRD-verifiable-spec-and-independent-verifier.md`
**Дата:** 2026-09-26

Ни одна фаза не затрагивает `apps/api`, `apps/web`, PostgreSQL или `STORAGE_ROOT`: весь эпик —
репозиторная инфраструктура (`scripts/`, `.github/`, `.claude/`, `docs/`, `project-management/`).
Тесты каждого скрипта — `scripts/*.spec.js` в той же задаче, что меняет скрипт (CI: `Test (scripts)`).

## Фазы реализации

### Фаза 1: Контракт issue и линтер
**Цель:** Появляется единый машинно-проверяемый формат issue и детерминированный линтер — tracer
bullet, на который опираются обе стороны фабрики.
**Затрагивает:** `.github/verifier/` (файл-контракт), `scripts/issue-lint.js`, `scripts/issue-lint.spec.js`
**Задачи:**
- [ ] Описать файл-контракт формата issue: обязательные секции, ID пунктов (`AC-n`, `DOD-n`, `TR-n`, `INV-n`), типы пунктов (`behavior`, `doc`, `config`, `ci`, `absence`), клауза `Verify:`, запрещённые формулировки вне `## Manual verification (owner, not gated)`
- [ ] Реализовать `scripts/issue-lint.js` по контракту с тестами на каждый случай отказа и CLI-режимом для хука и CI

**Когда готова:** закрывает PRD AC «Существует один файл-контракт формата issue…» (в части самого
контракта) и «`scripts/issue-lint.js` отклоняет тело без обязательных секций, без ID, с
повторяющимися ID, с пунктом `AC`/`DOD`/`TR` без типа или без `Verify:`, с условным пунктом и с
запрещёнными формулировками…».

### Фаза 2: Скилл пишет по контракту
**Цель:** `issues`-скилл производит только спеки, проходящие линтер, с негативными сценариями и
независимым ревью; невалидное тело не создаётся.
**Затрагивает:** `.claude/skills/issues/SKILL.md`, `scripts/git-closure-gate-hook.js`,
`scripts/git-closure-gate-hook.spec.js`, `.claude/settings.json`
**Задачи:**
- [ ] Перевести шаблон и правила `issues`-скилла на файл-контракт: убрать собственное описание формата, мета-пункт DoD и условные пункты, DoD через имена CI-проверок, правило негативных Given/When/Then-случаев
- [ ] Добавить в скилл шаг независимого ревью спеки агентом со свежим контекстом перед созданием issue
- [ ] Хук на `gh issue create|edit` и на создание/правку issue через GitHub MCP запускает `issue-lint.js` и блокирует невалидное тело, с тестами

**Когда готова:** закрывает PRD AC «Хук на `gh issue create|edit` и на создание/правку issue через
GitHub MCP блокирует тело, не прошедшее линтер…», «Шаблон скилла не содержит мета-пункта…», «Скилл
требует негативный или граничный Given/When/Then-случай… и описывает шаг независимого ревью спеки…»
и часть «…`.claude/skills/issues/SKILL.md`… ссылаются на него и не содержат собственного описания
формата».

### Фаза 3: Верификатор проверяет по контракту
**Цель:** Верификатор судит пункты по ID, требует доказательств нужного вида и решает
детерминированные пункты кодом; старые issue продолжают проверяться.
**Затрагивает:** `.github/workflows/acceptance-verifier.yml`, `.github/verifier/prompt.md`,
`.github/verifier/schema.json`, `scripts/acceptance-verdict.js`, `scripts/acceptance-verdict.spec.js`
**Задачи:**
- [ ] Preflight в job `verify`: `issue-lint.js` из trusted checkout; невалидная спека — FAIL без вызова модели; issue без ID идёт в legacy-режим с пометкой в комментарии
- [ ] `id` пункта в схеме, точное совпадение множеств ID, текст пункта из issue, явный статус каждого `INV-n` (`PASS`/`FAIL`/`N/A`); промпт ссылается на контракт вместо собственного описания формата
- [ ] `kind` у ссылок; PASS по `behavior` требует `impl` и `test`
- [ ] Пункты `ci` и `absence` решает `acceptance-verdict.js`, модель по ним не судит

**Когда готова:** закрывает PRD AC «Невалидная по линтеру спека даёт FAIL без вызова модели»,
«Отчёт с множеством ID, не равным множеству ID issue, даёт FAIL…», «Каждый `INV-n` присутствует в
отчёте…», «PASS по `behavior`-пункту без ссылки `impl` и ссылки `test` даёт FAIL», «Пункты `ci` и
`absence` решаются скриптом…», «Issue без ID проверяется по старому пути…» и часть
«…`.github/verifier/prompt.md` ссылаются на него…».

### Фаза 4: Заморозка спеки и авторизация лейблов
**Цель:** Исполнитель не может ни изменить одобренную спеку, ни выдать себе обход проверки.
**Затрагивает:** новый workflow на `issues: labeled`, `.github/workflows/acceptance-verifier.yml`,
`.github/verifier/` (trusted-список владельцев), `scripts/` (нормализация и хеш тела, проверка
авторства лейбла) с тестами, `.claude/ralph/github.js` и его тесты, `.claude/skills/issues/SKILL.md`,
`.claude/skills/task-lifecycle/SKILL.md`
**Задачи:**
- [ ] Trusted-список владельцев и проверка авторства `spec-approved`/`manual-verified` по timeline в `report`
- [ ] Workflow на `spec-approved`: нормализация тела (чекбоксы не влияют) и маркированный комментарий `github-actions[bot]` с хешем; verify даёт FAIL при расхождении или отсутствии комментария
- [ ] Ralph берёт в работу только issue с действующим `spec-approved`
- [ ] Скилл и `task-lifecycle` вместо «исполнитель расширяет `Affects`» требуют правку через владельца и повторный `spec-approved`

**Когда готова:** закрывает PRD AC «Установка `spec-approved` владельцем фиксирует хеш нормализованного
тела…», «`spec-approved` и `manual-verified`, поставленные не владельцем из trusted-списка, не
засчитываются», «Ralph не берёт в работу issue без действующего `spec-approved`» и «Скилл и
`task-lifecycle` не предписывают исполнителю править `## Affects`…».

### Фаза 5: Детерминированные проверки
**Цель:** Скоуп диффа, обязательные проверки и ослабление тестов решает код, а не модель.
**Затрагивает:** `scripts/acceptance-verdict.js` (или вынесенные модули в `scripts/`) с тестами,
`.github/verifier/` (trusted-список обязательных проверок), `.github/workflows/acceptance-verifier.yml`,
`.github/verifier/prompt.md`
**Задачи:**
- [ ] Сравнение изменённых файлов с путями и glob-шаблонами `## Affects` в скрипте; `out_of_scope_files` модели — только подсказка
- [ ] Trusted-список обязательных CI-проверок заменяет хардкод CodeQL в `parseCiFailures`; отсутствующая, незавершённая или неуспешная проверка — FAIL
- [ ] Сканер ослабления тестов по `diff.patch` (перечень из PRD AC) как отдельная причина FAIL

**Когда готова:** закрывает PRD AC «Изменённый файл вне путей и glob-шаблонов `## Affects` даёт FAIL,
вычисленный скриптом», «Отсутствующая, незавершённая или неуспешная проверка из trusted-списка…» и
«Сканер ослабления тестов ловит как минимум…».

### Фаза 6: Надёжность и аудит вердикта
**Цель:** Вердикт воспроизводим и прослеживаем; шум одного прогона модели не даёт ни ложного FAIL, ни
ложного PASS.
**Затрагивает:** `.github/workflows/acceptance-verifier.yml`, `scripts/acceptance-verdict.js` с тестами
**Задачи:**
- [ ] Provenance в комментарии верификатора: head SHA, хеш тела issue, коммит файлов верификатора, модель, версия Codex CLI
- [ ] Проверка, что `VERIFIER_MODEL` — датированный snapshot, иначе FAIL
- [ ] Второй прогон модели отдельным job только при FAIL от модельных пунктов или невалидном отчёте; расхождение — вердикт `NEEDS_HUMAN`

**Когда готова:** закрывает PRD AC «Комментарий верификатора содержит head SHA…», «`VERIFIER_MODEL`,
не являющийся датированным snapshot-ом, даёт FAIL» и «Второй прогон выполняется только при FAIL…».

### Фаза 7: Эталонный набор и метрики
**Цель:** Изменения промпта верификатора измеряются на известных случаях; качество спек видно в
цифрах.
**Затрагивает:** эталонный набор в `.github/verifier/` или `project-management/`, новый ручной
workflow (`workflow_dispatch`), `scripts/` (прогон набора, метрики) с тестами
**Задачи:**
- [ ] Эталонный набор PR (минимум #434, #446, #463) с ожидаемыми вердиктами и ручной workflow, выводящий ложные PASS/FAIL текущего промпта
- [ ] Скрипт метрик по запросу: доля `UNVERIFIABLE` и число прогонов верификатора по issue из комментариев через GitHub API

**Когда готова:** закрывает PRD AC «Эталонный набор содержит как минимум PR #434, #446 и #463…» и
«Скрипт по запросу выводит по каждой issue долю `UNVERIFIABLE`…».

### Фаза 8: Holdout-сценарии для Ralph
**Цель:** У Ralph-задач есть проверки, под которые агент не может подогнать код.
**Затрагивает:** каталог holdout-сценариев в репозитории, `.claude/ralph/workspace.js` и его тесты,
`.github/workflows/` (job исполнения сценариев), `.github/verifier/` при необходимости,
`.claude/ralph/README.md`
**Задачи:**
- [ ] Формат и каталог holdout-сценариев по номеру issue
- [ ] Контроллер Ralph убирает каталог из клона агента и не допускает его в коммит агента, с тестами
- [ ] CI-job исполняет сценарии issue с default-ветки против головы PR; провал роняет вердикт верификатора

**Когда готова:** закрывает PRD AC «Holdout-сценарии issue отсутствуют в клоне агента Ralph и не
попадают в его коммит; CI-job исполняет их с default-ветки, и его провал даёт FAIL вердикта».

### Фаза 9: Разделение сторон и документация
**Цель:** Сторону спеки и сторону верификатора нельзя незаметно поменять одним PR; решения эпика
зафиксированы.
**Затрагивает:** `.github/workflows/ci.yml` (новая проверка), `scripts/` с тестами,
`project-management/DECISIONS.md`, `docs/12_ai_software_factory.md`, `docs/05_epics.md`,
`docs/06_roadmap.md`
**Задачи:**
- [ ] CI-проверка разделения: PR, меняющий и сторону спеки, и сторону верификатора, красный без лейбла владельца
- [ ] ADR-042 и амендмент ADR-041; обновление `docs/12_ai_software_factory.md`, `docs/05_epics.md` (EPIC-27), `docs/06_roadmap.md`

**Когда готова:** закрывает PRD AC «PR, одновременно меняющий сторону спеки и сторону верификатора
без лейбла владельца, получает красную CI-проверку» и «ADR-042 описывает контракт, заморозку,
авторизацию лейблов, `NEEDS_HUMAN` и holdout; `docs/12_ai_software_factory.md` и `docs/05_epics.md`
(EPIC-27) обновлены».

Epic base branch не рекомендуется (см. PRD, последний раздел): файлы верификатора читаются с
default-ветки, поэтому фазы мержатся в `main` последовательно, каждая начинает защищать следующие PR
только после мержа.
