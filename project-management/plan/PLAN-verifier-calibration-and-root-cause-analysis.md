# Plan: Калибровка фабрики — разбор первопричин вердиктов верификатора (EPIC-31)

**PRD:** `project-management/prd/PRD-verifier-calibration-and-root-cause-analysis.md`
**Дата:** 2026-09-30

Ни одна фаза не затрагивает `apps/api`, `apps/web`, PostgreSQL или `STORAGE_ROOT`: весь эпик —
репозиторная инфраструктура (`scripts/`, `.github/`, `docs/`, `project-management/`). Тесты
каждого скрипта — `scripts/**/*.spec.js` в той же задаче, что меняет скрипт (CI: `Test
(scripts)`). Код фабрики пишется без литералов проекта: пути, имена проверок, логины и модели
берутся только из trusted-конфигов (инвариант EPIC-27/28). Внешняя предпосылка — #484 (скрипт
метрик верификатора, EPIC-27 · Фаза 9): он должен быть закрыт до Фазы 4.

## Фазы реализации

### Фаза 1: Judge разбирает один круг (tracer bullet)
**Цель:** После каждого прогона верификатора на PR `task/ISSUE-*` появляется отдельный
комментарий с разбором первопричины по закрытой таксономии. Judge не влияет на вердикт; его
можно запустить вручную на прошлом PR. Круги пока не сравниваются: каждый прогон разбирается сам
по себе.
**Затрагивает:** новые trusted-файлы калибровки (таксономия, схема разбора, промпт, allowlist
модели Judge) на default-ветке, новые скрипты Judge и их `*.spec.js`, новый workflow Judge,
`project-management/DECISIONS.md`
**Задачи:**
- [ ] Таксономия (`primary_cause`, `responsibility`, подтипы дефектов issue и верификатора) и
      JSON-схема разбора в trusted-конфиге, плюс валидатор. Находка имеет устойчивый
      `finding_id`, criterion ID или `null`, доказательства на SHA/входном JSON/логе; source
      проверки отделён от причины. Схема допускает неполный разбор без уверенной атрибуции.
      Валидатор отклоняет значения вне таксономии, находку без ID пункта issue или `null`, а
      также модель Judge, совпадающую с моделью верификатора или отсутствующую в allowlist
      Judge. Тесты на каждый случай.
- [ ] Сборщик входов для одного прогона: артефакты верификатора (`verdict*.json`,
      `refs-problems*`, `absence.json`, `scope.json`, `ci.json`, tampering scan, provenance),
      issue и `spec-lint.json`, diff и список файлов, итоговый вердикт и комментарий
      верификатора, комментарий исполнителя с AC self-report (если есть). Ключ круга —
      repository/run ID/attempt исходного верификатора; два его внутренних прогона — один круг.
      Сохраняются base/head SHA, issue hash, trusted verifier SHA, версии/хэши конфигов,
      модель/параметры, снимки CI, approval и исключений, сведения о завершении jobs. Текущие
      API-данные не подменяют исторические без отметки. Сборщик формирует два входа: независимый
      без текущих/прошлых выводов верификатора/Judge и self-report исполнителя, и полный.
      Отсутствующее явно помечается. Тесты без сети.
- [ ] Промпт Judge на основе черновика владельца из исходных заметок: фиксированный порядок
      (контракт → независимая оценка → отчёт верификатора), два изолированных вызова с
      сохранением первого результата. Правила различают дефект issue и придуманное требование
      верификатора, согласованное изменение спеки и дефект старой спеки, ложную находку и ложный
      итоговый FAIL. `INSUFFICIENT_EVIDENCE` вместо догадки; инфраструктурный сбой отделён от
      дефекта реализации; запрет ослаблять проверку ради одного PR; без указания, какой
      компонент улучшается. Рендер комментария: отдельный маркер, пометка «калибровочный разбор,
      не список исправлений», первопричина, компонент, контрфактуал, дефекты с ID, рекомендации,
      JSON разбора в скрытом блоке. Тесты рендера.
- [ ] Workflow Judge: `workflow_run` после workflow верификатора (только PR `task/ISSUE-*` из
      этого репозитория) и `workflow_dispatch` с номером PR; права без commit status и лейблов;
      промпт, схема, таксономия, allowlist и скрипты — sparse checkout с default-ветки; голова
      PR — только данные; ключ модели — только в шаге вызова модели, тот же pin
      `openai/codex-action`, что у верификатора; модель — из отдельной repo-переменной. Два
      изолированных вызова учитывают одноразовый `drop-sudo`: отдельные jobs, между ними только
      артефакт стадии 1. Второй вызов не переписывает результат первого. Ручной запуск принимает
      номер PR и опционально run ID/attempt; без выбора берёт последнюю завершившуюся попытку и
      явно показывает её ID. JSON разбора — артефакт и скрытый блок с ревизией/хэшем и
      манифестом снимка для подтверждения. Повтор Judge обновляет разбор исходного круга, не
      добавляет круг. Проверить retention и границу исторического разбора. Тесты конфигурации и
      идемпотентности.
- [ ] ADR о Calibration Judge (через скилл `adr`): advisory-статус, отдельная модель, trust
      boundaries, закрытая таксономия, эталон — разметка владельца, хранение в GitHub; ссылка из
      ADR-041/042.

**Когда готова:** закрывает PRD AC «Таксономия лежит в trusted-конфиге. Схема разбора отклоняет
значения `primary_cause`, `responsibility` и подтипов вне конфига», «Разбор, в котором находка
не ссылается ни на ID пункта issue, ни на `null`, отклоняется схемой», «Workflow Judge
запускается после завершения верификатора для PR `task/ISSUE-*` и вручную по номеру PR…»,
«Workflow Judge не имеет прав на commit status и лейблы…», «Промпт, схема, таксономия, allowlist
и скрипты Judge читаются с default-ветки…», «Модель Judge, совпадающая с моделью верификатора
или отсутствующая в allowlist Judge, даёт ошибку разбора…», «Независимая оценка строится первым
из двух изолированных вызовов…», «Отсутствующий или нечитаемый вход помечается в разборе как
отсутствующий…», «ADR о Calibration Judge принят…», AC о исторических снимках и идентичности
круга (без сравнения), а также часть «Комментарий Judge — отдельный комментарий со своим
маркером… начинается с явной пометки…» (без документации).

### Фаза 2: Круги — сравнение прогонов на одном PR
**Цель:** Judge видит историю PR. Переход оценки критерия и судьба конкретного дефекта хранятся
раздельно. Известно, что изменилось в задаче и значимых входах; несопоставимые круги не выдаются
за нестабильность модели. Комментарий показывает все круги и сохраняет ревизии разборов.
**Затрагивает:** скрипты Judge и их `*.spec.js`, схема разбора и промпт Judge (trusted-файлы
калибровки), workflow Judge
**Задачи:**
- [ ] Детерминированное сравнение соседних кругов: тип задачи `code`/`issue`/`both`/`none` по
      head SHA и issue hash; отдельно fingerprint значимых входов и сопоставимость
      `COMPARABLE`/`INPUTS_CHANGED`/`UNKNOWN`. CI snapshot нормализуется без зависимости от
      порядка и технических временных меток. Изменение trusted policy, модели/параметров, CI,
      approval или исключений при `none` не доказывает нестабильность. Тесты на каждый тип,
      изменённые входы и неполный provenance.
- [ ] Переходы статусов критериев по ID, включая `NOT_REPORTED`, и сравнение процитированных
      строк — скриптом. При `none` изменение статуса — `FLIP`, отдельно от диагноза причины.
      FAIL → PASS не присваивает `RESOLVED`, FAIL → FAIL не доказывает тот же дефект. Тесты.
- [ ] Схема и промпт: класс судьбы дефекта
      `INITIAL`/`RESOLVED`/`PERSISTING`/`NEW_REAL`/`LATE_FINDING`/
      `FIX_REGRESSION`/`FALSE_FINDING`/`UNKNOWN`, отдельно переход статуса. Сопоставление по
      устойчивому finding ID, механизму и доказательствам; один AC-ID может иметь несколько
      находок. Подтверждённая настоящая находка первого круга — `INITIAL`; при нехватке
      доказательств — `UNKNOWN`. Позднее исправление не стирает класс первого обнаружения.
      Модель решает реальность/историю дефекта и причинную связь; NEW_REAL отделён от регрессии
      исправления. Изменение issue требует сопоставления смысла версий, не автоматического
      ISSUE_DEFECT. На вторую стадию идут предыдущий разбор/provenance, diff кода и изменения
      спеки/политики; на независимую стадию прошлые выводы не попадают. Тесты схемы,
      сопоставления и входов.
- [ ] Комментарий содержит таблицу кругов (ключ, номер, head SHA, тип изменения, сопоставимость,
      verdict, переходы и классы), последний разбор и JSON всех кругов. Ревизии имеют хэш;
      обновление одного круга сохраняет остальные. Повтор события и конкурентная публикация не
      теряют историю. Тесты хранения/публикации и рендера.

**Когда готова:** закрывает PRD AC о сохранении истории комментария, ключе круга и
сопоставимости (часть сравнения), переходах статусов отдельно от судьбы дефекта, допустимых
классах/UNKNOWN, ревизиях и сохранении истории при повторной/конкурентной публикации.

### Фаза 3: Парные golden-кейсы с `mutation.patch`
**Цель:** Golden eval меряет ошибки верификатора в обе стороны: корректный PR должен дать PASS,
тот же PR с одной намеренной порчей — FAIL. Не зависит от Фаз 1–2, можно делать параллельно.
**Затрагивает:** `.github/workflows/acceptance-verifier-eval.yml`, `scripts/verifier-eval.js`,
`scripts/verifier-eval.spec.js`, `.github/verifier/golden/`,
`.github/verifier/golden/README.md`, `project-management/DECISIONS.md`
**Задачи:**
- [ ] Eval накладывает `mutation.patch` на head SHA; после мутации строит diff от base SHA,
      список файлов (включая добавленные), scope, tampering и другие входы, зависящие от кода.
      Исходный head SHA и хэш патча/результирующего дерева хранятся отдельно. Конфликт или
      неконсистентный пакет — `run failure`. CI явно заморожен для offline eval, код мутации не
      исполняется в доверенной среде; approval, исключения и версии политики — фикстуры. Тесты
      пересборки входов, конфликтов и добавленного файла. README описывает протокол; амендмент
      ADR-042 (ISSUE-483).
- [ ] Case фиксирует expected verdict, criterion ID или null и reason code. Eval проверяет
      ожидаемую причину: посторонний FAIL не считается успешным обнаружением мутации. Отчёт
      разделяет false PASS/FAIL, run failures и несовпадение причины. Тесты.
- [ ] Выбрать не меньше 5 корректных PR (кандидаты — PR с PASS после ISSUE-482). Владелец
      подтверждает исходные кейсы по issue и trusted-политике; прежний PASS не служит эталоном.
      Добавить пары: PASS-кейс и мутация с FAIL по ожидаемому ID/правилу и reason code. Пары
      покрывают убранный negative/edge-тест, нарушенный `INV`, одностороннее cross-layer
      изменение и файл вне `## Affects`. `scripts/verifier-eval.js` считает по ним ложные PASS и
      ложные FAIL.

**Когда готова:** закрывает PRD AC о `mutation.patch` и пересборке входов, проверке ожидаемой
причины и наборе не меньше 5 подтверждённых пар PASS/FAIL, покрывающих заданные виды порчи.

### Фаза 4: Разметка владельца и агрегат калибровки
**Цель:** Один лейбл остаётся сводкой PR. Ожидаемые verdict кругов и диагнозы подтверждаются
отдельно, в том числе одной командой для всех просмотренных ревизий. Скрипт показывает цель,
качество данных и компоненты для исправления, не выдавая гипотезы Judge за эталон. Требует
закрытого #484 и Фаз 1–2.
**Затрагивает:** `scripts/verifier-metrics.js`, `scripts/verifier-metrics.spec.js`,
trusted-конфиг порогов калибровки, переиспользуемый `scripts/label-authority.js` (только если
нужна общая функция)
**Задачи:**
- [ ] Авторизация лейблов (`verifier-correct`/`verifier-false-fail`/`verifier-false-pass`) и
      `/calibration` по timeline/комментариям: только владельцы из owners.json, не боты.
      Последний авторизованный лейбл — сводка, не подтверждение всех кругов. История может
      содержать оба типа ошибки; сводка false-pass не стирает false-fail. Тесты.
- [ ] Команды `round=<N> expected=…`, `cause=… [subtype=…]`, `finding=<finding_id> class=…`
      подтверждают/исправляют соответствующее поле конкретной ревизии. Criterion ID разрешён
      только при единственной находке. `confirm=all snapshot=<hash>` использует показанный в
      комментарии манифест точного списка кругов и хэшей просмотренных разборов; отсутствующий
      или несовпадающий снимок отклоняется. Новые круги/ревизии требуют нового подтверждения.
      Последняя авторизованная команда побеждает для одного поля/ревизии, история исправлений
      сохраняется. Тесты авторизации, неоднозначных команд, ревизий и разных уровней
      подтверждения.
- [ ] Режим калибровки verifier-metrics.js: матрица по кругам с подтверждённым expected verdict,
      отдельно NEEDS_HUMAN/UNDECIDABLE/технические сбои. False PASS — среди подтверждённых
      дефектных кругов, false FAIL — среди корректных; инфраструктура не смешивается с
      семантикой. Показывать числители/знаменатели, покрытие разметкой, версии policy/model.
- [ ] Число кругов до PASS для сошедшихся PR и отдельно несошедшиеся; классы по уникальным
      подтверждённым дефектам: происхождение по первому обнаружению (INITIAL включён в
      знаменатель), состояние по последнему доказанному классу; UNKNOWN отдельно, FLIP среди
      сопоставимых повторов. Частоты причин/подтипов отделяют подтверждения от гипотез. Повтор
      одного дефекта и его каскадные симптомы не дают дополнительные независимые случаи. Тесты
      на фикстурах.
- [ ] Пороги из trusted-конфига и подтипы с ≥ 3 независимыми подтверждёнными случаями. Лейбл не
      заменяет подтверждения; нулевой знаменатель — «нет данных», не выполненный порог. Один
      воспроизводимый критический дефект допускает немедленное отдельное системное issue, а не
      автоматическое применение рекомендации. Тесты метрик и порогов.

**Когда готова:** закрывает PRD AC о сводных лейблах, авторизованных командах и подтверждении
ревизий, а также агрегате с явными знаменателями, дедупликацией, неполными/неподтверждёнными
оценками, техническими сбоями и отсутствием данных. Требует закрытого #484 и Фаз 1–2.

### Фаза 5: Документация и включение
**Цель:** Процесс калибровки описан, и Judge работает на реальных PR с выбранной моделью.
**Затрагивает:** `docs/12_ai_software_factory.md`, trusted allowlist модели Judge,
repo-переменная модели Judge
**Задачи:**
- [ ] `docs/12_ai_software_factory.md` §5/§6: цель и пороги (0 ложных PASS, ложных FAIL ≤ 10 %,
      `NEEDS_HUMAN` ≤ 10 %, поздних находок ≤ 10 % на ≥ 20 размеченных PR с подтверждёнными
      оценками; golden eval без ошибок и с правильными причинами). Описать знаменатели,
      неизвестную историю/неполноту и границу «критерий пилота, не допуск к деплою». Таксономия,
      переходы статусов отдельно от классов дефектов, сопоставимость входов, подтверждение
      ревизий владельцем. Правило ручного флоу: исправляющему ИИ только отчёт верификатора.
      Правило «≥ 3 независимых случая → системное изменение» с исключением для критического
      воспроизводимого дефекта; калибровочный набор, выборочный режим, Judge в цепочке доверия.
- [ ] Выбрать модель Judge из доступных в аккаунте (не `VERIFIER_MODEL`), внести её в allowlist
      Judge и задать repo-переменную. Первый `workflow_dispatch` на нескольких прошлых PR делает
      владелец, это не gated-критерий.

**Когда готова:** закрывает PRD AC «Документация фабрики описывает цель и её пороги, таксономию,
разметку владельца, правило «≥ 3 случая → системное изменение», калибровочный набор и режим
после достижения цели» и часть «…Документация фабрики описывает правило ручного флоу:
исправляющему ИИ передаётся только отчёт верификатора».

Порядок: 1 → 2 → 4 (4 также после #484); 3 параллельно с 1–2; 5 последней. Epic base branch не
рекомендуется: все фазы — инфраструктура вне `apps/*`, и каждая независимо сливается в `main`,
не ломая его, потому что Judge advisory и не участвует в CI-гейтах.
