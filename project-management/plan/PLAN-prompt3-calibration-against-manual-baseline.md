### Фаза 1: Импорт и адаптация Prompt 3 текста

**Цель:** Заменить placeholder-контент `prompt_3` `PromptTemplate` на реальный, вручную
отточенный текст, пригодный для использования в автоматическом pipeline (не привязанный к
ChatGPT web app специфике).

**Затрагивает:** apps/api (`prompt-templates/`, возможно `pipeline/schemas/pre-pdf-check.schema.ts`)

**Задачи:**
- [ ] Прочитать `!prompt_3_final_pre-PDF_check_CURRENT_WORK_SYNC.txt` целиком и провести аудит на
      допущения, специфичные для ChatGPT web app (live browsing, файловые вложения, неявная
      сессионная память) — та же методология, что уже применена к Prompt 1/2 (issues #193/#198).
- [ ] По каждому найденному допущению: замаппить на существующий механизм (carry-forward,
      knowledge sources, manual note) либо переформулировать с явным fallback — ни одно не
      отбрасывать молча.
- [ ] Сверить референс-текст со схемой `pre-pdf-check.schema.ts` — если найдены поля вывода,
      которых в схеме нет (например структурированный результат "Current-work block check"),
      решить, нужно ли additive-поле (по прецеденту `quality_score`) — BOP-style findings уже
      решено НЕ выносить в отдельное поле, переиспользуют `corrections`.
- [ ] Создать новую версию `PromptTemplate` для `prompt_3` (не перезаписывая `v1` placeholder),
      сделать её активной.
- [ ] Обновить/убрать комментарий "Placeholder content pending full prompt-engineering review"
      для `prompt_3` в `prisma/seed.ts`/БД.

**Когда готова:** закрывает пункты PRD `## Критерии готовности`:
- "`PromptTemplate` контент для `prompt_3` основан на реальном
  `!prompt_3_final_pre-PDF_check_CURRENT_WORK_SYNC.txt` тексте, не написан с нуля; `prisma/seed.ts`
  / БД больше не помечает `prompt_3` как 'Placeholder content pending full prompt-engineering

- "Каждое найденное web-app-специфичное допущение в тексте `prompt_3` явно задокументировано с

### Фаза 2: Расширение convergence-методологии под Prompt 3

**Цель:** Дать golden-сравнению (Фаза 3) чёткие, проверяемые критерии — текущий
`docs/10_calibration_and_parity.md` §5 написан под decision/content-match Prompt 1/2 и не
покрывает `corrections`/`readiness`/BOP-check напрямую. Также закрыть архитектурный хвост
(`export_blocked`) документально, чтобы он не остался тихо нерешённым.

**Затрагивает:** project-management (`docs/10_calibration_and_parity.md`), project-management
(`DECISIONS.md`)

**Задачи:**
- [ ] Добавить в `docs/10_calibration_and_parity.md` §5 раздел convergence-критериев для Prompt 3:
      `corrections` предлагают валидные `field_path` и не ссылаются на несуществующие пути;
      `corrections` не изобретают факты, отсутствующие в `02_targeted_cv_content.json`; BOP-style
      check реально ловит известные проблемные паттерны (16 из референс-текста), если они
      присутствуют во входном CV-контенте; `readiness`-вердикт согласуется с решением, которое
      project owner фактически принял в ручном "Version 2"-разделе того же golden-кейса.
- [ ] Задокументировать метод проверки BOP-check конвергенции: грепом по 16 известным паттернам во
      входном CV-контенте против финального экспортированного текста (после применения
      `corrections`) — присутствовал на входе и отсутствует на выходе = поймали.
- [ ] Зафиксировать решение "`export_blocked` остаётся advisory-only" как новый ADR (или явное

**Когда готова:** закрывает пункты PRD `## Критерии готовности`:
- "`docs/10_calibration_and_parity.md` §5 расширен собственными convergence-критериями для
  Prompt 3 (не переиспользует decision/content-match критерии Prompt 1/2 буквально, раз они не
  применимы к corrections/readiness/BOP-check напрямую)."
- "Решение '`export_blocked` остаётся advisory-only' зафиксировано в `DECISIONS.md` как новый ADR

### Фаза 4: Итерация до convergence

**Цель:** По результатам Фазы 3 либо подтвердить, что Prompt 3 сходится с ручным baseline, либо
диагностировать реальную причину расхождения (по прецеденту #238 — сначала диагностировать, не
чинить промпт вслепую) и внести новую версию `PromptTemplate`.

**Затрагивает:** apps/api (`prompt-templates/`, возможно код — если причина расхождения окажется
не в промпте, аналогично найденному в #238 code-багу), project-management (`TEST_LOG.md`,
`comparison.md`)

**Задачи:**
- [ ] По каждому расхождению из Фазы 3 определить причину: формулировка промпта, недостающий
      контекст/evidence, или код-баг (рендеринг/маппинг) — не чинить промпт там, где причина не в
      нём (тот же Key Invariant, что уже применялся в #238).
- [ ] При необходимости — новая версия `PromptTemplate` для `prompt_3` (никогда не перезаписывая
      предыдущую) и повторный прогон затронутых golden-кейсов.
- [ ] Записать финальную запись в `project-management/TEST_LOG.md` с итоговым выводом:
      конвергенция достигнута, или задокументированное принятое исключение с обоснованием.

**Когда готова:** закрывает пункты PRD `## Критерии готовности`:
- "Convergence по расширенным критериям выполнены для golden-кейсов Prompt 3, либо
  задокументированное принятое исключение зафиксировано с обоснованием."
- "Версионная история `PromptTemplate` для `prompt_3` отражает итерации калибровки (несколько
  версий, предыдущие сохранены неактивными, не перезаписаны)."

---

Эпик небольшой (один промпт, методология уже отработана на Prompt 1/2), все 4 фазы — apps/api +
project-management, ни одна не касается apps/web. Per PRD's собственная оценка: отдельная epic
base branch (ADR-025) не нужна — каждая фаза может закрываться отдельным PR напрямую в `main`, по
аналогии с тем, как Фазы 6/7 EPIC-24 (content-level) уже делались без `-base` ветки. Фазы 2 и 3
частично независимы (Фаза 2 — методология, Фаза 3 — прогон), но Фаза 3 использует критерии из
Фазы 2 для оценки результата, поэтому порядок 1 → 2 → 3 → 4 сохраняется.
